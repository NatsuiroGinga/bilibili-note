## 三、进程分析（1 分钟粒度 `mcdn_cpu_moni`）

### 🚨 核心发现：`mcdn_cpu_moni` 指标无法反映瞬时 CPU

对比 ps 进程 CPU 总和 vs 节点实际 CPU（CSV）：

| 时刻 | ps 进程 CPU 总和 | 节点实际 CPU（CSV） |
| --- | --- | --- |
| 16:14（暴冲峰值） | 759% | **90.6%** |
| 16:20（下线时刻） | 761%（↑2%） | **85.7%** |
| 16:22（下线后 2 分钟） | 761%（不变） | **43.1%**（↓42%）🚨 |

**ps 进程 CPU 总和在暴冲和下线前后几乎完全不动（759% → 761%），但节点 CPU 暴跌了 42 个百分点。**

这意味着：

- nginx_worker 一直显示 328~329%，下线前后不变
- bvc-iobone-bin 一直显示 261~263%，下线前后不变
- 所有常驻进程合计 759~762%，15 分钟内仅波动 ±3%
- 但节点 CPU 从 90.6% 跌到 43.1%

### 结论

**`mcdn_cpu_moni` 上报的是平滑/累计值，不是瞬时 CPU 使用率。** 真正导致暴冲的进程——那个在 16:14~16:20 几分钟内把节点打到 90% 的东西——没有被这个指标采集到，或者被平滑掉了。

> ⚠️ **这直接影响 checkStatus 的 CPU 检查方案设计。** 如果使用 `sum(mcdn_cpu_moni{type="cpu"})`，值永远在 760% 附近，无法区分节点是 43% 闲还是 91% 忙。需要改用节点级原生 CPU 指标（如 `node_cpu_seconds_total{mode="idle"}` 反推）来判断实际空闲率。

## 五、根因判断

### 结论

**v-308 的暴冲来源无法通过 `mcdn_cpu_moni` 指标确定。**

1. `mcdn_cpu_moni` 是平滑/累计值，不反映瞬时 CPU——这是本次分析最重要的发现
2. bvc-iobone-bin 和 nginx_worker 在下线前后 CPU 值不变，排除它们是暴冲来源
3. 拍到的小量瞬发进程（python 24%、docker 11%）合起来也只有 ~40%，无法解释节点 90% 的暴冲
4. 真正的元凶进程没有被 `mcdn_cpu_moni` 采集，需要在告警触发时用 `top` 或 `/proc` 直接抓
