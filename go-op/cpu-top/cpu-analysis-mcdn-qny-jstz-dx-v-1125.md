## 四、根因判断

### 直接原因

这台机器是**混合型**问题：

1. **blink_collect 有 24 个并行实例**（CPU 合计 619%），说明也存在 fork bomb 现象。虽然比 v-1169（28 个）略少，但同样严重
2. **nginx_worker 持续吃 3.8 核**（三台中最高的），承担了大量流量
3. 常驻进程 689%（6.9 核）+ blink_collect 619%（6.2 核）= **13.1 核**，峰值 302% 出现时说明多进程叠加

### 暴冲模式解读

13:16-14:58 期间最疯狂，每 4~6 分钟一次暴冲。模式类似 v-1109 的周期性脚本 + v-1169 的 blink fork bomb 叠加。

### 四台机器横向对比

| 维度 | v-1125（本机） | v-1169 | v-1109 | v-308 |
| --- | --- | --- | --- | --- |
| **nginx_worker** | 🥇 379%（3.8核） | 303%（3核） | 183%（1.8核） | 329%（3.3核） |
| **bvc-iobone-bin** | 133%（1.3核） | 🥇 599%（6核） | 149%（1.5核） | 262%（2.6核） |
| **常驻总消耗** | 689%（6.9核） | 🥇 1092%（11核） | 440%（4.4核） | 759%（7.6核） |
| **blink_collect 实例** | 24 个 | 🥇 28 个 | ✅ 1 个 | ✅ 7 个 |
| **ps 可用性** | ✅ 2分粒度 | ✅ 2分粒度 | ✅ 2分粒度 | ❌ 指标不反映瞬时CPU |
| **暴冲来源** | ✅ blink+nginx | ✅ bvc+blink | ✅ python脚本 | ❓ 未被采集 |
| **类型** | 🔴 混合型 | 🔴 基座饱和型 | 🟡 脚本突发型 | ❓ 待定 |

**结论：四台机器虽然症状相同，但根因分属不同类型。v-308 因 mcdn_cpu_moni 指标平滑问题，无法通过当前数据确认根因。**

## 五、回源带宽与 CPU 暴冲的因果关系

> 数据源：7/6~7/7 节点回源带宽（1 分钟粒度，`mcdn-qny-jstz-dx-v-1125`）

### 7/7 下线时刻（10:48）的回源带宽

```text
10:00  313 Mb/s
10:08  998 Mb/s  ← 第一次暴冲
10:26  100 Mb/s  ← 瞬间回落
10:40  1.01 Gb/s ← 第二次暴冲开始
10:43  1.11 Gb/s
10:44  1.19 Gb/s
10:45  1.10 Gb/s
10:46  1.17 Gb/s
10:47  1.16 Gb/s
10:48  1.27 Gb/s ← 触发下线的时刻
10:49  1.21 Gb/s
```

**10:40~10:50 这 10 分钟内回源带宽从 370 Mb/s 暴冲到 1.27 Gb/s（3.4x），期间 v-1125 上午排查时 bvc=355%、si=32.6%、busy=68.9%，随后触发下线（88.12%）。**

### 因果链

```text
回源带宽暴冲 (1.27 Gb/s)
  → 网卡收发数据包数暴增
  → si（软中断）飙升到 32.6%（处理网卡中断）
  → ksoftirqd 线程抢占 CPU
  → bvc-iobone-bin 同时处理翻倍的业务数据（355%，历史平均 133% 的 2.7x）
  → nginx worker 也从 22~33% 升到 40~50%
  → busy = us + sy + si > 80%
  → 告警触发 → 下线
```

### 回源带宽统计（7/6 16:00 ~ 7/7 12:00）

| 指标 | 值 |
| ---- | ---- |
| min | 31.7 Mb/s |
| max | **998 Mb/s** |
| avg | 467.2 Mb/s |
| 晚高峰 avg（20~23点） | 614~746 Mb/s |

**回源带宽是上游根因。** 带宽暴冲直接驱动了 si（网卡中断）和 bvc-iobone-bin（业务处理量）的同步增长。正常机器 v-357 的 bvc 只有 161%、si 只有 17.8%——它的回源带宽大概率也远低于 1 Gb/s。
