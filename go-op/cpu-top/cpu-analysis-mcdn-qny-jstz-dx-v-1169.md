## 三、根因总结

### 直接原因

**bvc-iobone-bin + nginx_worker** 两个业务进程固定消耗约 9 核 CPU。2 小时内触发值分别为 80.03% 和 80.05%，仅超过阈值 **0.03~0.05 个百分点**，说明这台机器的 CPU 基线本身就贴近 80%，任何微小的进程抖动都会触发告警下线。

### 系统性问题

> ⭐ **自动恢复逻辑存在缺陷**：当前 `shouldOnline` 只按时间判定（30 分钟），不检查节点健康状态。机器上线后立刻接入流量，bvc-iobone-bin 的 CPU 立刻打满，再次触发下线，形成死循环。

这一点在代码层面已在 [autoonline.go](app/manba-bi/internal/service/autoonline.go) 中预留了 `checkStatus` 函数（当前恒返回 `true`），健康检查逻辑暂未落地。

### 短期建议

| 优先级 | 操作 | 预期收益 |
| ---- | ---- | ---- |
| **P0** | `checkStatus` 上线前查 CPU，当前 > 70% 则暂缓上线 | 避免擦边触发导致的死循环 |
| P1 | 排查 blink_collect 为什么同时 fork 28 个子进程 | 释放 ~21 核 buffer |
| P2 | 触发值连续 N 次擦边（80~82%）时，调高阈值到 90% | 避免反复上下线 |

### 长期建议

| 优先级 | 操作 | 预期收益 |
| ---- | ---- | ---- |
| P1 | 迁移到 relay + top 采集方案（本分支已开发），自动记录 top 信息到 msg 字段 | 上线后即可回溯 CPU 进程明细 |
| P2 | 评估 bvc-iobone-bin 是否可做 CPU 限流或垂直扩容 | 从源头控制 CPU 基线 |
