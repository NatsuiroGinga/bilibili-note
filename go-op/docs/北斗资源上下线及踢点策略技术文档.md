# 北斗资源上下线及踢点策略技术文档

> 基于代码分析和官方文档的完整技术说明，涵盖 MCDN 节点在北斗平台的上下线触发条件、执行流程和恢复机制。

---

## 1. 策略全景图

当前系统中存在以下资源上下线策略，按触发方式分为**主动踢点**和**自动恢复**两大类：

| 编号 | 策略名称 | 类型 | 动作 | 所在服务 |
|------|---------|------|------|---------|
| 1 | **告警平台监控踢点** | 踢点 | 修改 `is_disabled=true` | manba-dispatcher → manba-bi |
| 2 | **预测下线（卡顿率）** | 踢点 | 修改 `is_disabled=true` | manba-bi |
| 3 | **调度器直接下线** | 踢点 | 修改 `is_disabled=true` | manba-bi |
| 4 | **告警通知** | 通知 | 仅发消息，不下线 | manba-bi |
| 5 | **线路探测可用率** | 数据可信度判断 | 控制调度器是否采信探测数据 | portal |
| 6 | **自动上线恢复** | 恢复 | 修改 `is_disabled=false` | manba-bi |
| 7 | **心跳恢复** | 恢复 | 重新上报心跳后自动恢复 | portal |
| 8 | **Blink 恢复** | 恢复 | 原地重启或重新交付 | blink |
| 9 | **熔断保护** | 保护 | 当日下线次数达阈值后停止实际下线 | manba-bi |

## 2. 告警平台监控踢点（主流程）

### 2.1 策略含义

这是**最核心的踢点路径**。告警平台监控到节点异常指标后，通过 webhook 通知北斗，北斗消费消息后执行下线。当前接入的监控指标包括：**丢包率、重传率、磁盘故障率、CPU 负载、根目录、IP 冲突**。

### 2.2 完整数据流

```
[节点异常] → [moni 监控系统] → [告警平台触发告警规则]
    │
    ├─ BVC 告警规则: https://cloud.bilibili.co/alarm/config/alertRule/detail?id=860072
    └─ MOB 告警规则: https://cloud.bilibili.co/alarm/config/alertRule/detail?id=859813
    │
    ▼
[告警平台 webhook 推送]
    │
    ▼
[manba-dispatcher]
    POST /api/v1/portal/arrange/webhook
    │
    ▼
[databus] topic: Mcdn-dispatcher-01-T, group: Mcdn-dispatcher-01-OpsCdnops-P
    │
    ▼
[manba-bi] 消费 databus 消息
    │
    ├─ 熔断检查 → count >= MAX → 仅入库通知
    │
    └─ 未熔断 → 调用 portal 接口下线
                 PUT /api/v1/portal/pcdn?name={节点名}
                 Body: {"is_disabled": true}
                 │
                 ├─ SQL: UPDATE p_instances SET is_disabled=1, ... WHERE name=?
                 └─ 录入 msg_data_all + 企微/Blink 通知
```

### 2.3 告警规则参考

| 业务 | 告警规则 | 主要监控指标 |
|-----|---------|------------|
| BVC | [告警规则 860072](https://cloud.bilibili.co/alarm/config/alertRule/detail?id=860072) | 丢包率、重传率等 |
| MOB | [告警规则 859813](https://cloud.bilibili.co/alarm/config/alertRule/detail?id=859813) | 丢包率、重传率等 |

## 3. 预测下线（PredictOffline，action_id=200）

### 3.1 策略含义

基于**视频云（BVC）卡顿率（BufferRate）**指标的预测性下线。在问题恶化前将节点踢下线，提前规避高峰期服务质量不达标的风险。

> ⚠️ 此路径依赖 databus 消息中的 action_id=200，与上述告警平台告警监控路径**并行存在**。

### 3.2 触发流程

```
Databus 收到 action_id=200
    │
    ▼
PredictOffline()
    │
    ├─ 熔断检查 → count >= MAX → 仅通知不下线
    │
    └─ 未熔断 → 查询 BVC 获取该节点的卡顿率数据
                  │
                  ▼
            根据 BufferRate + 时段 判定
```

### 3.3 卡顿率判定逻辑

**数据来源：** BVC 接口 `/dataplane-api/mcdnAnalysis/sidStats.do`，查询最近 10 分钟内的卡顿率和播放次数。

**时段判定**（[Gettime 函数](app/manba-bi/internal/service/service.go#L555-L567)）：

| 时段 | 时间范围 |
|------|---------|
| 高峰期 | 10:00 ~ 14:30 及 17:30 ~ 次日 03:00 |
| 低峰期 | 03:00 ~ 10:00 及 14:30 ~ 17:30 |

**判定分支表：**

| 时段 | 卡顿率（BufferRate） | 动作 | 说明 |
|------|---------------------|------|------|
| 低峰期 | ≤ 3.5% | 不操作 | 卡顿率低，继续正常运行 |
| 低峰期 | 3.5% ~ 5% | **进入观察期** | 临界状态，等待 20 分钟后再次检测 |
| 低峰期 | > 5% | **立即下线** | 低峰期就超过 5%，高峰期会更差 |
| 高峰期 | ≤ 3.5% | 不操作 | 卡顿率正常，继续运行 |
| 高峰期 | 3.5% ~ 4% | **进入观察期** | 临界状态，等待 20 分钟后再次检测 |
| 高峰期 | > 4% | **立即下线** | 高峰期卡顿率超过 4%，立即下线 |

**观察期（Observed）逻辑**（[Observed 函数](app/manba-bi/internal/service/service.go#L694-L752)）：

```
进入观察期
    │
    ▼
等待 20 分钟（time.Second * 1200）
    │
    ▼
再次查询 BVC 卡顿率
    │
    ├─ BufferRate > 4% → 下线（is_disabled=true），录入操作记录
    │
    └─ BufferRate ≤ 4% → 符合服务标准，继续服务
```

## 4. 调度器直接下线（DirectOffline，action_id=100）

### 4.1 策略含义

收到调度器或告警系统的直接下线指令，立即将节点踢下线，不做卡顿率等业务判断。

### 4.2 执行动作

```
DirectOffline(count, msgdata)
    │
    ├─ 熔断检查 → count >= MAX → 仅入库通知，不下线
    │
    └─ 未熔断 → portal.ChangeServerStatus(name, true)
                 │
                 ├─ 超时 3 秒保护
                 └─ 录入 msg_data_all + 企微/Blink 通知
```

> 注意：当前代码中 OwnerCdn 函数对接到的 action_id=100/200 消息标记为"功能未开发"（[OwnerCdn 函数](app/manba-bi/internal/service/service.go#L524-L553)），实际下线操作由告警平台主流程（第 2 节）完成。

## 6. 自动上线恢复

### 6.1 策略含义

被踢下线的节点，BI 系统根据当日下线次数自动恢复上线。**当前健康检查为空实现**（调用 moni 后直接返回 true，不做实质性检查）。

### 6.2 触发方式

定时任务 `AutoOnline()` 周期性运行（[autoonline.go](app/manba-bi/internal/service/autoonline.go)），每 360 秒扫描所有下线节点。

### 6.3 恢复规则

| 今日下线次数 | 等待时间 | 健康检查 | 说明 |
|:----------:|:--------:|:--------:|------|
| 1 次 | **30 分钟** | 通过（空实现） | 距最后一次下线 ≥ 30 分钟 |
| 2 次 | **2 小时** | 通过（空实现） | 距最后一次下线 ≥ 2 小时 |
| ≥ 3 次 | **不自动恢复** | — | 需人工上线或 Blink 恢复 |

**健康检查说明：** 当前 `checkStatus` 函数（[autoonline.go#L79-L83](app/manba-bi/internal/service/autoonline.go#L79-L83)）调用 `moni.GetInstance` 后**忽略返回值**，直接 `return true`。文档说"健康检查通过"但实际上未做任何实质性检测。

### 6.4 恢复流程

```
AutoOnline()
    │
    ├─ 查询 msg_data_all 表（当天 action_id=100/200 的下线记录）
    ├─ 按节点聚合，统计当日下线次数
    │
    ├─ 对每个下线节点：
    │   ├─ 今日第 1 次下线且距最后一次 ≥ 30 分钟 → 自动上线
    │   ├─ 今日第 2 次下线且距最后一次 ≥ 2 小时  → 自动上线
    │   └─ 今日 ≥ 3 次下线 → 跳过（需人工恢复）
    │
    └─ portal.ChangeServerStatus(name, false)
        │
        ├─ SQL: UPDATE p_instances SET is_disabled=0, dial_ips='', updated_at=NOW() WHERE name=?
        ├─ 录入 msg_data_all（action_id=400）
        ├─ 企微通知「自动上线成功」
        └─ Blink 通知
```

### 6.5 恢复生效延迟

调用 `ChangeServerStatus(name, false)` 后：
1. 数据库 `is_disabled=0` 已更新
2. **但 `dial_ips` 同时被清空**（SQL 中 `dial_ips=''`）
3. 节点**不会立即出现在服务列表**
4. 需要等待 MCDN agent 重新上报心跳、填充 `dial_ips` 并更新 `updated_at`
5. portal 每 30 秒刷新缓存，查询条件：
   ```sql
   updated_at > NOW() - INTERVAL 3 MINUTE
     AND is_deleted = 0
     AND dial_ips != ''
     AND type = 'v'
   ```
6. 节点在下一个 30 秒窗口内重新出现

## 7. 心跳恢复

### 7.1 策略含义

北斗节点超过 3 分钟未上报心跳包，后续心跳恢复后，portal 自动将其重新纳入服务列表。**全程无需调用任何下线/上线 API**。

### 7.2 恢复流程

```
MCDN agent 恢复运行
    │
    ▼
重新上报拨测结果（dial_ips、端口状态等）
    │
    ▼
portal 更新 p_instances.updated_at 和 dial_ips
    │
    ▼
portal 每 30 秒缓存刷新（条件见下方 SQL）
    │
    ▼
查询到该节点更新 → 自动出现在服务列表
```

**portal 刷新 SQL**（[dao/mcdn.go](app/portal/internal/dao/mcdn.go)）：
```sql
SELECT * FROM p_instances
WHERE updated_at > NOW() - INTERVAL 3 MINUTE
  AND is_deleted = 0
  AND dial_ips != ''
  AND type = 'v'
```

### 7.3 节点可见性矩阵

| is_disabled | updated_at / dial_ips | 节点是否在服务列表 |
|:-----------:|:---------------------|:----------------:|
| false | 3 分钟内有更新 且 dial_ips 非空 | ✅ 在 |
| false | 超时 或 dial_ips 为空 | ❌ 不在（心跳失效） |
| true | 任意 | ❌ 不在（被禁用） |

## 8. Blink 恢复

### 8.1 适用场景

- 北斗节点超过 3 分钟未上报心跳包且未自动恢复
- 北斗节点一天内被踢点下线超过 3 次（触发熔断，无法自动恢复）

### 8.2 恢复方式

**重新交付：** 走 `POST /pcdns/create` 接口，将该节点作为全新机器进行交付

**原地恢复：** 通过 blink 执行脚本，等待 MCDN 恢复心跳：
```bash
supervisorctl restart portal_pin && python /data/cdn_tools/mcdn_init.py
```

`mcdn_init.py` 检查项：服务类型、hostname、厂商、SID、DNS、内核版本、系统语言、时区、磁盘挂载、容器运行状态等。

## 9. 熔断保护

### 9.1 策略含义

为避免当天短时间内大量节点被踢下线导致服务雪崩，设置当日熔断保护。当日下线次数达到阈值后，后续的踢点指令**仅记录和通知，不再实际执行下线**。

### 9.2 阈值配置

| 业务类型 | 常量名 | 阈值 | 熔断后行为 |
|---------|--------|:----:|-----------|
| 视频云（BVC） | `BvcMAX` | **50** | `Fusing=true`，仅入库+通知 |
| 移动端（Mob） | `MobMAX` | **100** | `Fusing=true`，仅入库+通知 |
| 其他（北斗/星辰） | — | 无限制 | 不熔断 |

> 阈值定义位置：[app/manba-bi/internal/service/service.go](app/manba-bi/internal/service/service.go#L12-L13)

### 9.3 熔断判断

```go
if count >= MAX {
    msgdata.Fusing = true      // 标记熔断
    msgdata.ActionStatus = false
    // 仅入库和发消息，不下线
    go s.dao.AddMsgTcre(msgdata)
    go s.notice.SendMsg(msgdata, true, count)
    return true, nil
}
```

## 10. 线路探测可用率策略

### 10.1 策略含义

在调度器获取 MCDN 节点列表时，根据监控探测器提供的线路探测数据，判断**当前这批监控数据的可信度**。

**注意：** 这是一个数据可信度判断策略，**不是踢点策略**。它影响调度器是否采信线路探测结果，而非节点是否上线/下线。

### 10.2 计算方式

**数据来源：**
- `GetAllValidLines(3 * 60)` / `GetValidLines(3 * 60)` — 最近 3 分钟内探测成功的 IP 列表（数据来源：`ads_tcp_conn_status_rt` 表 via ClickHouse）
- `GetAllValidPorts(3 * 60)` / `GetValidPorts(3 * 60)` — 最近 3 分钟内探测成功的端口
- `GetAllLiveMCDNs()` / `GetLiveMCDNs()` — 当前在线且未被禁用的节点列表

**可用率计算：**

```
validRatio = len(探测成功IP数) / 所有在线节点的总线路数

其中：
- 分子：3 分钟内探测成功返回的 IP 数量
- 分母：所有未被禁用的节点的线路总数（Lines × LineCap 求和）
- 时间窗口：3 分钟
```

### 10.3 判定逻辑

```go
if validRatio < 0.8 {
    // 监控数据异常，不再采信 → 所有 IP 不做过滤（视为全部可用）
    mcdn.IPs = ips  // 原始 IP 不做筛选
} else {
    // 监控数据可信 → 按探测结果过滤
    for _, ip := range ips {
        if AllValidCount[ip] > 0 {
            mcdn.IPs = append(mcdn.IPs, ip)       // 探测成功 → 可用
        } else {
            mcdn.InvalidIPs = append(mcdn.InvalidIPs, ip)  // 探测失败 → 标记不可用
        }
    }
}
```

### 10.4 阈值

- 当前阈值：**0.8（80%）**
- 低于阈值的行为：**不再采信**本次监控数据，所有 IP 视为可用
- 高于阈值的行为：按探测结果区分可用/不可用 IP

### 10.5 受影响场景

策略在以下 5 种业务类型中独立执行，互不影响：

| 业务类型 | 获取函数 | 执行位置 |
|---------|---------|---------|
| 点播 MCDN（全部） | `getAllMCDNs()` | [pcdn.go#L319](app/portal/internal/service/pcdn.go#L319) |
| 点播 MCDN（IPv4） | `getMCDNs()` | [pcdn.go#L425](app/portal/internal/service/pcdn.go#L425) |
| 点播 P2P | `getP2pMCDNs()` | [pcdn.go#L520](app/portal/internal/service/pcdn.go#L520) |
| IPv6 | `getIpv6MCDNs()` | [pcdn.go#L615](app/portal/internal/service/pcdn.go#L615) |
| 直播 | `getLiveMCDNs()` | [pcdn.go#L712](app/portal/internal/service/pcdn.go#L712) |
| 直播 P2P | `getLiveP2pMCDNs()` | [pcdn.go#L816](app/portal/internal/service/pcdn.go#L816) |

### 10.6 常见误解

| 误解 | 纠正 |
|------|------|
| 线路可用率低于 80% 会踢点下线 | ❌ 不影响节点在线状态，只影响调度器是否信任探测数据 |
| 低于 80% 会触发告警 | ❌ 仅日志记录，无告警通知 |
| 高于 80% 时探测失败的 IP 会被踢下线 | ❌ 仅标记为 `InvalidIPs`，不影响节点本身的 `is_disabled` 字段 |

## 11. BBAN 依赖的北斗接口

### 11.1 `/mcdn/resource`

- 用途：周期性同步北斗 MCDN-v 资源状态
- 范围：**仅同步在线节点**
- 鉴权：有

### 11.2 `/mcdn/list`

- 用途：周期性同步北斗所有 MCDN-v 资源
- 范围：**包含在线 + 离线节点**
- 用途：用于机房划分

**内部调用链路：**
```
/mcdn/resource 或 /mcdn/list
    │
    ├─ 鉴权
    ├─ 读取缓存（go-cache / Redis）
    │
    ├─ 缓存 miss → 走 DB：
    │   ├─ mcdn_disks（最近 10 分钟磁盘数据）
    │   ├─ ads_tcp_conn_status_rt（最近 5 分钟线路监控 via ClickHouse）
    │   ├─ p_instances（在线节点）
    │   └─ mcdn_info_disks（最近 10 分钟磁盘明细）
    │
    ├─ 计算 validRatio
    ├─ 过滤禁用节点，遍历实例组装 MCDN 数据
    └─ 回写缓存
```

## 附录：关键术语表

| 术语 | 含义 |
|------|------|
| **踢点** | 将 MCDN 节点下线，设置 `is_disabled=true` |
| **拉起/上线** | 将 MCDN 节点恢复上线，设置 `is_disabled=false` |
| **BufferRate** | 业务卡顿率，来源于 BVC 视频云数据接口 |
| **SID** | 节点在北斗平台的唯一标识 |
| **LineCap** | 单条线路带宽容量 |
| **Lines** | 节点总线路数 |
| **validRatio** | 线路探测可用率（分子：探测成功 IP 数；分母：总线路数） |
| **is_disabled** | 北斗实例的"是否被禁用"标记，true=已下线 |
| **dial_ips** | 节点拨测 IP 列表，心跳上报后填充 |
| **熔断** | 当日下线次数达阈值后停止实际下线动作 |
| **BVC** | 视频云服务 |
| **moni** | 监控系统 |
| **BBAN** | 依赖北斗接口的外部系统 |
