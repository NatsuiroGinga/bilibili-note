# VisQUIC：面向加密流量分析的大规模 QUIC 数据集

> Barak Gahtan、Robert J. Shahla、Reuven Cohen、Alex M. Bronstein，2024 首发，2025 年 v6，arXiv:2410.03728v6，7 页。

## 一句话

VisQUIC 能用完整 QUIC 迹线、方向、时间、包长和受控解密真值研究 HTTP/3 协议表征，但它不是恶意流量检测数据集；当前最合理的用途是补充 QUIC 观测边界与序列表征方法，不是训练当前 Qwen 恶意流量生成任务。

## 采集环境与范围

论文在两个跨洲住宅网络中连续四个月、覆盖一天不同时段采集（PDF 第 2 页）。具体大洲、日期范围、网络编号和每条迹线所属采集站没有在论文或 README 中公开。

采集流程是：

1. 从 Tranco 顶级站点列表选取支持 HTTP/3 的网页；
2. 使用 Headless Chrome 无痕模式顺序访问，关闭缓存和会话恢复；
3. 使用 Tshark 捕获并只保留 QUIC 包；
4. 每个 PCAP 配套一个 `.key` 文件，用于受控解密并生成 HTTP/3 响应数真值。

客户端固定为 Chrome。论文所说的 Chromium QUIC、Meta `mvfst` 和 Cloudflare `quiche` 多实现覆盖，主要来自不同服务器端。因此不能把该数据写成多浏览器数据。

## 数据形式与规模

论文表 I 合计：

- 44,514 个“Websites”项；
- 100,664 条 QUIC 迹线；
- 5,408,166 张 0.1 秒窗口图像；
- 1,932,275 张 0.3 秒窗口图像。

Cloudflare 组有 44,700 条迹线，占 44.41%；Cloudflare、PCMag、Semrush、Bleacher Report 和 Discord 前五组共占 83.32%。这是服务器/网页分布不平衡，不是恶意类别分布。

官方 README 描述的全量分卷为：

- `VisQUIC*.zip`：`server_name/website_name/pcap + key` 层级；
- `rgb_images*.zip`：`server_name/website_name/trace/window_size/overlap/label/png` 层级。

仓库仅明确说样例来自 `VisQUIC1.zip` 和 `rgb_images1.zip`。Dropbox 全量页本轮无法连接，官方也没有提供文件清单、总字节数或哈希，因此当前不宜启动全量下载。

官方 README 声称 `links-for-request/all_websites.txt` 包含 9,075 条网页链接，而论文表 I 的“Websites”合计为 44,514。两个口径无版本化清单解释，可能反映原始 URL 列表、成功抓取项或不同数据版本的差异；在没有清单前不应擅自选择其中一个作为“唯一网站数”。

## 图像表征与标签

每张 RGB 图像用时间和包长作为二维分箱轴，用红通道表示服务器到客户端，绿通道表示客户端到服务器，强度表示包密度（PDF 第 2 至 3 页）。论文使用 32×32 图像和 0.1/0.3 秒窗口。

类别标签是通过密钥解密后得到的**窗内 HTTP/3 响应数**。它是有序计数目标，不是网站恶意性或异常类别。官方 README 还承认，部分迹线使用了数据中未提供的其他密钥，不是所有迹线都可用配套 `.key` 完整解密。

## 论文基线

论文声称按每个服务器组随机划分 80% 迹线训练、20% 迹线测试，重复 5 次（PDF 第 4 页）。训练设置为批量 64、Adam、`ReduceLROnPlateau`、早停，并使用聚焦项、距离项和有序回归项组成的复合损失。

| 切分 | 0.1 秒 `CAP±1` | 0.1 秒 `CAP±2` | 0.3 秒 `CAP±1` | 0.3 秒 `CAP±2` |
| ---: | -------------: | -------------: | -------------: | -------------: |
|    1 |           0.93 |           0.97 |           0.91 |           0.96 |
|    2 |           0.92 |           0.96 |           0.90 |           0.97 |
|    3 |           0.93 |           0.98 |           0.91 |           0.95 |
|    4 |           0.94 |           0.97 |           0.92 |           0.93 |
|    5 |           0.91 |           0.96 |           0.92 |           0.94 |

`CAP±k` 衡量预测响应数与真值相差不超过 `k` 的比例。因此摘要中的“97% accuracy”是**允许 ±2 个响应误差的 CAP**，不是精确分类准确率。

在迹线级将各窗口预测求和后，0.1 秒窗在 ±3 容差下为 92.6%，0.3 秒窗为 71.0%。测试集分别含 12,520 和 12,142 条迹线，平均每迹线 21.2 和 7.5 张图像。

## 实现与论文不一致

本次只读审计官方仓库当前默认分支，发现：

1. `deep-model/dataset.py` 先将所有图像平铺，再使用没有固定生成器的 `random_split` 做 80:20 划分，不保证完整迹线不交叉。
2. `main_deep.py` 使用交叉熵、SGD 和固定 1000 轮，而论文写的是复合损失、Adam、学习率调度和早停。
3. 仓库的默认输出层为 18 类，论文图 3 以 0 至 14 及 15–20 的合并尾组描述标签，类别契约没有在 README 中版本化。

这些只能证明**2026-04-07 默认分支不能直接复现 v6 基线**，不能在没有历史提交和训练制品的情况下断言论文实际运行必然使用了图像级切分。

## 泄漏与泛化风险

1. 同一 URL 可有多次请求。即使按迹线随机切分，同一网页内容也可能进入训练和测试。
2. 一条 PCAP 会产生多张窗口图像。图像级切分会直接交叉同迹线的时序片段。
3. 生成器支持 90% 窗口重叠。若这些近重复图像按图像随机分组，测试结果会严重乐观。
4. 网页、服务器实现和网络地理条件之间存在强相关，应分别做 URL 留出、服务器实现留出和采集站留出。
5. 响应数标签长尾。0.1 秒窗的训练集中，0 和 1 两类约占 55.6%，15–20 合并尾组只占约 1.5%。

## 论文原结论

1. QUIC/HTTP/3 迹线可以通过方向、时间和包长的图像表征进行无明文分析。
2. 配套密钥可以生成受控解密真值，为可观测特征基线提供对照。
3. 0.1 秒窗在迹线响应数累积任务上优于 0.3 秒窗，但较细窗口需要更多图像和存储。

## 本课题推论

以下不是作者原话：

1. 因为全部迹线是普通网页访问，VisQUIC 不能直接评估恶意流量召回、良性误报或未知攻击拒识。
2. 它可以用来检查当前 8 字段流表是否丢失 QUIC 的突发、方向和多路复用信息，但这只是表征诊断，不是恶意检测主结果。
3. 安全划分必须使完整 PCAP 只属于一个分区，并进一步使同一 URL/网页只属于一个分区。

## 与现有 Qwen + PINN 的关系

PCAP 可派生当前八个公开字段，但现有工程没有 VisQUIC PCAP/图像适配器。更重要的是，VisQUIC 无法为 `binary_label`、`attack_family` 或 `attack_subtype` 提供真值，所以不能直接加入当前分层生成训练包。

数据没有瓶颈队列、链路容量、入队、出队、队列丢弃和队列状态真值。配套密钥只是协议解密真值，不是 PINN 物理监督。

## 可迁移机制

- 用解密真值监督只使用加密可观测量的模型，适合设计“训练期特权信息，推理期仅公开字段”对照。
- 方向分通道的时间–包长直方图可作为当前五/八字段标量序列的表征对照。
- 完整迹线和 URL 双层分组规则可迁移到其他网页指纹数据。

## 不可直接声称

- 不能把 VisQUIC 称为恶意 QUIC 数据集或入侵检测数据集。
- 不能把摘要的 97% 写成精确恶意分类准确率。
- 不能在没有数据清单和许可的情况下声称全量数据已满足可重现发布契约。
- 不能把 SSL key 称为队列物理真值。

## 待验证

1. Dropbox 分卷的精确文件名、字节数、哈希、版本日期和数据许可。
2. 100,664 条迹线中可完整解密的数量和失败类型。
3. 每条迹线所属采集站、精确时间和服务器 QUIC 实现标识是否存在于全量元数据。
4. 论文 v6 数字对应的历史代码提交、配置、种子和模型权重。

## 原始摘要要点

作者将 VisQUIC 定位为大规模加密 QUIC 分析数据，包含超过 10 万条迹线、4.4 万以上网页项、配套密钥与图像表征，并以 HTTP/3 响应数估计展示可观测包特征的信息量。该段为 PDF 第 1 页摘要的中文转述。
