## 5.6 评测服务的多语言实现对比

训练系统除批量训练入口外还提供另一服务面：把已训练的检测模型作为评测服务，接收特征矩阵并返回判别概率。训练任务在单机上串行执行，评测请求则以并发方式到达，两类负载的资源形态不同。本节对照两种服务端实现的请求路径开销，为系统的评测服务形态提供依据。

对照采用同一份契约。接口含端点与载荷两部分：健康端点返回服务与设备状态、输入维度与成员数；评测端点接收行优先的 32 位浮点矩阵，批次上限为 32，返回四成员平均后的判别概率。载荷取二进制浮点编码而非十进制文本，4,561 维特征若以文本传输每请求约 3 兆字节，测得的将是浮点格式化开销而非服务开销。两侧实现共用该契约，模型与判定行为完全一致。

两端实现的差异在服务栈。一侧以 Python 的 FastAPI 框架实现，模型前向经由 PyTorch 的 MPS 后端执行；另一侧以 Rust 的 axum 框架实现，模型前向经由 Rust 侧的 libtorch 绑定执行，与 Python 侧共用同一底层计算内核，加载前以权重文件哈希核对权重一致性。这一构造把实现差异限制在请求路径：接口解析、调度与序列化由两种语言各自动实现，张量计算由同一内核承担，对照测得的是请求路径开销与并发调度能力，不把模型实现的差异混入结果。

服务栈语言对照的外部基准可作为量级参照，标注为外部候选依据：公开 Web 框架基准的最新轮次在高并发连接下的 JSON 吞吐显示 Rust 框架约为 Python 框架的 7.6 倍，低并发连接下约为 1.3 倍；该基准面向纯请求处理负载，与本场景的评测请求路径不同，不能直接外推到本系统。本课题的对照实验冻结了同权重、同内核、同契约三项前提，对照指标为延迟与吞吐随并发档位的曲线，判定张量前向占主导时两种实现的差距被摊薄的程度。

对照实验在 Apple M1 单机上完成，两种实现串行运行并各以两轮顺序互换复现，方向一致。两种实现加载同一权重文件（safetensors，加载后对同批样本的输出与 Python 端最大绝对差为 1.41×10⁻¹¹），张量前向由同一计算内核承担。实测读数为：单并发下两种实现的差距较小，中位延迟 5.76 毫秒对 6.34 毫秒，吞吐 4,634 对 4,173 样本每秒；八并发下差距放大，中位延迟 19.84 毫秒对 31.93 毫秒，尾延迟 34.44 毫秒对 73.98 毫秒，吞吐 12,323 对 7,154 样本每秒（约 1.7 倍）；服务内存占用约为对照实现的 0.53 倍，含模型加载的启动时间在缓存预热后为 0.99 秒对 2.37 秒。逆序复现轮的方向与量级一致。

上述读数刻画了两种实现在本系统评测面上的取舍：请求处理与并发调度构成的差距随并发档位放大，张量前向占主导的批量评测中差距被摊薄；内存占用与启动时间在两种并发档位下均稳定占优。系统默认以吞吐与尾延迟更优的实现承载评测端点，对照实现作为同契约的参照保留。
