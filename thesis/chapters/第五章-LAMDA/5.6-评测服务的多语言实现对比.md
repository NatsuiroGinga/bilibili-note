## 5.6 评测服务的多语言实现对比

训练系统除批量训练入口外还提供另一服务面：把已训练的检测模型作为评测服务，接收特征矩阵并返回判别概率。评测负载与训练负载的资源形态不同——训练任务在单机上串行执行，计算阶段独占加速器；评测请求则以并发方式到达，服务的吞吐与尾延迟由请求路径的实现质量决定。服务端实现语言是影响该路径的直接因素，本节以对照实验度量两种实现语言的差异，为评测服务的实现选型提供依据。

### 5.6.1 对照构造

对照采用同一份契约。接口含端点与载荷两部分：健康端点返回服务与设备状态、输入维度与成员数；评测端点接收行优先的 32 位浮点矩阵，批次上限为 32，返回四成员平均后的判别概率。载荷取二进制浮点编码而非十进制文本——4,561 维特征若以文本传输每请求约 3 兆字节，测得的将是浮点格式化开销而非服务开销。

两侧实现的差异被限制在请求路径。一侧以 Python 的 FastAPI 框架实现，模型前向经由 PyTorch 的 MPS 后端执行；另一侧以 Rust 的 axum 框架实现，模型前向经由 Rust 侧的 libtorch 绑定执行。两侧共用同一底层计算内核与同一权重文件（safetensors 格式，加载前以哈希核对权重一致性），接口解析、并发调度与序列化由两种语言各自实现。该构造隔离出语言差异的作用面：对照测得的是请求路径开销与并发调度能力，不把模型实现的差异混入结果。

对照的对象是评测端点这一可部署组件的实现选型，与平台的 Web 服务层分属两个层面。当检测模型部署为在线评测服务时，服务端实现存在真实的选型问题：Python 加深度学习框架是该场景的事实默认做法，Rust 则是追求并发承载与资源占用时的候选——两者的差距需要测量而非假设。平台的 Web 层由 Go 承担（5.2 节），而 Go 没有成熟的模型推理绑定，若以 Go 承载评测仍须经由 Python 或中间格式转换，不构成本组件的直接备选；因此对照在事实默认与性能候选之间展开，回答的是"为评测端点引入 Rust 能换来多少承载能力"这一部署问题。

加载一致性以数值验证闭合：两种实现对同批样本的输出最大绝对差为 1.41×10⁻¹¹，即服务层实现的不同不改变模型的判别行为。

### 5.6.2 实测读数

实验在 Apple M1 单机（16 GB 内存）上完成，两种实现串行运行，并以两轮顺序互换（先 Python 后 Rust、先 Rust 后 Python）复现方向。每轮在并发 1 与并发 8 两档下各执行三遍完整的 2024 年度测试面板（9,686 个样本），取中位数记入表 5-10。

### 5.6.3 结果解读与实现取舍

实测形态呈现清晰的两层结构。张量前向由同一计算内核承担，故两种实现处理单个大批次的计算时间相同；语言差异作用在请求路径——连接处理、载荷解析、响应序列化与并发调度。并发档位越低，请求到达间隔使该路径开销被计算时间吸收，差距缩小至个位数百分比；并发档位升高后，Python 实现的请求路径开销在等待队列中叠加，吞吐差距放大至 1.7 倍、尾延迟差距放大至一半以上。服务进程的内存占用与启动时间在两档下均稳定占优，反映两种语言运行时的固有差异。

服务栈语言的外部基准呈现同一形态，标注为外部候选依据：公开 Web 框架基准的最新轮次在高并发连接下的 JSON 吞吐显示 Rust 框架约为 Python 框架的 7.6 倍，低并发连接下约为 1.3 倍。该基准面向纯请求处理负载，不含模型前向，绝对数值不可外推；但其"低并发差距小、高并发差距放大"的形态与本章对照一致。

据此，本系统的评测端点交由 Rust 实现承载：其请求路径优势恰好作用于评测负载的并发形态，且不引入与训练侧的任何数值差异。Python 实现保留在代码库中，承担三个角色：对照实验的参照臂（本节结论的度量基准）、模型更新时与训练侧同框架的一致性验证入口，以及推理绑定跟随深度学习框架版本升级前的兼容实现；生产部署的评测端点由 Rust 实现承载，保留的参照实现不以服务实例形式运行。需要说明的边界是：该对照刻画的是评测服务面的实现选型，训练内核仍由 PyTorch 承担——张量计算由 libtorch 内核执行，服务层语言的选择不改变模型训练与判别行为。
