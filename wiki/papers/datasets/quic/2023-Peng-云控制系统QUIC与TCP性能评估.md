# 云控制系统下 QUIC 与 TCP 的性能评估

> Peng、Tärneberg、Fitzgerald、Kihl（隆德大学电气与信息技术系），SoftCOM 2023。
> 本地原件为隆德大学 LUP 仓库版，PDF 共 8 页：**前 2 页是仓库封面**（含 DOI、引用格式与版权声明），正文自 PDF 第 3 页开始（对应正文第 1 页）。封面标注 `Document Version: Early version, also known as pre-print`。
> 本笔记统一按 **PDF 页码**定位，以免与未编号的正文页混淆。

## 一句话

一篇工整但结论平淡的协议对比：作者反复强调 QUIC 与 TCP 的优劣完全取决于目标应用的 QoS 要求，并用「采样周期是否短于网络时延」这一个开关，让同一套实现给出两个相反的结论。

## 研究设定

- 目标系统是云控制系统（CCS）：被控对象（机械臂、自动驾驶车、产线）在本地，控制器部署在边缘或公有云，控制回路被网络切开（PDF p.3 §II-B）。
- 控制回路的通信模式被抽象为：客户端每 d 毫秒发一个 p 字节请求（对应控制系统的采样率），服务端收到后同步回一个 p 字节响应（PDF p.5 §III-A）。
- 作者引用自己此前的 CCS 研究说明载荷很小：**承载被控对象状态或控制信号的载荷通常在 200–300 字节**，远小于网页或视频下载；多数情况下无需分段，因为 QUIC 与 TCP 分别支持到 1350 与 1500 字节（PDF p.4 §II-B）。
- 四个服务端（PDF p.4 §III）：(i) 单流 QUIC；(ii) 纯 TCP（无 TLS）；(iii) HTTP3-over-QUIC；(iv) HTTP1.1-over-TLS/TCP。作者明确指出前两者没有应用层协议，因此包大小与网络开销天然小于后两者。
- 实现：Golang，QUIC 与 HTTP3 用 quic-go 库（PDF p.4 §III-A）。客户端跑 Ubuntu-jammy（内核 5.19.0-38-generic）；服务端容器化，部署在边缘集群或公有云。
- 边缘集群：七节点裸金属 Kubernetes 集群，服务跑在 BestEffort QoS class 的 Pod 里，节点内核 5.15.0-69-generic（PDF p.4）。公有云：AWS ECS（Fargate），数据中心在斯德哥尔摩，每个服务 1 vCPU + 3 GB 内存（PDF p.4–5）。
- **作者刻意不调优网络**：为了评价不同云环境与网络场景下的真实表现，他们「有意不对网络或网络配置做针对性控制或调优」（PDF p.4 §III-A）。
- 每组参数运行一小时（PDF p.5 §III-A）。

## 三个场景与基准 RTT（PDF p.5 表 I）

| 场景名 | Ethernet | 5G | AWS |
| --- | --- | --- | --- |
| 部署环境 | 边缘集群 | 边缘集群 | AWS 公有云 |
| 网络 | Ethernet LAN | 私有 5G | 互联网 |
| PING RTT | 0.520 ms | 10.688 ms | 13.553 ms |

指标定义（PDF p.5 §III-B）：
- 响应时延 = 在被控对象侧测得的应用响应时间，通常长于网络时延，含传输与应用协议处理时间及云端控制器执行时间。
- 抖动以百分比表示 = 平均抖动 / 平均响应时延。
- 数据量用「每请求平均包大小」与「每响应平均包大小」表示，而不是吞吐（式 (1)，PDF p.5）：`每请求数据量 = 被控对象发送总量 / 请求数`，`每响应数据量 = 被控对象接收总量 / 响应数`。理由是控制系统的吞吐由采样频率与载荷大小决定，用吞吐无法反映协议开销；而云端控制器按流量计费时开销直接等于成本。

## 关键结果

### 一、低频场景（d = 25 ms > 网络时延，PDF p.5–6 §IV-A-1）

- 三个场景下，**单流 QUIC 的时延都比纯 TCP 高约 0.3 ms**；作者归因于其 TCP 实现没有加密，握手与处理开销更小。
- 响应时延随载荷增大而上升（更大包的处理时间更长）；载荷大小对 QUIC 与 HTTP3 的影响更大，尤其体现在时延中位数上。
- Ethernet 场景（最可靠、无丢包）下 **HTTP3 的响应时延差于 HTTP1.1**，作者称这与既有研究一致。5G 场景（时延更高但可靠、几乎无丢包）表现相同。
- 抖动（PDF p.6 图 2，载荷 256 字节、d = 25 ms）：Ethernet 与 5G 场景下 **TCP 抖动小于 QUIC，HTTP1.1 抖动小于 HTTP3**。
- 机制解释（PDF p.6）：HTTP1.1 的 TCP 连接持久复用，一次握手之后每个请求的确认可以搭在响应和下一个请求上；HTTP3 虽然只建一条 UDP 连接，但**每个请求-响应对走一条独立的双向流**，服务端必须持续发 MAX_STREAMS 帧来累积允许打开的流数，且上一个响应的确认无法用新流承载、必须单独发送。这些构成了低频场景下 HTTP3 相对 HTTP1.1 的额外开销。

### 二、AWS 场景的异常（PDF p.6 §IV-A-1）

- HTTP1.1 的响应时延中位数比 TCP **低约 1 ms**，且第一/第三四分位之间的范围明显更宽。
- 作者的解释是**猜测性的**：云服务商可能限制或降级没有应用层协议的流量（纯 TCP 与纯 QUIC）。
- 另一个观察：AWS 场景下 **HTTP1.1 的 TLS/TCP 报文无法被解密，而 HTTP3 与 QUIC 可以**，作者推测与数据中心的安全规则有关，并认为这也影响了 HTTP1.1 的时延。
- AWS 场景响应时延的方差反而比其他场景小（PDF p.6）。

### 三、高频场景（d = 5 ms < 5G 网络时延 10.688 ms，PDF p.6–7 §IV-A-2）

- 此时纯 TCP 与单流 QUIC 无法工作（需要多路复用），比较只在 HTTP3 与 HTTP1.1 之间进行。
- 结论**反转**：HTTP3 在响应时延与抖动上都优于 HTTP1.1（图 3，PDF p.7）。
- 机制（PDF p.7）：网络时延超过采样周期时，HTTP1.1 的持久 TCP 连接因队头阻塞成为瓶颈；但控制系统必须按周期发状态，不能等上一个响应。应用只能为下一个请求新建 TCP 连接，而新会话要重做传输与加密握手；若新建的会话短时间内没被复用就会被关闭。
- 量化（PDF p.7 图 4，5G 场景，每 1000 次请求建立的平均 TCP 会话数）：
  - d = 5 ms：**约 100–200 条会话 / 1000 次请求**；
  - d = 10 ms：降到**少于 15 条**；
  - d > 50 ms：通常整场实验只用 **1–2 条**。
  - 作者同时说明，即使 d 大于网络时延，抖动也可能导致建立多于一条会话；同参数下不同实验的会话数也不同。

### 四、数据量（PDF p.7–8 §IV-B，5G 场景，载荷 128 字节）

- 所有情况下 **HTTP1.1 的每请求数据量都大于 HTTP3**，主要因为 TCP 头比 UDP/QUIC 头大。
- HTTP1.1 的每请求数据量更接近其实际 HTTP 包大小，说明其开销主要来自协议头；HTTP3 的开销则主要来自流控帧与 ACK 包（PDF p.8）。
- d = 5 ms 时 HTTP1.1 的数据量远高于其他情形，原因正是大量 TCP 会话建立带来的握手包开销（PDF p.8）。
- 结论：考虑公有云部署成本时，HTTP3 更经济（PDF p.8 §V）。

## 结论与作者自陈（PDF p.8 §V）

- 控制系统频率较低且网络时延不显著时，QUIC 与 HTTP3 表现**差于** TCP 与 HTTP1.1，与既有研究一致。
- 频率更高且网络时延显著时，HTTP3 的响应时延更短、变化更小，对时间敏感应用与高级控制设计有利。
- 数据量上 HTTP3 每请求产生更少数据与更少网络开销。
- 后续工作：部署真实的时间敏感控制过程，检验不同协议下的时延补偿效果。

## 与本课题的关系

本文与加密恶意流量检测**没有内容关联**。以下均为方法论层面的推论，未在本课题数据上验证。

1. **可引用边界**：只能用于「QUIC/HTTP3 与 TCP/HTTP1.1 的优劣取决于应用负载特征」这一类背景陈述，且本课题论文中大概率无需引用。不可用于任何检测、漂移或聚合论断。

2. **最值得借的一点：结论翻转点是一个可写出来的不等式**。本文把「谁更好」归结为「采样周期 d 与网络 RTT 的大小关系」，并给出可观测的中介量（每 1000 请求的 TCP 会话数：100–200 → <15 → 1–2）。本课题当前的困境结构相同：因果前缀均值在某些种子上（0.2879）胜过逐流 XGBoost（0.2244）、在另一些种子上（0.1848）败下阵来。**待验证假设**：是否存在一个可写出来的条件（例如实体的流数、时间跨度或标签稀疏度）决定前缀均值何时优于逐流模型？最小验证实验：按实体流数分箱，逐箱比较两种方法的 AP，看是否存在单调的交叉点。这是推论，尚未验证。

3. **可迁移机制：给出中介量而不只给出结论**。本文没有停在「高频下 HTTP3 更好」，而是量出会话数这个中介变量，让读者能自行判断适用范围。本课题在解释「实体级聚合把 AP 从 0.22 提到 0.52」时，也应给出中介量（例如每个实体的流数分布、聚合后正样本实体的比例），而不是只报聚合前后的两个数。

4. **反面提示：不要用猜测填补异常**。AWS 场景下 HTTP1.1 比纯 TCP 更快、且只有 HTTP1.1 无法被解密，作者只给了「可能是云服务商限流」「可能是数据中心安全规则」两句推测，没有做任何验证实验。本课题遇到类似异常（例如完整 RWKV-7 状态递归反而更差）时，应当把推测明确标为待验证，并设计最小实验，而不是用一句合理化解释收尾。
