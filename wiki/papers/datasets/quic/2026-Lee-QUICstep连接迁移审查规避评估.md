# QUICstep：基于连接迁移的 QUIC 审查规避评估

> Lee、Wang、Jia、Birge-Lee、Wang、Mittal（普林斯顿大学）与 Qiang Wu（GFW Report）。PoPETs 2026(1):257–272。
> 本地 PDF 16 页；`pdftotext -layout` 全文 1,093 行可抽取，表 1–表 3 数值可从文本层直接读取。

## 一句话

这是一篇审查规避论文，但它顺手产出的一个测量数字——**真实校园网 24 小时内 29.1% 的 QUIC 连接不含任何 Initial 或 Handshake 包**——直接冲击了整个"用前 N 个包做加密流量分类"的技术路线，也直接冲击本课题以 2-IP 无向对为实体键的稳定性假设。

## 方法：QUICstep 是什么

- 核心思路来自 Wang 等的 CoMPS：QUIC 的连接迁移允许连接在 IP 或端口改变后继续存活，因此可以**只把握手包送进抗封锁信道（VPN/代理），其余包走本地直连**，从而既躲开基于握手的审查，又把代理负载降到最低（§1、§2.2.1，p.257–259）。CoMPS 只给了这一思路的高层草图，未实现也未评估；本文是第一次把它做成可用原型并量化。
- **实现关键点**（§3.2.2–3.2.3，p.261）：如何判断握手已完成？服务器发送的 `HANDSHAKE_DONE` 帧是加密的，从应用外部难以识别。作者放弃了 eBPF 启发式与修改 QUIC 客户端两条路，改用一个纯粹基于线上可见信息的判据——**QUIC 握手包用长包头格式，数据包用短包头格式，二者由 QUIC 头未加密的第一个比特区分**。因此 iptables 规则只需把"目的端口 443 且载荷首字节以 1 开头的 UDP 包"路由到 WireGuard 接口。
- 原型不修改客户端应用、上层协议、操作系统或浏览器；若服务器不支持 QUIC 或连接迁移，客户端回退到 TCP（全部经握手信道传输），用户无感知失败。

## 关键指标（带小节与页码）

### 一、真实流量中的无握手连接（§5，p.268）——本文对本课题最重要的一条

作者为评估"审查者是否可以直接丢弃所有不含 Handshake 或 Initial 包的 QUIC 连接"这一潜在攻击，分析了 2022 年 11 月 6 日某校园网 24 小时的 QUIC 流量（已匿名化，有 IRB 批准，见脚注 5）：

- 唯一 QUIC 连接总数：**3,786,050**
- 其中既不含 QUIC Initial 包也不含 QUIC Handshake 包的：**1,100,439，占 29.1%**
- 作者判断这些流"很可能来自常规的连接迁移活动"。

作者据此论证：QUICstep 触发的迁移在流量特征上与典型客户端移动性事件触发的迁移**无法区分**，逐连接地封禁所有已迁移连接会造成大量附带损害。原文表述为这些连接<q>did not contain a QUIC Initial nor a QUIC Handshake packet</q>（§5，p.268）。

### 二、QUIC 与连接迁移的部署现状（§4.2，p.262–263）

- 2024-10-25，Tranco 前 100 万域名中 **219,729 个（22%）支持 QUIC**；其中 **28,104 个（12.8%）与 QUICstep 兼容**（即完整支持连接迁移）。

按服务商拆解（表 1，p.262）：

| 服务商 | QUIC 域名数（占前 100 万比例） | QUICstep 兼容数（占该商 QUIC 域名比例） |
| --- | --- | --- |
| Cloudflare | 163,900（16.4%） | **335（0.2%）** |
| Google | 7,191（0.72%） | 748（10.4%） |
| Amazon | 7,067（0.71%） | 3,858（54.6%） |
| Hostinger | 4,738（0.48%） | 2,770（58.5%） |
| Fastly | 4,140（0.41%） | 2,114（51.1%） |
| Hetzner | 2,187（0.22%） | **1,802（82.4%）** |
| Automattic | 1,675（0.17%） | 9（0.5%） |
| Wix | 1,084（0.11%） | 0（0.0%） |
| OVH | 1,068（0.11%） | 710（66.5%） |
| Bigcommerce | 896（0.09%） | 1（0.1%） |

**74.6% 的 QUIC 域名托管在 Cloudflare，而 Cloudflare CDN 尚未完整支持连接迁移**（作者另行测试了 Cloudflare 开源实现 quiche，确认其当前缺乏对连接迁移的正确支持，p.262）。作者估算：若 Cloudflare 正确支持连接迁移，**87.2% 的 QUIC 支持域名**将可使用该特性（p.263）。Hetzner 的高兼容率来自其托管服务多用 Litespeed 服务器。

### 三、连接迁移支持度的增长（§4.2.3，p.263）

对 Tranco 前 100 万域名做每日扫描，2024-08-03 至 2024-11-13：

- 2024-08-03：**26,234** 个域名支持端口迁移
- 2024-09-26：**28,060**
- 2024-09-29：**31,262**，此后一直保持在 31,000 以上
- 三个月测量期内部分支持连接迁移的网站数增长 **20%**（摘要与 §1，p.257）

作者观察到的两类不一致：存在只支持 IP 迁移不支持端口迁移的域名（几乎全部关联 CloudFront CDN）；同一 amazon 域名的不同服务器（按 IP 区分）对 IP 迁移的响应也不一致，部分服务器返回"connection migration disabled by server"错误而另一些不返回。

### 四、审查规避效果（§4.3，p.263–264）

- 对本地 Palo Alto Networks 防火墙的 TLS SNI 审查：QUICstep 成功建立会话；但作者诚实指出该防火墙对 QUIC 流量**未做 SNI 封锁**，原生 QUIC 连接也能成功，因此这只验证了 QUICstep 对传统 TCP SNI 审查的适用性。
- 对 GFW 的真实 QUIC SNI 审查（阿里云中国大陆 VM 作为客户端）：以 `youtube.com` 作为 SNI 时，原生 QUIC 客户端在若干次重复取回后被封锁（审查者以概率方式检查流量），而 **QUICstep 客户端在 50 次连续取回中全部成功**。
- 对 7 个被 QUIC SNI 封锁的 `tiktokcdn.com` 子域名的重复测试：原生连接在数次取回后失败，QUICstep 始终成功。

### 五、被审查域名与迁移支持的交集（§4.3.3，p.264）

- 并行工作测得 GFW 的 QUIC SNI 封锁列表含 **28,458** 个域名；其中 **2,404 个（8.45%）支持 QUIC**，这 2,404 个里 **828 个（34.4%）与 QUICstep 兼容**。
- 对 TCP SNI 审查列表（测试列表 65,153,600 个域名）：识别出 **5,700,928** 个被 TCP SNI 审查的网站，其中 **3,524,808 个（61.8%）支持 QUIC**，这些里 **3,516,979 个（99.8%）兼容 QUICstep**。作者指出这一极高比例源于封锁列表中大量 `blogspot.com` 与 `wixsite.com` 子域名。

### 六、性能（§4.4，p.264–267）

默认设置：客户端在伦敦（AWS），握手信道提供者在俄亥俄，限速 5 Mbps；用 Selenium 驱动 Chrome，每轮在原生/全 VPN/QUICstep 三种连接间轮换，共 100 轮，报告中位数。

- 相比全量 VPN，**页面加载时间最多减少 84%**（100 个 QUICstep 兼容域名，图 4，p.264）。
- **代理负载中位减少 93%**（图 7，p.266）；`www.youtube.com` 一例：全 VPN 时经代理流量 3.634 MB，QUICstep 只有 96 KB，**减少 97.4%**。
- 带宽越受限收益越大（表 2，p.267，QUICstep/VPN 页面加载时间比值，客户端在伦敦）：

| 代理位置 | 1 Mbps | 5 Mbps | 10 Mbps | 无限速 |
| --- | --- | --- | --- | --- |
| Ireland | 0.069 | 0.338 | 0.510 | 0.996 |
| Frankfurt | 0.070 | 0.340 | 0.616 | 0.898 |
| Montreal | 0.072 | 0.463 | 0.738 | 1.052 |
| Ohio | 0.088 | 0.458 | 0.588 | 0.996 |
| Oregon | 0.088 | 0.554 | 0.860 | 1.071 |
| Seoul | 0.128 | 0.586 | 0.633 | 0.765 |
| Tokyo | 0.124 | 0.682 | 0.976 | **1.553** |

无限速且代理很远时（Tokyo，1.553）QUICstep 反而更慢——作者解释为 AWS 代理之间连接质量很好，代理路径可能优于直连路径。

- DNS 解析位置的影响（表 3，p.268）：默认设置下 DNS 走代理，客户端会连到靠近代理的服务器。若客户端能自行获得靠近自己的服务器 IP，Oregon 代理的 QUICstep/VPN 比值从 0.554 降到 0.238，Seoul 从 0.586 降到 0.282，Tokyo 从 0.682 降到 0.301。作者据此指出**服务器位置比代理往返时延对性能影响更大**。

## 作者自陈局限（原样记录）

1. **威胁模型限定为无状态审查者**（§3.1，p.260）：审查者按包做判定、不记录全部网络流、不做流级流量分析。作者明确声明 QUICstep **不对有状态流量分析做任何安全声明**（§5，p.268），例如基于连接迁移事件异常频率的检测。
2. 握手完成时刻是**近似**的（§3.2.2，p.261）：用长/短包头区分代替 `HANDSHAKE_DONE` 帧识别；作者指出若迁移更精确，页面加载时间的减少幅度可能更大（§4.4.2，p.265）。
3. 本地防火墙实验未验证 QUIC SNI 封锁（该防火墙不封 QUIC），只验证了对 TCP SNI 审查的适用性（§4.3.1，p.263）。
4. 真实域名测试样本很小（7 个 tiktokcdn.com 子域名）（§4.3.2，p.264）。
5. 校园网流量分析只有单点、单日 24 小时数据。

## 与本课题的关系

第 1 点为引用范围界定，第 2–4 点为本课题推论，均未经本课题实验验证。

1. **可直接引用的**：真实校园网 24 小时 QUIC 流量中 29.1% 的连接不含 Initial 与 Handshake 包（§5，p.268）；QUIC 与连接迁移的部署比例与服务商分布（§4.2，表 1）；连接迁移在流量特征上与客户端移动性事件不可区分（§5）。**不可引用为**恶意流量检测的任何性能参照——本文任务是审查规避，与本课题威胁模型无关。

2. **对本课题「前 N 包表示」这一整条技术路线的直接冲击**：
   - [[2025-Luxemburk-QUIC域名识别预训练的通用嵌入函数]] 的全部方法建立在"前 30 个包"或"前 10 个包"的序列表示上；本课题的因果前缀均值同样把早期时序作为主要信息源。
   - 本文的 29.1% 说明：在真实网络中，近三成 QUIC 连接**根本没有握手阶段可观测**，前若干包是迁移后的短包头数据包而非 Initial/Handshake。对这些流，任何依赖握手阶段特征的模型都在处理一个截断的、语义不同的输入。
   - **可立即执行的最小验证实验**：在 LSPR23/LSPR24 上统计"流的首包是否为连接建立包"的比例，以及缺失建立阶段的流在逐流与实体级指标上的分面表现。若该比例可观，则应把"是否含建立阶段"作为一个显式分面报告，而不是让它隐含在平均指标里。这是本篇为本课题带来的最具行动性的产出。

3. **对本课题实体键（2-IP 无向对）稳定性的直接警示**：
   - QUIC 用连接标识符而非 IP+端口元组标识连接（§2，p.258）；连接迁移使同一条逻辑连接在多个 IP/端口上出现。本文测得端口迁移支持域名在三个月内从 26,234 增至 31,000 以上并持续上升。
   - 因此在 QUIC 占比上升的数据集上，**2-IP 无向对既可能把同一实体的一条连接切成多个实体，也可能把不同实体的流量并进同一对**。本课题当前实体级 AP 0.5233–0.5475、DR@4%FPR 0.7207–0.8324 的结果若要外推到 QUIC 主导的流量，必须先量化数据集中的连接迁移比例。
   - 这与 [[2025-Kadi-QUIC时代入侵检测机器学习适配]] 用整幅图讨论 NAT 后实体归属歧义、以及 [[2026-Alshaali-QUIC二进制与系统集成安全分析]] 明确要求按目的连接 ID 而非 IP 端口对归并连接，构成同一问题的三个独立证据点：**QUIC 时代的"实体"不能默认由网络元组定义**。这三点合起来可支撑本课题在局限性一节中的一段论述。

4. **对证据类型 (b)（分布漂移）的补充**：本文的三个月纵向测量（26,234 → 31,262 端口迁移支持域名）是**协议特性部署面本身在漂移**的证据。这是一类与"攻击行为演化"平行、但常被忽略的漂移来源：**同一份检测器面对的流量在协议行为层面就在逐月变化**。本课题的 LSPR23→LSPR24 跨年度退化中，有多少来自攻击演化、有多少来自底层协议部署演化，目前无法区分；这应作为一条明确的局限性登记，并在有条件时用协议构成分布的年度对比来做初步归因。

## 可迁移的机制

1. **用最少的线上可见信息做判定**：QUICstep 只依赖 QUIC 头未加密的第一个比特（长包头 vs 短包头）来区分握手包与数据包，避免了状态跟踪与客户端改造。本课题在设计特征时可借鉴这一"先问哪些位在加密后仍然可见"的纪律。
2. **主动探测代替间接推断**：作者批评先前工作只发送带新连接 ID 的包来推断迁移支持，无法验证迁移后能否真正加载资源；QUICstep 通过**实际触发一次人工移动性事件**获得确定性确认（§4.2.4，p.263）。对应到本课题：验证一个机制是否生效应当触发它并观测结果，而不是从配置或符号存在性推断。
3. **纵向每日扫描 + 拐点标注**：图 3 与 §4.2.3 的时间序列指出 2024-09-26 到 09-29 之间的跳变，并归因到 QUIC 库升级（Varnish CDN）。本课题在跨年度对比中也应做同样的"何时发生跳变、能否归因到某次外部变更"的分析，而不只报告两个端点的差值。
4. **性能收益随约束加强而放大**：表 2 显示 QUICstep 的相对收益从无限速时的约 1.0（无收益甚至变差）放大到 1 Mbps 时的 0.069。本课题报告效率类收益时应同样给出"在什么资源约束下收益才显现"的完整曲线，而非只报最有利的一档。
5. **反面教训**：本文承认本地防火墙实验其实没验证到目标机制（该防火墙不封 QUIC），仍如实写入正文。本课题遇到"实验条件未触发目标机制"时应照此处理，而非事后重新定义实验目标。
