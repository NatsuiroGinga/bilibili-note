# R2 QUIC v4 突发与队列容量实现计划

> **执行代理要求：** 按 `subagent-driven-development` 的任务边界执行；本任务只进行一次聚焦的 `test-driven-development` 红灯—绿灯周期。

**目标：** 在保留 v3 兼容性的前提下，实现按字节计量、服务与传播分离、逐事件可重放的 QUIC v4 用户态整形合同，并使本地代码具备启动三轮正式门禁的条件。

**架构：** 代理按方向维护待服务字节、传播中字节和独立的服务完成事件。收集器把冻结容量合同传给代理，审计器从逐事件日志重算峰值、包/字节守恒和序列化积分。v4 配置固定 `aioquic → quiche → aioquic` 三轮身份；包装器只负责持久化 v4 启动状态，不在本任务启动运行。

**技术栈：** Python 标准库、Bash、JSON。

## 全局约束

- 每方向容量固定为 `2,097,152` 字节；`1,677,721` 字节只作为 80% 诊断阈值，不作为运行通过条件。
- 最大数据报按实现配置驱动：aioquic 1.3.0 为 `1,200` 字节，quiche 0.24.5 为 `1,350` 字节；`65,535` 只记录为 UDP 接收缓冲上限，禁止解释为合法 QUIC 数据报上限。
- 服务率固定为 `20,000,000 bit/s`，单向传播时延固定为 `50,000 us`。
- 零随机丢弃、零队列丢弃、零发送错误，关停时等待字节、服务中字节、传播中字节和调度堆均为零。
- 三轮身份严格为 aioquic 索引 12、quiche 索引 32、aioquic 索引 12。
- 只运行一个目标测试文件的红灯和绿灯，不运行正式门禁、完整测试、GPU、Pyright 或独立复审。

## 已识别风险

- v4 用户态队列只是非丢包整形包络，不是内核或真实路由器队列真值。
- 即使三轮门禁通过，也只能授权 QUIC 种子字段矩阵；正式 QUIC 专家仍需 600 条连接及来源审计。
- 原 v4 分析把 `65,535` 字节接收缓冲误作最大数据报，并把 80% 误设为硬门禁；实现已按一手代码证据更正，正式分析文档需由主代理同步修订。
