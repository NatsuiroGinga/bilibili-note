# R2 QUIC v4 突发与队列容量合同分析

## 结论

v3 run2 的 `404` 个丢弃不是审计器误报：在现有用户态代理的定义内，服务端到客户端方向确实达到 `1000p` 上限，随后 404 个报文因 `userspace_queue_limit` 被拒绝。但该事实只证明**当前代理实现中的有限队列溢出**，不能证明内核队列、真实链路或网络设备发生了同样的拥塞。

唯一推荐是建立全新 v4 合同：容量从“每方向 `1000` 个报文”改为“每方向 `2,097,152` 字节（`2 MiB`）”，把速率服务阶段与固定传播时延阶段分离，按待服务字节执行准入，并要求三轮全部满足队列丢弃为 0、峰值待服务字节不超过 `1,677,721` 字节（容量的 80% 向下取整）。这是一项防止非预期丢包的工程包络，不得称为真实路由器队列模型。

不得通过事后接受 `404` 个丢弃、增大审计容差、补跑有利轮次或继续试探其他容量来放行。v4 只允许下面冻结的一次实现和三轮串行门禁；失败即维持 `NO-GO_KEEP_QUIC_UNKNOWN`。

## 1. 分析边界与证据

### 1.1 输入

- v3 计划：`.Codex/docs/2026-08-05-R2-QUIC-v3复审阻断修复计划.md`。
- v3 实现报告：`.Codex/docs/2026-08-05-R2-QUIC-v3复审阻断修复报告.md`。
- v3 门禁报告：`.Codex/docs/2026-08-05-R2-QUIC-v3三次端到端门禁报告.md`。
- 本地代理实现：`thesis/experiments/llm_probe/scripts/r2_quic_udp_proxy.py`。
- v3 冻结配置：`thesis/experiments/llm_probe/configs/r2_quic_controlled_determinism_repair_v3.json`。
- 服务端证据根：`runs/data-raw/r2-quic-controlled-field-userspace-v3-run2-quiche/`。
- 主代理只读回传的 run2 `proxy-stats.json` 关键统计。

本分析没有修改生产代码、没有启动新连接、没有补跑 v3，也没有读取公开检测最终测试。QUIC 继续保持 `formal=false`、训练权重 0 和 `UNKNOWN` 回退。

### 1.2 已核验事实

run2 固定为 quiche、`p03`、种子 43、`bulk=67,108,864` 字节、每方向 `20,000,000 bit/s`、固定单向时延 `50 ms`、随机丢包率 0、队列上限 `1000p`。运行耗时 `31.214 s`，响应完整，解密错误、发送错误和关停残留队列均为 0。

| 方向 | 接收包 | 接收字节 | 调度/转发包 | 调度/转发字节 | 队列丢包 | 峰值队列 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 客户端到服务端 | 主代理尚未回传精确总数 | 主代理尚未回传精确总数 | 未发现不守恒 | 未发现不守恒 | 0 | 56p |
| 服务端到客户端 | 66,167 | 70,905,840 | 65,763 | 70,389,979 | 404 | 1000p |

服务端到客户端方向满足：

```text
66,167 = 65,763 + 404
70,905,840 = 70,389,979 + 515,861
```

因此 404 个丢弃对应 `515,861` 字节，平均 `1,276.884` 字节/包；丢弃占接收包的 `0.6106%`、接收字节的 `0.7275%`。已调度报文平均 `1,070.358` 字节，累计序列化时间 `28.362336 s`，与 `70,389,979 × 8 / 20,000,000` 精确一致；最终冻结发送偏移 `28.412336 s`，恰为累计序列化时间加 `50 ms`。

客户端到服务端方向的精确包数和字节数未进入主代理回传摘要，不能编造；当前可确定其峰值仅为 `56p` 且队列丢弃为 0。该缺口不影响溢出方向和 v4 容量裁决，但完整 v4 实施计划发布前应从原始 `proxy-stats.json` 补齐。

## 2. 负载、服务率与 BDP

### 2.1 全程平均不是持续过载

服务端到客户端接收平均速率为：

```text
70,905,840 × 8 / 31.214 = 18.172830 Mbit/s
```

已调度平均速率为 `18.040617 Mbit/s`，均低于冻结服务率 `20 Mbit/s`。因此不能把 404 个丢弃解释为整段 31.214 秒内输入长期超过服务能力；它来自短时突发或用户态处理聚集。

完整转发字节比 64 MiB 应用响应多 `3,281,115` 字节（`4.889%`），可包含 QUIC/UDP 开销与重传。丢弃后响应仍完整，只说明 QUIC 恢复机制工作，不会把这 404 个非预期队列丢弃变成合格结果。

### 2.2 BDP

按当前代理参数：

```text
单向 BDP = 20,000,000 × 0.050 / 8 = 125,000 B
RTT BDP  = 20,000,000 × 0.100 / 8 = 250,000 B
```

以已调度报文平均长度换算，单向 BDP 约为 `116.8` 个报文，RTT BDP 约为 `233.6` 个报文。现有 `1000p` 约等于 `1,070,358` 字节和 `0.428 s` 的平均服务量，但这只是用全程平均报文长度得到的估计，不是峰值队列字节真值。

v3 只记录 `peak_queue_packets=1000`，没有记录峰值待服务字节。因此可确定的峰值是 1000 个报文；精确峰值字节及其时间区间不能从汇总统计恢复。v4 必须补齐字节占用收据，不能继续用平均包长冒充峰值。

## 3. 404 个丢弃的来源裁决

### 3.1 代理模型内是真实有限队列溢出

本地代码在每个方向维护独立 `queued_packets`。报文通过随机丢包判断后，只要 `queued_packets >= queue_limit_packets`，就记录 `reason=userspace_queue_limit` 并拒绝调度。run2 同时出现 `peak_queue_packets=1000`、`queue_drop_packets=404` 和收发守恒，故不是审计器把其他错误误计为队列丢弃。

只有服务端到客户端方向触顶，客户端到服务端峰值为 56 且无丢弃；结合 64 MiB 响应方向，可判断压力来自服务端响应突发，而不是双向参数整体失效。

### 3.2 不能外推为真实网络拥塞

现有实现至少包含三项会放大或改变队列占用语义的用户态因素：

1. `queued_packets` 从调度时增加，直到固定时延加序列化后的最终转发时才减少，因此把“等待速率服务”和“已完成服务、等待传播时延”混在同一个受限队列内。真实瓶颈队列不应把传播中的报文继续算作待服务缓存。
2. 每次可连续读取最多 256 个 UDP 报文，之后才调用一次到期转发。若读取期间已有服务完成，报文仍可能以旧计数接受或拒绝，队列峰值含有事件循环批量处理效应。
3. 当前发送时间以首包纪元加累计序列化时间计算。空闲后服务时间轴可能落后于当前时间，新突发可取得未设上限的历史服务信用；这不是已冻结桶深的令牌桶，也不是严格工作保守队列。

因此最强允许表述是：“quiche run2 在 v3 用户态代理的 `1000p` 混合等待队列中发生 404 个确定性溢出丢弃。”禁止写成“20 Mbit/s、50 ms 的真实网络队列发生 404 个拥塞丢包”。

## 4. v4 唯一容量合同

### 4.1 容量单位与冻结公式

每个方向独立使用字节容量。报文个数只作诊断，不再参与准入。冻结量为：

```text
C                 = 20,000,000 bit/s
D                 = 0.050 s
RTT               = 2D = 0.100 s
T_burst            = 0.500 s
B_drop_v3          = 515,861 B
M_datagram         = 65,535 B
Q_raw              = C × (RTT + T_burst) / 8 + B_drop_v3 + M_datagram
                   = 2,081,396 B
Q_v4               = ceil_to_MiB(Q_raw)
                   = 2,097,152 B = 2 MiB/方向
Q_margin_max       = floor(0.80 × Q_v4)
                   = 1,677,721 B
```

`T_burst=0.500 s` 是一次性冻结的工程突发预算：v3 的 `1000p` 按已调度平均包长相当于约 `0.428 s` 服务量，向上固定为 0.5 秒；再显式加入 v3 已拒绝的 515,861 字节和一个最大 UDP 报文余量。公式最终只产生一个 MiB 对齐值 `2 MiB`，不得在看到 v4 结果后改成 3 MiB、4 MiB 或其他值。

这个公式用于构造非丢包整形包络，不是论文中的物理队列公式。后续若研究真实有限缓存丢包，必须另建明确的缓存/主动队列管理实验合同，不能复用本门禁的零丢包目标。

### 4.2 服务与传播阶段

v4 必须采用每方向独立、工作保守的字节服务模型：

```text
serialization_start  = max(arrival_time, previous_serialization_finish)
serialization_finish = serialization_start + datagram_bytes × 8 / C
release_time          = serialization_finish + D + frozen_jitter
```

准入前先按当前时间结算已完成序列化的报文。容量只约束尚未完成序列化的 `service_backlog_bytes`；已完成序列化、仅等待 `D` 或抖动的 `delay_inflight_bytes` 不占队列容量。准入规则唯一为：

```text
admit iff service_backlog_bytes_before + datagram_bytes <= Q_v4
```

等于容量时允许入队，超过一个字节也必须以 `userspace_queue_limit_bytes` 拒绝。每个报文最大长度固定为 `65,535` 字节；超过即合同失败，不得截断。随机丢包判断与字节队列丢包分账；`p03` 的随机丢包必须为 0。

批量读取每个报文前都要结算服务完成事件，不能等 256 个报文全部读取后才更新容量。空闲后 `serialization_start` 必须重置到当前到达时间，禁止继承无限历史服务信用。

## 5. 必须记录的队列收据

### 5.1 配置级收据

- `queue_capacity_unit=bytes`。
- `queue_capacity_bytes=2097152`，每方向分别记录。
- `queue_margin_ratio=0.80` 与 `queue_margin_max_bytes=1677721`。
- `max_datagram_bytes=65535`。
- `rate_bits_per_second=20000000`、`delay_us=50000`、调度模式和实现版本。
- 明确声明 `kernel_queue_truth=false`、`kernel_netem_truth=false`、`network_namespace_truth=false`。

### 5.2 逐事件收据

每个接收报文至少记录：方向、方向内报文序号、到达时间、报文字节、服务前后待服务字节、延迟阶段字节、序列化开始/完成时间、最终释放时间、准入结果和拒绝原因。每个转发事件还要记录计划释放时间、实际转发时间与滞后。

逐事件日志必须能够独立重放并复算：

- `peak_service_backlog_bytes` 及对应报文序号和时间。
- `peak_delay_inflight_bytes`，与队列峰值分开。
- `max_receive_batch_packets/bytes`。
- `max_actual_forwarding_lag_us`。
- 每方向接收、随机丢弃、队列丢弃、调度、转发、发送错误和关停残留的包/字节双守恒。
- `sum(serialization_duration) = scheduled_bytes × 8 / C`，允许的微秒取整误差必须预先固定。

状态摘要和事件日志都要进入制品清单，逐项绑定相对路径、字节数和 SHA-256。审计器必须从事件日志重算全部峰值与守恒，不能只相信代理自报摘要。

## 6. 三轮唯一顺序与门禁

沿用 v3 的科学条件与实现次序，只改变全新的 v4 队列合同和对应运行身份：

| 轮次 | 实现 | 目标索引 | 固定条件 |
| --- | --- | ---: | --- |
| run1 | aioquic | 12 | `p03`、seed 43、bulk、20 Mbit/s、50 ms、2 MiB/方向 |
| run2 | quiche | 32 | 与 run1 完全相同 |
| run3 | aioquic | 12 | 与 run1 完全相同，用于重复性门禁 |

严格串行，每轮使用新进程、空状态、新数据根和新启动器目录。不得复用 v3 制品，不得重试失败轮次，不得补第四轮。

### 6.1 单轮 GO 条件

以下条件必须全部为真：

1. 原有 v3 的固定四元组、源端口、服务端原始退出/受控信号、64 MiB 响应、qlog、PCAP、配置哈希和制品清单门禁继续通过。
2. `random_drop_packets=0`、`queue_drop_packets=0`、`send_error_packets=0`，且对应字节均为 0。
3. 两方向 `peak_service_backlog_bytes <= 1,677,721`；等于阈值允许，超过即失败。
4. 关停时 `service_backlog_bytes=0`、`delay_inflight_bytes=0`、调度堆为空。
5. 包与字节双守恒、序列化积分、事件重放峰值与代理摘要完全一致。
6. 批量读取不能让已完成服务的字节继续占队列；事件审计必须能证明逐报文结算。

### 6.2 总体状态

- 三轮单轮条件全部通过、启动器严格串行、身份恰好为冻结三项、独立复审严重和重要问题均为 0，才可给出 `GO_TO_NEW_FIELD_MATRIX_QUIC_SEED_ONLY`。
- 任一轮失败，唯一状态为 `NO-GO_KEEP_QUIC_UNKNOWN`。不得接受少量队列丢弃，不得以响应完整替代队列门禁，不得调高容量后再跑。
- 即使三轮通过，也只授权新的 QUIC 种子字段矩阵；在 600 条正式连接、来源与真值审计、实现/配置组冻结全部完成前，仍不得启用正式 QUIC 专家或形成效果主张。

## 7. 风险与限制

1. 当前回传摘要没有客户端到服务端的精确包数和字节数，完整 v4 计划发布前必须从 run2 原始 `proxy-stats.json` 补齐。
2. v3 没有记录峰值字节队列，无法证明 `1000p` 峰值等于多少字节；这正是改用字节合同和事件重放的原因。
3. `2 MiB` 会提供最多约 `0.839 s` 的满载服务包络，属于防止门禁中非预期丢包的工程缓存，不代表合理的生产网络缓存时延。
4. v4 修复能裁决用户态代理的确定性和容量余量，不能把用户态事件提升为内核队列真值或互联网路径真值。

## 8. 最终裁决

v3 run2 是有效的负面门禁证据，必须保留 `NO-GO_KEEP_QUIC_UNKNOWN`。新 v4 的唯一可预注册路径是：按字节计量、服务与传播分离、每方向固定 `2 MiB`、峰值不超过 80%、零非预期队列丢弃，并按 `aioquic → quiche → aioquic` 三轮严格串行验证。除此之外，不建议接受 404、只改审计器、只把 1000p 改成更大的包数，或继续试探容量。
