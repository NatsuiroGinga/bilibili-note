# R2 QUIC v4 官方方案检索

## 1. 结论

当前 v4 合同的**核心方向正确，但定容公式和门禁语义必须修订**。

可以保留的部分：

1. 把链路串行化服务时间与固定传播时延分开。
2. 按方向建立独立字节队列，并为每个数据报生成事件收据。
3. 用离线重放核对积压峰值、丢包和字节守恒。
4. 在三次串行的 aioquic、quiche、aioquic 运行中要求代理零丢包。

必须修改的部分：

1. `M_datagram=65535` 错把套接字接收缓冲大小当成最大数据报。quiche 0.24.5 示例配置为 `1350` 字节，aioquic 1.3.0 默认配置为 `1200` 字节；跨实现合同应冻结为实际配置上限，并审计观测值。
2. `2 MiB` 可以保留为本轮一次性修复的预注册工程硬上限，但现有证据不能把它称为物理定容结果。
3. `80%` 没有 RFC、网络演算或缓存定容论文支持，只能降级为工程余量诊断，不应决定科学 `GO/NO-GO`。
4. 合同必须新增发送节奏有效性凭据。quiche 官方接口返回计划发送时刻 `SendInfo.at`，但 0.24.5 示例客户端没有兑现它；aioquic 的异步协议层会把内部计时器注册到事件循环。两者会产生实现相关的入队突发。
5. `service_backlog` 语义过于含混，必须拆成 `queue_waiting_bytes`、`in_service_bytes` 和 `delay_inflight_bytes`。只有前两者受用户态服务队列容量约束。

本报告仅修订实验合同，不修改生产代码，也不阻塞正在进行的 v4 实现与实验。

## 2. 当前问题与一手证据

### 2.1 QUIC 端点必须兑现发送节奏

RFC 9002 第 7.7 节指出，连续无间隔发送多个分组会形成突发并造成短期拥塞或丢包；发送端应进行节奏控制，或至少限制突发大小。第 7.2 节同时把拥塞窗口和最大数据报定义为字节尺度的独立状态。

quiche 0.24.5 官方源码给出两个关键事实：

- `quiche::Connection::send()` 返回的 `SendInfo.at` 是应用应当发出该分组的时刻；官方文档要求应用通过 `SO_TXTIME` 或用户态定时器兑现该时刻。
- `apps/src/client.rs` 在 `conn.send()` 后立即调用 `socket.send_to()`，没有读取 `send_info.at`。示例客户端还把最大收发 UDP 载荷配置为 `1350` 字节。
- 示例服务器尝试启用 `SO_TXTIME`，但其批量发送辅助函数只有在发送节奏和通用分段卸载同时启用时才携带计划发送时刻；否则仍循环立即发送。

aioquic 1.3.0 官方源码则在连接对象中维护 `_pacing_at`，并在异步协议层把 `get_timer()` 的结果通过事件循环计时器重新调度。其默认 `max_datagram_size` 为 `1200` 字节。

Linux `tc-etf(8)` 进一步说明，`SO_TXTIME` 只提供每包发送时刻；真正按该时刻排队需要配置 `ETF` 队列规则，且时钟必须与套接字时间戳一致。仅仅成功设置套接字选项不能证明系统已经按计划时刻发包。

**合同含义：**不能把 quiche 的突发直接归因于物理队列，也不能仅凭配置字段声称发送节奏已生效。每次运行至少要记录：

- 端点实现与版本；
- 最大 UDP 数据报配置和观测最大值；
- `SendInfo.at` 或 aioquic 内部计划发送时刻；
- 实际进入代理的单调时钟时间与相邻间隔；
- `SO_TXTIME` 设置结果、`ETF` 队列规则、时钟源和通用分段卸载状态；
- 计划时刻与实际到达时刻的偏差分布。

这个证据支持“发送节奏差异是候选根因”，但在逐事件时序完成前，**不支持**“quiche 忽略 `at` 是 v3 第二次运行失败的唯一原因”。64 MiB 响应主要由服务器发往客户端，客户端节奏问题还可能只影响确认流；必须按方向核验。

### 2.2 服务时间与传播时延应当分离

对方向 `d` 的第 `i` 个数据报，令到达时刻为 `a_i`、字节数为 `l_i`、链路速率为 `C_d`，则确定性串行化服务可写为：

\[
s_i=\max(a_i,f_{i-1}),\qquad
f_i=s_i+\frac{8l_i}{C_d}.
\]

若固定单向传播时延为 `D_d`、预注册抖动为 `J_i`，释放时刻为：

\[
r_i=f_i+D_d+J_i.
\]

Le Boudec 与 Thiran 的网络演算把积压定义为累计到达与累计离开的差，并把固定时延视为独立时延元素或速率－时延服务曲线中的时延项。这支持以下分账：

- `queue_waiting_bytes`：尚未开始串行化的数据报；
- `in_service_bytes`：当前正在串行化的数据报；
- `delay_inflight_bytes`：已经完成串行化、等待传播释放的数据报。

容量只作用于 `queue_waiting_bytes + in_service_bytes`。传播中的字节不再占用服务队列容量，否则会把带宽时延积重复计入等待队列。

为了保持整数、确定性的事件账，建议使用 `time.monotonic_ns()`。在 `20 Mbit/s` 下，串行化一个字节恰为 `400 ns`，不需要浮点时间。相同时刻的事件顺序必须冻结，例如先处理 `finish/release`，再处理 `arrival/admission`，并由离线重放复现。

### 2.3 容量应来自到达包络与服务曲线

网络演算的确定性积压上界为：

\[
B_{\max}\leq \sup_{u\geq0}\{\alpha(u)-\beta(u)\},
\]

其中 `α` 是到达曲线，`β` 是服务曲线。对已经冻结的逐事件开发迹线，也可以直接重放累计到达 `A(t)` 与累计服务 `S(t)`，求：

\[
B_{\text{dev}}=\sup_t\{A(t)-S(t)\}.
\]

当前 v4 草案把以下四项相加：

\[
\frac{C}{8}T_{burst}+\frac{C}{8}RTT+B_{drop}+2M_{datagram}.
\]

这个式子不能作为物理定容公式，原因是：

1. 没有定义到达包络，`T_burst` 与 `RTT` 可能重复计入相同在途数据。
2. `B_drop` 是旧实现失败后的结果，不是独立的物理先验。
3. `M_datagram=65535` 是接收缓冲区大小；quiche 与 aioquic 的实际配置上限分别为 `1350` 和 `1200` 字节。
4. 式子没有说明当前正在服务的数据报是否计入容量。

因此正式定容应采用“冻结开发到达包络或开发事件迹线 + 服务曲线 + 明确分组化余量”。若本轮修复必须立即运行，可以先把 `2 MiB` 固定为工程硬上限，避免继续追逐门禁结果调参；但报告中只能说它“足以排除当前代理容量不足”，不能说它“由 QUIC 物理规律推导”。

### 2.4 `2 MiB/80%` 的合理性裁决

在 `20 Mbit/s` 和 `100 ms` 往返时延下，带宽时延积约为：

\[
BDP=20\times10^6\times0.1/8=250000\ \text{bytes}.
\]

`2 MiB` 约等于 `8.39 BDP`，也等价于约 `0.839 s` 的链路服务量。Appenzeller 等人的 SIGCOMM 论文表明，`RTT × C` 只是在少量同步 TCP 长流、以维持链路利用率为目标时的经验规则；大量独立长流下，建议缓存还会按流数平方根缩小。该结果并不适用于单连接 QUIC 用户态代理，却足以否定“带宽时延积是普适容量定律”的说法。

RFC 7567 指出，最佳缓存取决于运行目标、最大正常突发、到达量及突发性和离开速率。RFC 8238 要求微突发测试同时报告分组大小、分组间隔、业务类别和缓存单位，并明确术语规范不规定理想缓存大小。

据此裁决：

- **`2 MiB`：有条件保留。**作为在新运行前冻结的一次性工程容量可以接受；作为物理公式结果不接受。
- **`80%`：降级。**可以报告为工程余量诊断，但没有依据成为科学通过门槛。若峰值超过 `80%` 但零丢包、重放一致和时延可解释，不应仅因此判 v4 失败。
- **正式容量：后续重定。**在发送节奏修正后，用独立开发迹线或预注册到达包络计算 `B_dev`，再冻结明确的分组化余量；最终门禁不得反向修改容量。

## 3. 64 MiB 受控传输的正确代理模型

64 MiB 只规定长期负载，不直接决定瞬时队列容量。正确的用户态代理至少需要以下状态机。

### 3.1 到达与准入

每个方向维护单调事件序号。数据报到达时先结算所有 `finish_time <= arrival_time` 的服务完成事件和 `release_time <= arrival_time` 的传播释放事件，再计算准入前占用。

准入条件固定为：

\[
Q_{waiting}^{pre}+Q_{service}^{pre}+l_i\leq Q_{capacity}.
\]

拒绝时必须写明 `drop_reason=queue_capacity`；套接字错误、随机损失和代理退出分别使用不同原因，禁止统一记成 `queue_drop`。

### 3.2 服务与传播

准入后按先进先出顺序计算 `start_time` 和 `finish_time`。数据报完成服务后进入传播集合，传播集合不占服务队列容量；达到 `release_time` 后再实际转发。

若实现以完整数据报为内存单位，则 `in_service_bytes` 在完成前计入完整数据报字节。若实现使用连续剩余字节，则收据必须记录剩余量并保证重放模型完全相同。两种定义都可用，但不能混用。

### 3.3 逐事件收据

每条收据至少包含：

- `event_id`、`packet_id`、运行编号和方向；
- 端点实现、版本和最大数据报配置；
- `arrival_ns`、`start_ns`、`finish_ns`、`release_ns`；
- `packet_bytes`；
- 准入前后 `queue_waiting_bytes`、`in_service_bytes`、`delay_inflight_bytes`；
- 计划发送时刻、实际发送时刻和调度滞后；
- 准入或丢弃结果及唯一原因；
- 转发返回值、系统错误码和关联 qlog 标识。

离线重放必须重新计算事件次序、三个字节账户、容量判定、各类峰值和各类丢包，并与在线摘要一致。

### 3.4 字节守恒

若按完整数据报离散记账，则任意事件边界应满足：

\[
B_{accepted}=B_{waiting}+B_{service}+B_{delay}+B_{released}.
\]

总输入还应满足：

\[
B_{input}=B_{accepted}+B_{queue\_drop}+B_{other\_drop}.
\]

运行结束时要求三个暂存账户均为零，且释放字节与成功转发字节一致。64 MiB 应用响应完整只能作为端到端完整性门禁，不能替代上述账本；QUIC 重传可能让应用最终完整，同时掩盖中间代理丢包。

## 4. 建议的 v4 最小合同修订

### P0：本轮运行前必须修改

1. 将 `max_datagram_bytes` 改为配置派生值。跨 quiche/aioquic 合同可冻结为 `1350` 字节上限，同时分别记录各实现配置和观测最大值；`65535` 只保留为套接字读取缓冲说明。
2. 保留服务与传播分离，但将在线状态拆成等待、服务中和传播中三个账户。
3. 使用单调纳秒整数时间，并冻结相同时刻事件顺序。
4. 新增端点节奏凭据；若使用 `SO_TXTIME`，必须同时记录 `ETF` 队列规则和时钟源。若使用用户态定时器，必须记录计划时刻与实际时刻误差。
5. 将 `80%` 从 `GO/NO-GO` 条件移出，只报告峰值比例和剩余字节。
6. 保留 `2 MiB` 作为本轮预注册硬容量，不得在看到三次门禁结果后再次提高。

### P1：正式论文实验前必须完成

1. 用不含最终门禁结果的独立开发事件迹线建立到达包络，按服务曲线计算正式容量与分组化余量。
2. 对 quiche 与 aioquic 分方向比较到达间隔、计划发送时刻误差和峰值积压，确认实现差异不再是混杂因素。
3. 将每次运行的逐事件收据、离线重放摘要、qlog 和代理日志绑定到同一制品清单。
4. 对容量、链路速率、传播时延和突发包络做预注册敏感性分析，但不在最终测试集上选择容量。

## 5. 修订后的三次门禁

三次串行运行仍为 aioquic、quiche、aioquic。每次至少要求：

1. `response_bytes=67108864`，响应哈希一致；
2. `queue_drop_packets=0`、`random_drop_packets=0`、`send_error_packets=0`；
3. 结束时 `queue_waiting_bytes=0`、`in_service_bytes=0`、`delay_inflight_bytes=0`；
4. 在线摘要与离线事件重放完全一致；
5. 字节守恒成立；
6. 观测最大数据报不超过冻结配置；
7. 发送节奏凭据完整，且计划时刻与实际时刻误差在预注册容差内；
8. 报告峰值字节、容量比例、等价服务时间和三个账户的独立峰值。

`peak_ratio < 0.8` 不再单独决定通过。若 quiche 仍出现高峰值，必须先用到达间隔和节奏滞后证明是端点输入突发、系统调度还是代理服务模型造成，禁止再次只靠扩大容量修复。

## 6. 实现陷阱

1. **接收缓冲冒充数据报上限。**`[u8; 65535]` 只是读取空间，不代表一次 QUIC UDP 载荷为 65535 字节。
2. **配置节奏等于实际节奏。**`enable_pacing(true)` 或 `SO_TXTIME` 成功不代表内核已经按时发送；必须核验 qdisc 与实测间隔。
3. **把传播字节计入服务缓存。**这会重复计算带宽时延积并虚增队列。
4. **以浮点时间排序事件。**长运行中会引入边界比较漂移；当前速率可直接使用整数纳秒。
5. **相同时刻事件顺序不固定。**先准入还是先完成服务会改变容量边界，必须在合同中固定。
6. **以历史丢包反向定容。**把失败运行中的丢包字节加入容量会形成结果驱动参数；只允许独立开发迹线定容。
7. **传输成功掩盖代理丢包。**QUIC 重传能恢复应用内容，必须同时核对代理账本和端点 qlog。
8. **只看总方向。**64 MiB 响应与确认流方向不同，客户端和服务器节奏路径也不同，必须按方向出账。
9. **把工程余量写成物理定律。**`2 MiB/80%` 若保留，必须明确标注其工程角色和预注册时间。
