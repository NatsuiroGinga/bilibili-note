# R2 QUIC v8 确定性有限队列丢包合同

## 1. 合同状态与目标

本合同已经用户批准，但当前只冻结设计，不授权实现、同步或运行。后续实现必须另建实施计划，并按实验工程开发范式完成一次最小红灯与绿灯。

v8 只修正一项合同语义：当固定有限队列因容量不足拒绝数据报，且每个拒绝事件均可由冻结配置和完整事件序列重放证明时，该 `queue_drop` 是网络动力学真值，不再被误判为基础设施失败。

v8 不改变任何科学参数，不追求指定丢包数、吞吐率、分类指标或专家增益，也不把 v7 失败制品追认成成功。

## 2. v7 证据与合同变化依据

v7 run1 的固定身份为 `r2-quic-directional-datagram-v7-run1-aioquic`，原始输出根为：

`/root/autodl-tmp/thesis/experiments/llm_probe/runs/data-raw/r2-quic-directional-datagram-v7-run1-aioquic`

该运行已经证明：

- 方向上限正确绑定为 `client_to_server=1200`、`server_to_client=1350`。
- 代理 `contract_error=null`，数据报上限错误为 `0`。
- 客户端自然完成并收到完整 `67108864` 字节响应。
- PCAP、qlog 和代理事件均已生成。
- `server_to_client` 共发生 `1306` 包、`1761903` 字节队列丢弃。
- 峰值服务积压为 `2097015` 字节，接近固定容量 `2097152` 字节。

首批真实丢弃事件的字段满足以下关系：

- `action="dropped"`
- `reason="userspace_queue_limit_bytes"`
- `admitted=false`
- `service_backlog_before_bytes=2096306`
- `bytes=1350`
- `2096306 + 1350 = 2097656 > 2097152`
- 丢弃后 `service_backlog`、`waiting` 和 `in_service` 均保持不变
- 序列化开始、结束和释放时间均为空

因此，v7 的失败暴露的是合同矛盾：一方面配置明确建立 `2 MiB` 有限队列，另一方面旧门禁又要求队列丢弃必须为零。v8 通过新合同版本和新运行身份修正该矛盾。v7 的启动器状态和单轮审计仍永久保留为 `failed` 与 `NO-GO_KEEP_QUIC_UNKNOWN`。

该变化不是事后放宽以追求模型效果，理由如下：

1. 不修改容量、速率、负载、种子、实现、方向上限或超时。
2. 不读取标签、预测、F1、损失或最终测试集。
3. 不允许任意丢包，只接受能从入队前状态严格复算的容量丢包。
4. 新合同使用新身份重新运行，不覆盖、不裁剪、不重新解释 v7 制品。

## 3. 方案取舍

### 3.1 采用方案：因果可重放的有限队列丢包

保持原有限队列，允许满足严格容量条件且账本闭合的 `queue_drop`。该方案既保留 QUIC 拥塞和重传所需的物理激励，也能通过逐事件审计排除代理异常。

### 3.2 否决方案：扩大队列直至零丢包

扩大容量会改变物理场景，并根据已观察结果反向调参，不能用于 v8。

### 3.3 否决方案：取消队列丢包门禁

无条件接受丢包会混入随机丢包、发送错误、代理过载或事件缺失，无法作为物理真值。

## 6. 确定性有限队列丢包定义

设方向 `d` 的数据报 `i` 到达时：

- 入队前待服务字节为 `B^-_{d,i}`；
- 数据报长度为 `L_{d,i}`；
- 冻结队列容量为 `C=2097152`。

唯一合法准入规则为：

`A_{d,i} = 1[B^-_{d,i} + L_{d,i} <= C]`

其中 `A=1` 表示准入，`A=0` 表示容量丢弃。等于容量时必须准入，只有严格大于容量时才能丢弃。

### 6.1 合法丢弃事件

每条合法 `queue_drop` 必须同时满足：

1. `action="dropped"`。
2. `reason="userspace_queue_limit_bytes"`。
3. `admitted=false`。
4. `bytes` 为正，且不超过该方向冻结数据报上限。
5. `service_backlog_before_bytes + bytes > 2097152`。
6. `service_backlog_after_bytes == service_backlog_before_bytes`。
7. `waiting_after_bytes == waiting_before_bytes`。
8. `in_service_after_bytes == in_service_before_bytes`。
9. 序列化开始、结束和释放时间均为空。
10. 事件全局序号和方向包序号连续，不能缺失、重复或回退。

### 6.2 合法准入事件

每条 `scheduled` 事件必须满足：

1. `admitted=true`。
2. `service_backlog_before_bytes + bytes <= 2097152`。
3. 准入后积压等于准入前积压加数据报长度。
4. 服务中与等待中分类账本闭合。
5. 序列化、传播和最终转发事件能按现有工作保守服务模型重放。

### 6.3 包与字节守恒

每个方向都必须满足：

`received_packets = scheduled_packets + random_drop_packets + queue_drop_packets`

`received_bytes = scheduled_bytes + random_drop_bytes + queue_drop_bytes`

`scheduled_packets = forwarded_packets + send_error_packets + scheduled_packets_at_shutdown`

`scheduled_bytes = forwarded_bytes + send_error_bytes + scheduled_bytes_at_shutdown`

同时必须满足：

- 事件日志中合法容量丢弃事件数量等于 `queue_drop_packets`。
- 合法容量丢弃事件的 `bytes` 求和等于 `queue_drop_bytes`。
- 所有方向的关停队列、待服务、等待中、服务中和传播中字节均为 `0`。
- `peak_service_backlog_bytes <= 2097152`。
- 队列余量诊断可以为假，不作为成功或失败条件；其原始值必须保留。

### 6.4 准入决策流与完整生命周期

对每个方向分别从完整事件日志筛选 `action` 为 `scheduled` 或 `dropped` 的事件，得到准入决策流。该流必须满足：

1. 长度严格等于该方向 `received_packets`。
2. `packet_sequence` 严格覆盖整数 `1..received_packets`，每个值恰好出现一次。
3. 每个接收数据报必须且只能产生一个 `scheduled` 或 `dropped` 决策，不得两者兼有或两者皆无。
4. 所有事件的全局 `sequence` 严格覆盖 `1..N`，无缺失、重复或回退。
5. 方向级 `receive_batch_id` 连续；所有批次的包数和字节和分别等于该方向接收包数和接收字节。

每个 `scheduled` 数据报必须恰有一个同方向、同 `packet_sequence` 的 `service_completed` 事件和一个 `forwarded` 事件。其时间关系必须满足：

`arrival_offset_us <= serialization_start_offset_us <= serialization_finish_offset_us <= scheduled_release_offset_us <= forwarded_offset_us`

服务完成时间必须等于序列化结束时间；服务积压、等待中、服务中和传播中字节必须从前一事件逐项重放至后一事件，不能仅核对最终统计。每个 `dropped` 数据报不得出现对应的 `service_completed`、`forwarded` 或发送错误事件。

离线审计必须从空状态开始，按全局事件顺序重建两个方向的全部队列状态，并最终得到与 `proxy-stats.json` 完全一致的接收、调度、丢弃、转发、峰值和关停统计。任一生命周期事件缺失、重复、跨方向错配或账本中间状态不闭合均计为无法解释事件并立即失败。

## 7. 零容忍错误

以下任一值非零或缺失，单轮立即失败：

- `random_drop_packets`
- `random_drop_bytes`
- `send_error_packets`
- `send_error_bytes`
- `scheduled_packets_at_shutdown`
- `scheduled_bytes_at_shutdown`
- 无法由容量条件解释的丢包数
- 缺失、重复、次序错误或账本不闭合的事件数

以下任一状态出现，单轮立即失败：

- `contract_error` 非空。
- 数据报超过方向级上限。
- 非冻结的丢弃原因。
- 代理、客户端或捕获进程异常退出。
- 客户端超时或非自然完成。
- 服务端退出不满足既有自然退出或控制器 `SIGTERM` 收据合同。

## 8. 完成性与制品门槛

每轮必须同时满足：

1. 客户端在 `240` 秒内自然完成。
2. 响应目录恰有一个文件，大小严格等于 `67108864` 字节。

本合同中的“确定性”只表示：给定记录在事件中的入队前状态、数据报长度和冻结容量，准入或丢弃结论由唯一规则决定，并能被离线逐事件复算。它不表示不同运行的到达时刻、丢包数量、丢包比例或事件文件必须逐字节相同。

## 12. 最小可证伪实验

实现完成后的第一个且唯一允许启动的实验是 v8 run1。该实验必须证明：

1. `1350` 字节服务端数据报继续合法通过方向上限。
2. 至少一个 `server_to_client` 容量丢弃事件满足第 6 节全部条件。
3. 篡改任一丢弃事件，使 `before+bytes<=capacity`、丢弃后状态变化、原因变化或统计计数不闭合时，离线审计必须失败。
