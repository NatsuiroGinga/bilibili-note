# 全项目文档混合检索架构建议

## 结论

**默认查询不应混排论文、过程文档、实验收据和论文正文。** 当前 1701 个 Markdown 只有约 14.1 MB，继续使用 SQLite、FTS5、E5 与 NumPy 精确点积足够；主要风险是权威性、历史状态和敏感信息，而不是向量规模。

推荐保留论文索引 `papers.sqlite3`，新增治理边界独立的 `project.sqlite3`。后者使用多 collection 保存活动项目文档、论文正文和精选实验收据。`scope=all` 在查询时联邦融合两库，不把所有内容复制进单一无差别排名池。

## 五个必答问题

1. **默认是否混排论文与过程文档：否。** 默认按意图选择唯一 scope；只有用户明确跨域或路由无法确定时才使用 `all`，并按分区展示。
2. **如何防止旧恢复卡压过当前真源：** 默认排除 archive、废稿和兼容恢复页；活动恢复卡按 route/chapter 精确选择。历史只在“历史、为何废弃、变更追溯”等意图下启用，并带 `status=superseded/archive` 降权。
3. **scope 如何明确：** `paper/project/experiment/thesis/all` 五类；在线 `papers/code/hub` 是候选通道，不是本地 scope。
4. **SQLite 与 NumPy 是否足够：是。** 当前文档与向量规模距离需要 ANN 尚远，先构建真实全项目索引并剖析。
5. **何时 ANN 或分库：** 分库现在就按治理边界实施；ANN 只在精确向量矩阵超过 1 GiB，或代表性并发下向量扫描 P95 超过 50 毫秒且占总查询时间 30% 以上时进入对照评估。ANN 必须相对精确结果达到 Recall@10 不低于 0.99，才可替换默认通道。这些是测量触发门，不是预判当前系统已需要 ANN。

## 作用域合同

| scope | 默认 collection | 主要用途 | 默认排除 |
|---|---|---|---|
| `paper` | `papers` | 文献、相关工作、引用、机制来源 | 过程文档、实验、论文草稿 |
| `project` | `route-control`, `recovery`, `plans`, `reports`, `research-notes` | 当前路线、状态、计划、决策追溯 | archive、废稿、逐样本制品 |
| `experiment` | `experiment-receipts` | 运行状态、聚合指标、配置和资源 | 检查点、预测、最终测试标签、原始大数组 |
| `thesis` | `thesis-chapters`, `output-deliverables`, `bibliography` | 正文定位、章节一致性、公开表述 | 过程日志、历史草稿 |
| `all` | 上述 scope 联邦查询 | 明确跨域问题 | 不取消敏感过滤，不把候选通道混入证据 RRF |

路由优先使用明确触发词和当前任务路径：文献问题走 `paper`；“当前状态/为何/计划”走 `project`；“指标/运行/资源”走 `experiment`；“第几章/正文/表述”走 `thesis`。无法唯一确定时返回分区结果并说明所选 collection，而不是静默混排。

## 物理存储裁决

### `papers.sqlite3`

保持现有论文身份、多视图、结构化 YAML、块向量和论文级 RRF。其更新由 `indexed-paper-reading` 与论文 lint 驱动，稳定性和证据门槛最高。

### `project.sqlite3`

使用同一 SQLite 模式和嵌入后端，但按 collection 隔离：

- `route-control/recovery`：总控和当前章节恢复卡。
- `plans/reports/research-notes`：活动实施计划、报告和过程笔记。
- `experiment-receipts`：明确 allowlist 的状态、manifest、聚合指标和资源收据。
- `thesis-chapters/output-deliverables`：论文正文与高层交付。

分成两个物理库的理由不是性能，而是治理：论文库可复用严格全文与身份合同；项目库更新频繁、含历史和敏感面，必须独立清理、重建、权限和陈旧策略。不要为每个 scope 再建一个库，否则原子构建、版本和联邦查询成本不必要地增加。

## 元数据合同

每个文档和分块至少保存：

| 字段 | 含义 |
|---|---|
| `doc_id`, `note_id` | 稳定规范路径或结构化制品身份 |
| `collection`, `doc_type` | 物理集合与文档类型 |
| `authority` | `source/current-control/run-fact/requirement/review/public-draft/working-note/history` |
| `route`, `chapter` | RWKV/PINN-R2 等路线及章节；不适用为 null |
| `status` | `current/active/pending/completed/superseded/rejected/archive` |
| `date` | 文档事实日期，不用文件 mtime 代替 |
| `evidence_level` | 全文、原始运行、聚合收据、审查、计划、推论等 |
| `sensitivity` | `public/project/restricted/excluded` |
| `source_hash`, `parser_contract_hash`, `embedding_contract_hash` | 增量与陈旧检测 |
| `title_path`, `chunk_key` | 标题层级和稳定块身份 |

`authority` 必须随查询意图解释：运行指标以 `run-fact` 高于报告；路线边界以 `current-control` 高于旧计划；文献主张以原件/全文高于论文草稿。不能用一个固定全局权重替代领域规则。

## 分块策略

- 论文笔记：沿用结构化元数据块与标题路径块，后续只在块级 qrel 就绪后评估 token 感知调整。
- 总控/恢复卡：按二级或三级标题切分，始终附带 route、chapter、status 和文档标题；表格不拆行。
- 计划/报告/notes：标题路径加段落边界；“目标、合同、结果、风险、下一步”分别成块，避免把需求与结果放在同一块。
- 论文正文：按小节和论证段落切分，保留章节号、图表题、公式号和引用邻域。
- JSON/CSV 实验收据：不转储原始文本；由类型化适配器提取允许字段形成一个运行摘要块和若干指标块。
- 源码、Shell、配置默认不做自然语言索引；需要源码时走 GitHub/本地代码搜索，而不是扩大文档 RRF。

## 历史与权威降级

默认查询仅纳入 `current/active/completed`。`superseded/rejected/archive` 必须由显式历史意图解锁，并在结果中显示状态和替代文档。`RWKV当前恢复卡.md` 只是兼容页，不得与第三/四章恢复卡并列高权重。恢复文档冲突时按根规则使用新原始证据修正路线总控，检索器不自动裁决事实。

## 敏感信息门禁

采用目录 allowlist 加内容拒绝两层门禁：

1. 只允许明确 collection 的 Markdown 和精选结构化收据。
2. 排除环境文件、密钥、证书、认证头、登录命令、私有地址、模型权重、检查点、逐样本预测、成员数组、最终测试标签和原始大数组。
3. 构建前只报告命中路径和原因，不把疑似秘密写入错误摘要。
4. `runs/` 不递归全文索引；实验 collection 由 manifest allowlist 精确选取聚合 JSON。
5. GitHub/HF token 只从环境进入请求头，外部候选保持 `unverified` 或 `paper_linked_candidate`，不自动下载或入库。

## 增量、融合与陈旧

- 继续使用规范路径、源哈希、解析合同和嵌入合同共同决定复用；mtime 只作诊断。
- 每个 collection 独立记录 manifest、added/changed/deleted/reused/reembedded/excluded。
- 先在 collection 内完成 BM25/向量 RRF，再进行 scope 级联邦 RRF；不同 collection 原始 BM25 或余弦分数不可直接相加。
- 联邦阶段按路由给定候选配额和 authority 门禁，权威只用于同语义候选的裁决与展示，不用来把不相关高权威文档推上榜。
- `all` 输出本地证据分区和在线 `paper_candidates/code_candidates/hub_candidates`；在线候选不进入本地证据融合。

## Codex 自动路由

1. 先识别意图 scope，再运行相应本地状态与查询。
2. 文献不足或用户要求近期工作时扩展学术 API；需要源码调用官方 `github:github`；需要 HF 模型、数据、Space 或论文关联调用现有 HF 技能。
3. 外部候选只读；正式纳入转 `indexed-paper-reading`。
4. 项目、实验和论文正文查询默认不联网，除非用户明确需要外部核验。
5. 结果必须带 scope、collection、authority、status、evidence_level 和原路径，避免用户把计划、历史或候选误当事实。

## 真实用户查询评估

- `curated-regression-v1` 只用于开发与回归，不代表用户分布。
- `real-user-query-v1` 的 8 条原问在独立 qrel 完成前不运行、不展示排名、不用于调参。
- qrel 必须分别标注 scope、相关 doc_id、证据块、允许的历史状态和期望 authority。
- 每个 scope 分别报告 Recall@5/10、MRR、nDCG、块命中、错误 collection 率、历史文档误升率、敏感排除、延迟和零结果；禁止把五个 scope 合并成单一平均数掩盖路由错误。

## 优先级

### P0

- 冻结 scope、collection、元数据、authority/status 和敏感 allowlist；没有该合同不得扫描 `.Codex/docs` 或 `runs/`。
- 建立 `project.sqlite3` 的 Markdown 与结构化实验收据适配器，默认排除历史和敏感对象。
- CLI 强制回显路由与证据元数据；`all` 只做联邦分区，不做无差别混排。

### P1

- 独立标注真实用户多 scope qrel，建立历史误升和敏感门禁评估。
- 为长计划、表格、论文正文和结构化收据实现类型化分块。
- 增加 collection 级增量收据、延迟剖析和重复/冲突诊断。

### P2

- 只有达到测量触发门时比较 NumPy 精确扫描与 ANN；精确结果始终保留为金标准。
- 在有足够开发 qrel 后再评估 authority-aware 联邦融合参数，不使用真实用户验收集调参。

## 最多三项立即实施建议

1. **P0：先冻结全项目索引清单与元数据 schema。** 收益是阻止历史、计划和敏感制品误入；成本低到中；风险是 allowlist 漏收，使用 dry-run 清单人工审阅验证。
2. **P0：保留论文库并新增单一项目库多 collection。** 收益是复用现有索引器且隔离治理；成本中；风险是联邦重复，通过 doc_id、来源哈希和分区输出验证。
3. **P1：先做真实用户多 scope qrel 与路由评估，再调融合或考虑 ANN。** 收益是让扩展可证伪；成本中；风险是标注受现有排名污染，因此标注阶段禁止查看系统输出。

## 验收门

- dry-run 清单中 0 个凭据、检查点、逐样本预测、最终测试标签和 archive 默认对象。
- 每个 scope 的前 10 项均显示 collection、authority、status、evidence_level 和路径。
- 当前恢复问题不返回旧兼容卡或 archive；历史问题能显式找回并标注替代关系。
- 增量与干净全量在文档、块、FTS、向量字节和固定查询排序上一致。
- 在 ANN 触发前记录真实矩阵字节、加载、点积、P50/P95/P99 和并发；未达到触发条件继续精确扫描。
