# R2 QUIC v5 第一轮失败只读诊断

## 1. 结论

v5 第一轮在客户端发送首个 QUIC 数据报之前失败。唯一根因假设已经由原始日志、工具路径和源码构建入口相互印证：v5 的 Python 包装器把纯源码目录置于 `PYTHONPATH` 首位，使 `aioquic` 从 v5 源码树加载；该源码树没有已编译的 `aioquic._buffer` 扩展，而可用的 `_buffer.abi3.so` 只存在于 v1 虚拟环境的 `site-packages` 中，因此客户端导入阶段立即退出 1。

这不是网络动力学、队列容量、发送节奏、证书、端口、超时或服务端协议行为导致的科学条件失败。按冻结合同，本次 v5 三轮尝试必须记为 `NO-GO_KEEP_QUIC_UNKNOWN`，不得继续 run2、run3，也不得重试 run1；但该结果只否决本次 v5 工具链绑定，不否决 QUIC 专家或端点节奏机制。

## 2. 调查边界

- 只读检查 v5 合同、实施记录、官方方案报告、实现报告以及旧 5090 服务器上的 run1 原始制品。
- 未修改代码、配置、工具、运行目录或冻结报告。
- 未补跑 run1，未启动 run2/run3，未占用 GPU，未干预 TCP 实验。

服务器运行入口：

- 启动器：`runs/launchers/r2-quic-endpoint-pacing-v5-run1-aioquic/`
- 数据根：`runs/data-raw/r2-quic-endpoint-pacing-v5-run1-aioquic/`
- 连接：`connections/b74dd9cdddca8667358671db/`

## 3. 首个致命日志行

客户端完整回溯最终停在：

```text
ModuleNotFoundError: No module named 'aioquic._buffer'
```

调用链从 v5 源码树中的 `examples/http3_client.py` 进入 `aioquic.asyncio.client`、`aioquic.tls` 和 `aioquic.buffer`，随后相对导入 `._buffer` 失败。启动器稍后报告的“客户端自然退出码非零：1”只是对该首个错误的上层传播，不是根因。

## 4. 根因证据链

### 4.1 v5 包装器改变了包解析根

`scripts/build_r2_quic_v5_toolchain.sh` 生成的 v5 Python 包装器执行：

```bash
export PYTHONPATH="${TOOL_ROOT}/sources/aioquic-1.3.0/src${PYTHONPATH:+:${PYTHONPATH}}"
exec "${BASE_ROOT}/aioquic-venv/bin/python" "$@"
```

因此虽然解释器来自 v1 虚拟环境，`aioquic` 包本身会优先从 v5 源码树加载。

### 4.2 源码树和安装包的扩展制品不一致

- v5 源码树只存在 `aioquic/_buffer.c` 与 `aioquic/_buffer.pyi`。
- v1 虚拟环境存在 `site-packages/aioquic/_buffer.abi3.so`。
- Python 已从 v5 源码树加载顶层 `aioquic` 包，随后相对导入只在同一包路径内查找 `_buffer`，不会退回 v1 的同名包目录拼接扩展模块。

这解释了为什么构建阶段只对 `protocol.py` 执行 `py_compile` 能通过，而真实客户端导入整个 `aioquic` 包时失败：`py_compile` 不会验证运行期 C 扩展能否从当前包根加载。

### 4.3 失败发生在网络交互之前

- 连接总耗时 `2.049` 秒，`client_natural_completion=true`、`client_exit=1`，不是 240 秒超时。
- `observed_client_endpoint=null`，说明客户端没有成功绑定冻结源端口。
- 代理已在 `127.0.0.1:20012` 就绪，但收包为 0。
- 抓包进程与代理退出码均为 0。
- 参考服务端退出码 `-15` 带有控制器发送 `SIGTERM` 的收据，是客户端失败后的正常清理，不是服务端自行崩溃。

## 5. 分类裁决

| 候选类别 | 裁决 | 证据 |
| --- | --- | --- |
| 科学条件失败 | 否 | 客户端在首包前导入失败，物理队列、节奏和 QUIC 传输均未发生。 |
| v5 端点节奏算法缺陷 | 未触发 | 打补丁的端点逻辑尚未执行，不能据此评价节奏机制。 |
| 启动器身份或配置绑定错误 | 否 | run1 身份、aioquic 1.3.0、目标索引 12、方向种子和配置 SHA-256 均与冻结合同一致。 |
| v5 工具链绑定缺陷 | 是 | 纯源码包覆盖已安装包，但源码包缺少同包根下的编译扩展。 |
| 证书或端口错误 | 否 | 证书与密钥已生成，代理和参考服务端端点已绑定，运行前后端口排他性检查通过。 |
| 客户端超时 | 否 | 客户端在约 2 秒内自然退出 1。 |
| 服务端异常 | 否 | 服务端由控制器在客户端失败后发送 `SIGTERM` 结束。 |

## 6. v5 门禁裁决

冻结合同规定任一轮失败即为 `NO-GO_KEEP_QUIC_UNKNOWN`，且不允许重试失败轮、补第四轮或在失败后调整参数继续同一合同。因此：

1. v5 run1 保留为失败制品。
2. v5 run2、run3 不启动。
3. 当前 `quic_expert_ready` 仍为 `false`，QUIC 继续走 `UNKNOWN`。
4. 该失败不得写成 QUIC 物理机制无效，也不得计入队列容量或节奏科学统计。

## 7. 下一版本最小修复边界

下一版本只能修复 Python 包的运行时绑定，不得同时改数据、端口、容量、种子、节奏公式或审计阈值：

1. 保证被加载的 `aioquic` 包目录同时包含补丁后的纯 Python 模块与兼容的 `_buffer.abi3.so` 等编译扩展。可选择在隔离虚拟环境中从修补后的源码完成正式安装，或在独立复制的已安装包内只替换经哈希绑定的纯 Python 模块；不得继续用不完整源码根覆盖整个已安装包。
2. 构建门禁必须使用正式客户端的同一解释器和同一包路径执行运行时导入检查，至少验证 `aioquic._buffer`、`aioquic.asyncio.protocol` 和客户端入口可导入，并记录模块实际来源路径与 SHA-256。
3. 新合同使用新版本身份和全新运行目录；不得复用或覆盖 v5 run1。
4. 只有运行时导入门禁通过后，才允许从新的 run1 开始严格串行三轮。

这是一项单一、可证伪的工具链修复，不需要调整 QUIC 物理模型，也不需要 GPU。
