# RWKV 固定结构统一 BF16 重训证据笔记

## 范围裁决

- 主代理最新裁决覆盖初始任务：BF16 不重做已经完成或正在完成的 FP32 配置搜索。
- 输入适配器固定为 R2；最终容量只从旧 FP32 `capacity_selection_frozen.json` 消费。
- 容量收据尚未生成时只允许模板配置存在，正式启动必须机械阻断，不得预填 K。
- BF16 新运行只训练固定结构的 C00/C01/C10/C11，各格从头初始化，不复用 FP32 权重、优化器、轮次或目标结果。

## 兼容性裁决

- 旧 rerun1 检查点身份包含当前 FP32 工具 SHA-256；直接修改旧工具会使后续原生恢复失败。
- 因此旧 FP32 工具与启动器保持字节不变，BF16 使用独立 Python 工具和独立 Shell 入口。
- 新入口可以复用旧工具的只读数据、切分、指标和制品辅助函数，但不能调用其适配器/容量搜索主流程。

## PyTorch 接口核验

- 目标环境版本来自统一精度实施报告：PyTorch `2.13.0+cu130`；本任务不访问服务器，未重新探测。
- Context7 库：`/pytorch/pytorch`；当前没有 2.13 固定文档页，最接近固定页为 `/websites/pytorch_2_12`。
- Context7 核验统一入口为 `torch.amp.autocast(device_type, dtype=..., enabled=...)`；CUDA BF16 使用 `dtype=torch.bfloat16`，FP32 敏感区使用同一入口并设 `enabled=False`。
- 统一精度合同已机械规定 BF16 不创建 `GradScaler`；目标 2.13 的真实 CUDA 行为仍须在正式环境第一完整优化步核验。

## 双归一约束

- 旧流损失分母是有效流数量。
- ELP 辅助损失分母是按冻结正类权重加权后的序列权重和，不等于有效流数，也不等于未加权序列数。
- 共享单目标累积器不能把两种分母合并为一个 `normalization_unit`。BF16 入口仍复用共享配置、autocast、FP32 岛、微批计划、检查点状态和 FP32 参数门，但在模型入口显式计算两条全有效批分母，并把流与序列运行时状态分别写入检查点。

## 微批依据

- 有效批 64 个序列继承旧冻结训练合同，不改变科学预算。
- 微批 8、累积 8 是资源实现参数，不参与指标选择。对最坏 K2，单层递归矩阵状态为 `8×12×64×64×4 = 1,572,864` 字节，三层单时间点约 4.5 MiB；时间展开与反向仍须以正式首步收据核验。
- 所有四格使用同一解析后容量、同一 profile 和同一微批计划。

## 实施发现

- 旧 FP32 工具的 `forward` 将输入 dtype 与递归状态 dtype 绑定为同一个 FP32 条件；BF16 专用模型改为 profile 身份门，输入仍从 FP32 数据缓存送入，由 autocast 只在适配器和安全算子处降为 BF16。
- RWKV 递归函数本身已把 `r/k/v/a/b/w` 提升为 FP32并新建 FP32 矩阵状态；BF16 专用时间混合又在进入递归前显式关闭 autocast，避免依赖隐式提升。
- 每格第一完整优化步分别写资源收据，因此 C11 的序列归一化与额外机制也有独立首步证据，不以 C00 收据替代。
- 解析配置只在启动器运行目录生成，模板始终保留 `selected_capacity=null` 与空摘要；这使未封印容量不会被误写成科研事实。

## 静态验证事实

- 项目 `uv --no-sync` 本地环境缺少 `numpy`，模块导入在依赖加载处失败；没有安装或同步依赖。
- 使用仓库既有 `/opt/miniconda3/envs/rwkv/bin/python` 完成模块导入、帮助和配置核验。
- K0、K1、K2 三种可能的解析容量均只做模型实例化与 R2 参数量核验，全部通过；没有前向、反向或训练。
- `py_compile`、JSON 解析、`bash -n`、`git diff --check` 和静态精度岛搜索通过。
