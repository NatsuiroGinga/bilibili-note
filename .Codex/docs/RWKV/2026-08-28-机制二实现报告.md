## 二、任务 1：实体分层采样器

### 接口

- `EntityStratifiedSamplerConfig(n_pos, n_neg, max_bag_flows=None)`：冻结数据类，
  `n_pos`/`n_neg` 无默认值（由未来宿主按共同预算合同冻结，本模块不代为选择）。
- `EntityStratifiedSampler.sample(rng) -> dict`：返回
  `positive_entities`/`negative_entities`/`segment_rows`（按 `(entity,T23)` 升序）。
- `EntityStratifiedSampler.batch_composition_receipt(batch) -> dict`：正/负实体数、
  总片段数、总有效流数、最长袋流数、被截断实体数（对照诊断阈值 `max_bag_flows`）。

### 实现要点

- 实体索引：`np.lexsort((T23, E23))` 一次建立全局 `(entity,T23)` 升序片段行序，
  配合 `np.bincount` 前缀和给出每实体的片段行区间，`sample()` 直接切片拼接。
- 正实体标签、每实体有效流总数：独立实现（不导入既有诊断脚本
  `ch3_lspr23_entity_history_availability.py`，避免隐式耦合），分块扫描
  `I23/M23/y23`，逻辑与该诊断脚本一致（已用真实数据交叉验证结果量级一致，
  见下）。
- 正实体抽样：不放回轮转队列，一轮（正实体基数 239）耗尽后重新洗牌；
  跨轮边界处若与本次已抽出实体撞车则放回队尾重抽，保证同批内绝不重复。
- `require(positives.size >= 1, "每步至少一个正实体")` 作为运行断言，是
  阻断条件第一条的直接实现。

## 三、任务 2：前缀实体分数与多预算 CVaR-pAUC 损失

### 接口

- `prefix_scores(logits, valid, segment_owner) -> (entity_scores[E], entity_source_row[E])`。
- `cvar_pauc_loss(pos, neg, budgets, xi) -> (loss, diagnostics)`。
- `bag_policy_diagnostics(logits, valid, segment_owner, entity_is_positive, entity_chain_length, budgets, xi, config) -> dict`：
  同批并行算三种袋处置，只对 `config.active_policy` 保留反传图。
- 附加工具：`CvarThresholdState`（按全局实体 ID 持久化 `xi`）、
  `effective_budget`（5.4 节无偏抽样折算）。

### 第三方 API 核验记录（`npx ctx7@latest`，本机 PyTorch `2.12.0`）

| 查询 | 来源 | 核验到的签名/行为 |
| --- | --- | --- |
| `torch.argmax` 并列行为 | `docs.pytorch.org/docs/2.11/_sources/generated/torch.Tensor.argmax.rst.txt` | 「If multiple values equal the maximum of the tensor, the first occurrence of the maximum value is returned」——并列取首个最大值，已确认为官方文档行为 |
| `Tensor.scatter_reduce` | `docs.pytorch.org/docs/2.11/generated/torch.Tensor.scatter_reduce.html` | `Tensor.scatter_reduce(dim, index, src, reduce, *, include_self=True) -> Tensor`，out-of-place，`reduce` 支持 `"sum"/"prod"/"mean"/"amax"/"amin"` |
| `Tensor.scatter` | `docs.pytorch.org/docs/2.11/generated/torch.Tensor.scatter.html` | `Tensor.scatter(dim, index, src)`，out-of-place 版本存在 |

设计决策：由于 `scatter_reduce` 官方文档未对 `amax`/`amin` 的并列反传行为
给出保证，`prefix_scores` **不依赖其反传**，只用它做数值定位（对其输入
`.detach()`），真正的梯度路径始终经确定性的 `argmax`（并列取首个，已核验）
+ `gather`（标准、无歧义的反传路由到单一位置）组合，保证梯度只回到唯一
确定的一条流，不依赖任何未文档化的并列反传约定。

### 实现要点与设计判断（与 spec 5.3/5.4 节的一处显式接口约定）

- `prefix_scores` 用两级定位（片段内 `argmax`+`gather`，片段间
  `scatter_reduce(amax)` 定位数值 + `scatter_reduce(amin)` 定位最靠前来源
  片段 + `gather` 取值）实现 `S_e=max_t l_{e,t}`，唯一最大值梯度只回到该流，
  并列固定取「最靠前」（若调用方按 task1 的 `(entity,T23)` 升序传入，等价于
  取因果最早的流）。
- `cvar_pauc_loss` 按 spec 5.3 公式**字面实现**（`R_K=mean_p[xi+(1/K)*sum_n[.]_+]`），
  对「当前传入的 `neg`」求和。spec 5.4 节的无偏性论证要求当 `neg` 是从更大
  总体 `N_-` 均匀抽样而来时，需按 `beta_K=K/N_-` 重加权；本实现把这一步
  显式拆到 `effective_budget()` 工具函数，由调用方决定是否应用——这是本次
  独立模块实现相对 5.4 节留下的**一处透明的接口约定**，理由：`budgets` 的
  真实值来自「源年冻结告警合同」，该合同尚未接入本次范围，若在本模块内
  暗自套用某个假设的 `N_-` 会引入未经登记的魔法数字。诊断验证中按探针
  脚本同款约定处理（把批内 `neg` 当作全体负实体，与 `ch3_gradient_controller_conflict_probe.py`
  的口径一致，因此两者的比值可直接比较）。
- `bag_policy_diagnostics` 的「分层加权」处置：spec 5.3.1 节明确标注该处置
  仍「待裁决」。本实现给出一种可运行、可比较、退化时与完整袋等价的忠实
  解释——把 `cvar_pauc_loss` 中「负实体 `(1/K)*sum_n`」与「正实体外层
  `mean_p`」两处等权均值，都换成「先桶内等权均值、再桶间等权均值」的
  两层分层均值（`log2` 尺度分桶，边界由本批实体链长自身量级决定，不引入
  外部魔法阈值）。全部实体落在同一桶时退化为与完整袋数值相同。**此为本
  代理的实现判断，非源年数据裁决结果**，若未来源年裁决出不同权重公式，
  只需替换 `_cvar_pauc_loss_stratified`，不影响其余接口。
- `bag_policy_diagnostics` 的因果前缀截断：按 `(片段序号,列位置)` 因果序
  逐实体截断有效掩码；发现并修复一处实现缺陷（见下）。

### 实现中发现并修复的缺陷

`prefix_scores` 最初要求「每个片段（行）至少一条有效流」，但因果前缀截断
会把超出预算的片段整体置为无效（这是设计的一部分），导致真实运行时在
`bag_policy_diagnostics` 内触发该断言而崩溃。根因：断言粒度错误——应在
**实体级别**核验「每个实体至少一条有效流」，而不是在**片段级别**核验
「每个片段至少一条有效流」（后者与因果截断的语义直接冲突）。修复：移除
片段级断言，改为在算出 `entity_scores` 后核验 `torch.isfinite(entity_scores).all()`
（若某实体被截断到 0 条有效流则其分数为 `-inf`，会被此断言捕获，属于
调用方配置错误，非本函数缺陷）。修复后真实数据运行通过。

## 七、遗留风险

1. **`cvar_pauc_loss` 的population-scale重加权未在本次范围内验证**：
   `effective_budget()` 是按 5.4 节公式推导的工具函数，但本次三个模块均
   不接入宿主，未在真实的「大总体负实体池 + 小批量抽样」场景下端到端
   验证其数值效果，留给宿主接入阶段核验。
2. **`stratified_weighting` 的具体权重公式是本代理的实现判断，非源年数据
   裁决**：见第三节说明，5.3.1 节该处置仍标「待裁决」，等 C00 双选轮跑出
   源年前缀分数曲线后可能被替换。
3. **`CvarThresholdState` 未在真实多步训练循环中验证跨步持久化**：本次
   诊断脚本每次调用都用零初始化或分位数初始化的一次性 `xi`，未验证
   `get()`/`commit()` 在真实多步优化中的行为（该行为依赖宿主训练循环，
   不在本次范围内）。
4. **`prefix_scores` 对因果截断产生的空片段的处理已修复并验证，但
   `_causal_truncate_valid` 使用 Python 级双重循环**（按实体、按片段），
   对诊断规模（每实体≤8段）足够快，但未在生产规模（单实体可达 19,338 段）
   下做性能测试；若未来宿主接入需要处理真实全量袋规模，建议先做性能
   基准测试，必要时向量化。
5. **`bag_policy_diagnostics` 的 `truncate_length` 诊断默认值 256 与
   5.3.1 节记录的生产值 8192 不同**，仅为在诊断子采样批上实际触发截断
   路径而选取，报告已在参数说明与本文档中明确标注，未来宿主接入必须
   使用冻结的生产值，不得沿用本诊断默认值。
