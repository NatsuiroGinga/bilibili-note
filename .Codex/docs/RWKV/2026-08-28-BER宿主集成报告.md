### 2.2 训练步接线（对应计划任务 1 步骤 2 的五步伪代码）

新增函数与既有函数的关系：

| 新增函数 | 与既有函数的关系 |
| --- | --- |
| `prepare_entity_ranking_sampler` | 把 `EntityStratifiedSampler` 限定在训练角色片段内（`arrays["E23"][train_rows]` 等），避免验证角色实体泄漏进训练侧采样——独立模块本身不知道训练/验证角色概念 |
| `_flow_phase_bare` | 复刻既有 `training_step`，唯一差异是不调用 `accumulator.finish()`（不清空 `.grad`、不 `optimizer.step()`），留给调用方读出 `g_flow` 后自行合成 |
| `_flow_phase_entity_memory` | 复刻既有 `entity_memory_training_step`，同样只是不调用 `finish()` |
| `_entity_ranking_bare_forward` | z1=0 时实体排序批的并行前向（无跨片段状态依赖） |
| `_entity_ranking_memory_forward` | z1=1 时实体排序批的顺序前向，读写**独立 scratch `EntityMemoryState`**（见 2.3 节） |
| `_ranking_phase` | 抽实体批、（按 z1 分派两种前向）编码、`bag_policy_diagnostics` 算 CVaR-pAUC、`xi` 用自身子梯度更新、读出 `g_rank` |
| `_combine_and_step` | `combine_gradients` 合成 + `verify_first_order_invariants` 机械核验 + 写回 `.grad` + 一次 `optimizer.step()` |
| `entity_ranking_training_step` | C01：`_flow_phase_bare` + `_ranking_phase(entity_memory_enabled=False)` + `_combine_and_step` |
| `combined_mechanism_training_step` | C11：`_flow_phase_entity_memory` + `_ranking_phase(entity_memory_enabled=True)` + `_combine_and_step` |

**为什么不改造 `training_step`/`entity_memory_training_step` 本身**：这两个函数是 z1/z2=0
阻断条件保护的既有对象，任何改造都有意外改变既有路径的风险；复制少量代码（约 60 行/份）换取
"z2=0 时新增代码路径完全不被触碰"这一从代码结构上即可验证的事实，而不只是运行时断言。

`probe_runtime`/`run_training` 的训练步分派从二路 `if/else` 扩展为四路 `if/elif/elif/else`
（C11/C10/C01/C00），`z2=0` 分支（第三、四路）与改动前逐字相同。`run_training` 对
`entity_ranking_enabled=True` 同样 `require(not resume, ...)` 拒绝 `--resume`（采样器状态与
`CvarThresholdState` 尚未纳入检查点，与 z1 的既有限制同理）；每轮落盘
`entity-ranking-diagnostics-{epoch}.json`（`c_scaling` 中位数、`c==1` 步数、梯度范数中位数、
投影触发步数、末步完整快照）。

### 2.3 C11 的联合设计：独立 scratch 记忆状态（新增判断，非计划字面规定）

设计规约第六节的"联合算法"要求 C11 的排序分数直接来自机制一正在推进的同一严格过去状态
`M_(t-1)`。若直接复用训练角色链式调度器（`EntityChainScheduler`）持有的**持久**
`memory_state`，会与 `EntityStratifiedSampler`（不感知链式游标、总是从实体因果最早片段开始）
在同一优化步内对同一实体产生两条独立的状态遍历，后者可能把状态推进到"未来"（超出链式调度器
游标当前位置），导致下次链式调度器按游标读到不该读到的未来信息，违反设计规约第 4.3 节的
严格过去约束与第 8.5 节"硬失败：任何未来信息"判据。

处置：为 C11 的实体排序批新建一个**独立的第二个 `EntityMemoryState` 实例**（"scratch"，与
持久 `memory_state` 完全隔离，不写回、不共享张量），每次经过实体首段时按
`EntityMemoryState.reset_entities` 语义自动清零——这是宿主接线阶段新增的隔离设计，两个机制
模块本身均未涉及这一问题（各自独立正确，只是从未被设计成共享同一状态实例）。**这是对设计规约
"同一 `M_(t-1)`"字面表述的一处偏离**：C11 当前实现的排序分数来自一次独立的从头重放，而不是
与流表示共享的同一在线状态；完全共享状态的联合算法留待源年前缀分数曲线裁决袋处置方案后再设计
（与设计规约第 5.3.1 节"裁决时点"一致），已在代码注释与本报告中显式登记，不掩盖为"已完成"。

### 4.1 C01 在本机 MPS 上的真实运行：发现一处设备相关缺陷（非本次接线代码缺陷）

用临时缩小配置（`n_neg=8`、`truncate_length=512`，未落盘为新文件，与机制一实现报告"构造
slots=4 临时配置"同一做法）跑通到"零门退化断言通过""采样器就绪：正实体池=165 负实体池=121336"
后，在 `_ranking_phase` 内部调用 `ch3_ft_entity_ranking_loss.prefix_scores()` 时崩溃：

```
File "ch3_ft_entity_ranking_loss.py", line 109, in prefix_scores
    first_pos = first_pos.scatter_reduce(0, segment_owner, candidate_pos, reduce="amin", include_self=True)
RuntimeError: not supported for torch.int64
```

**根因定位**（最小隔离实验，单变量=dtype）：

```python
# /opt/miniconda3/envs/rwkv/bin/python，torch 2.12.0，device=mps
torch.int64 amin FAILED: RuntimeError('not supported for torch.int64')
torch.int64 amax OK -> tensor([3., 4., 5., -inf, -inf])
torch.int32 amin OK -> tensor([0, 0, 0, 0, 0], dtype=torch.int32)
torch.float32 amin OK -> tensor([0., 0., 0., 0., 0.])
```

PyTorch 2.12.0 的 MPS 后端**不支持** `Tensor.scatter_reduce(reduce="amin")` 作用于 `int64`
张量（`int32`/`float32` 均正常）。`prefix_scores()` 内部 `positions = torch.arange(..., device=device)`
默认生成 `int64`，`first_pos`/`candidate_pos` 因此继承 `int64`，触发该限制。这是
`ch3_ft_entity_ranking_loss.py`（机制二冻结模块）本身在真实 `device="mps"` 场景下的一个此前
未被覆盖的边界情况——该模块作者的诊断脚本 `main()` 从未显式 `.to(device)`，一直停留在 CPU
默认设备，从未触发过这条路径。**本次未修改该模块**（"不要重写，只接线"），已作为独立发现
向协调者报告，并派发了一个后台核验任务（`task_9a1ae3d4`）请求在服务器 CUDA 环境上跑同一条
最小复现命令，确认 CUDA 是否受同一限制——这直接决定 C01/C11 能否在服务器上按当前实现运行，
是需要主代理裁决的真实风险，不是可以在本次任务内自行消化的次要问题。

### 4.2 C01 在 CPU 上的完整端到端核验：宿主新增代码本身正确

`prefix_scores()` 的 MPS 限制不影响 CPU（machine 2 的诊断脚本证明过 CPU 路径可用）。为了在
"MPS 阻塞"与"任务 3 已降级为可选"的双重约束下仍验证本次新增的宿主胶水代码（`_ranking_phase`/
`_combine_and_step` 等）本身是否正确，写了第二个探针脚本，绕过 `resolve_runtime` 的

## 六、遗留风险

1. **C11 参数量与计划文本冲突**（见 3.4 节）：已选择与冻结 C10 一致的 `1,075,196`，偏离计划
   文本字面的 `1,074,428`；需要用户/主代理裁决是否需要更新实施计划文本，或反过来统一改回 R=4
   （后者需连带修改已冻结的 C10 配置，本次未做）。
2. **MPS 上 `prefix_scores()` 因 `int64 scatter_reduce(amin)` 崩溃**（见 4.1 节）：已定位根因、
   已派发后台核验任务确认 CUDA 是否同样受限（`task_9a1ae3d4`）。若 CUDA 也受限，`ch3_ft_entity_ranking_loss.py`
   需要修复（例如把内部定位用的索引张量改为 `int32`，或改用不依赖 `scatter_reduce(amin)` 的
   并列定位实现），这是机制二模块自身的缺陷，不在本次"只接线"范围内，需要主代理决定由谁、何时修。
3. **C11 的排序分数来自独立 scratch 记忆状态，非设计规约字面的"同一 `M_(t-1)`"联合**（见 2.3 节）：
   当前实现是正确、无因果泄漏的简化版本，但不是设计规约第六节描述的完全共享状态联合算法；后者
   留待源年前缀分数曲线裁决袋处置方案后再设计。
4. **C10/C11 未在本机跑通端到端冒烟**：C01 已验证（MPS 到 `_ranking_phase` 前、CPU 全链路），
   C10 本身在机制一报告中已验证，但"C10 + BER 排序批（走 scratch 记忆）"这一组合在本次 C11
   代码路径下**从未真实运行过一次**，其正确性目前只能类比 C01 的验证结果与 C10 已验证的记忆
   读写逻辑推断，未经直接真实运行确认；首次在服务器 CUDA 上运行 C11 时须格外关注。
5. **`xi_learning_rate=1e-4` 是本代理的实现判断**，非源年数据裁决值（复用科学身份唯一已冻结
   学习率，避免引入新魔法数字，但未验证是否是合适的 `xi` 更新速率）；若观察到 `xi` 轨迹发散或
   不收敛，需要另行调整。
6. **`max_segments_per_entity` 的宿主侧片段级预截断**（`ceil(truncate_length/sequence_length)=64`）
   意味着 `bag_policy_diagnostics` 并行计算的"`full`"策略并非真正无限制的完整袋，而是"完整袋
   截至宿主预截断上限"——这是让训练在有限时间内可行的必要工程妥协，已在代码注释中说明，未来若
   需要真正的完整袋对照实验，需要另行设计（例如分块累积）。
7. **z2 不支持 `--resume`**：与 z1 的既有限制同理，采样器状态与 `CvarThresholdState` 尚未纳入
   检查点，`run_training` 已显式拒绝该组合而不是静默产生错误结果。
