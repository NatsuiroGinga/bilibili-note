# RWKV K0 CUDA 融合核实施报告

## 结论

已完成 K0 官方基础 WKV CUDA 前反向融合后端、供应商归档、等价性与速度基准、冻结配置和唯一远程启动器的独立实现。实现不修改当前纯 PyTorch BF16 训练文件，不把 K0 改为 `C=128`，不接入 ChannelMix 或完整官方块。

当前裁决是 **设计可行，实验待证**。本机无 PyTorch/CUDA 目标环境，且本任务被明确禁止访问服务器，因此不宣称 `sm_120` 编译、前向、反向、数值等价、吞吐或显存通过。在资格收据产生之前，当前纯 PyTorch BF16 后端仍是唯一允许的训练路径。

## 实现边界

### Python 后端

`tools/rwkv7_k0_fused_backend.py` 提供：

- `backend_contract()`：返回源码、许可证、形状、dtype、状态精度和目标环境合同。
- `validate_build_environment()`：严格要求 `torch==2.13.0+cu130`、`torch.version.cuda==13.0`、计算能力 `(12,0)`、BF16、`nvcc`、`ninja` 和 C++ 编译器。
- `load_k0_extension(build_root=...)`：仅显式调用时编译，扩展缓存必须位于持久运行根，禁止 `/tmp`。
- `rwkv7_k0_fused(...)`：六输入严格为 `[B,128,112]` 连续 CUDA BF16，只允许 `HEAD_SIZE=16`，输出和六梯度为 BF16，递归状态与累加为 FP32。

官方核接收 `w_raw`，核内完成 soft-clamp。项目融合 TimeMix 明确传入 `w_raw`，没有把当前纯 PyTorch 路径的 `w_clamped` 再传入核，因此不会二次变换。

### 基准工具

`tools/ch3_rwkv7_k0_fused_benchmark.py` 实现五个阶段：

1. `synthetic`：共同种子和六个共同 BF16 量化输入，对照 FP32 算术参考、纯 PyTorch 与 fused 的前向、六输入梯度和一次 AdamW 更新。
2. `lspr23-first-batch`：只读冻结 LSPR23 首个 K0/C00 微批，三份模型共用初始权重，比较 logits、损失、全参梯度和一次优化步。
3. `epoch-pytorch`：纯 PyTorch BF16 完成 LSPR23 C00 一整轮 `1000` 优化步。
4. `epoch-fused`：fused 以相同种子、初始权重、批序列和训练合同完成一整轮。
5. `eligibility`：合并数值、梯度、优化步、验证逐流 AP、选择轮、吞吐和峰值显存门。

工具不枚举 LSPR24 数组，不创建 SwanLab 身份，不保存逐流分数或模型检查点。任一门失败时写出已完成收据并非零退出，资格收据明确写「保留当前纯 PyTorch BF16 后端」。

## 预注册门槛

- BF16 单次舍入单位：`2^-8=0.00390625`。
- 绝对误差门：`0.03125=8u`。
- 相对误差门：`0.02≈5.12u`。
- 混合通过式：`abs(candidate-reference) <= 0.03125 + 0.02*abs(reference)`。
- 验证逐流 AP 绝对差：不超过 `1e-6`，且选中轮完全一致。
- 工程资格：fused 整轮有效流吞吐比不小于 `1.0`，峰值 reserved 显存比不大于 `1.0`。

这些值在目标执行前冻结，不根据待测结果调整。`max_rel` 在近零元素上只作诊断，通过性使用混合门。

## 唯一服务器基准命令

所有新文件同步至冻结项目根，且当前纯 PyTorch BF16 训练释放 GPU 后，服务器只执行：

```bash
cd /root/autodl-tmp/thesis/experiments/llm_probe && bash scripts/remote_launchers/run_ch3_rwkv7_k0_fused_benchmark_v1.sh
```

启动器会依次执行合成公式门、LSPR23 首批门、纯 PyTorch 整轮、fused 整轮和资格汇总，不接受其他正式参数，不自动重试或覆盖旧运行根。

## 预计工作量

- 一次 C++/CUDA 扩展编译和加载。
- 一组 `B=2,T=128,C=112` 合成六输入前反向与优化步。
- 一个 LSPR23 `8×128` K0/C00 真实首批的三后端前反向与优化步。
- 两个整轮后端运行，每个 `1000` 优化步、有效批 `64`、微批 `8`、最多 `8,192` 流位/步；两后端合计最多 `16,384,000` 流位，外加两次 LSPR23 实体不相交验证集逐流 AP。
- 不设人为墙钟上限。因本任务没有目标机实测，且旧 FP32 `4.844` 小时投影来自不同精度和运行合同，不虚构小时数；真实墙钟与剩余时间由启动器日志中的每 `100` 步吞吐收据给出。

## 阻断与后续裁决

1. Context7 没有 PyTorch `2.13` 文档索引，目标 ABI 必须实机验证。
2. 本机项目环境无 `torch`，不能导入新后端或基准工具。
3. 当前纯 PyTorch BF16 运行正占用服务器，基准启动器的并发门和资源门应在资源释放前阻止新运行。
4. 只有 `eligibility.json` 写出 `eligible_for_new_training_identity=true` 后，才能另立 fused 训练配置、运行根和 SwanLab 身份。
5. 任一门失败时不修改当前 K0 数学语义，不放宽预注册误差，不弱化纯 PyTorch 对照，直接保留当前纯 PyTorch BF16 后端。
