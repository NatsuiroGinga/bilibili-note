## 〇之二点七点五、梯度控制器的已确认事实（2026-09-03，读代码＋读收据）

### `c_scaling` 是上限，不是归一化

`tools/ch3_ft_gradient_controller.py:45` 的 `combine_gradients`：

```
c = min(1.0, ‖g_flow‖ / ‖g_rank_projected‖)
combined = g_flow + c * g_rank_projected
```

- 排序梯度**大于**逐流时：压到 `‖g_flow‖`（`c < 1`）
- 排序梯度**小于**逐流时：`c = 1`，**原样保留，绝不放大**

**「归一化到同等幅值」这个说法只在 `c < 1` 的那一侧成立**，另一侧是恒等通过。
历史上曾把它整体读作「归一化」，据此推出的结论须重核。

### C01-half 第 10 轮的逐步统计（`step_count = 1000`）

| 观测量 | 值 | 含义 |
| --- | ---: | --- |
| `c_equal_one_step_count` | **`276`** | 仅 `27.6%` 的步排序梯度未被压制 |
| 推得：被上限卡住的步 | **`724`（`72.4%`）** | 多数步排序梯度超过 `‖g_flow‖` |
| `projection_triggered_step_count` | `277` | `27.7%` 的步两梯度方向冲突，需去反向分量 |
| `c_scaling_median` | `0.0154` | — |
| `grad_norm_flow_median` | `0.3063` | — |
| `grad_norm_rank_median` | `0.0964` | — |

**三者能同时成立，说明排序梯度的逐步分布极度偏斜**：少数步极大（拉低 `c` 的中位数），
多数步很小（使范数中位数低于逐流）。**不要用中位数之间的比值反推 `c`**——
中位数不保持函数关系，`median(c) ≠ min(1, median(‖g_f‖)/median(‖g_r⁺‖))`。

### 判断补底座影响时该看哪个量

**`c_equal_one_step_count` 是核心指标**，不是范数中位数。补底座后 `g_flow → g_base`，
范数变大 ⇒ 上限提高 ⇒ 被卡住的步里排序梯度能过得更多。
**该方向为机制推理，未经实验，不得作为结论**——`g_base` 比 `g_flow` 大多少取决于
`w_e` 与实体梯度量级，二者尚未实测（实测任务因本机死机中断，须挪服务器）。

### 派子代理的一条分工原则（2026-09-03 事故）

**代理负责「把工具写对」，不负责「用工具跑完」。**

事故：PDF 批量转换代理耗 `252k` token、`91` 次工具调用、`35` 分钟，
其中脚本产出有价值，但**大半消耗在「等第 N 批完成」的空转上**——
它把等待后台任务当成了自己的工作，每批完成报告一次。

**根因在简报**：要求它「批量转换 ＋ 固化脚本」，它就把两件事串成
「建脚本 → 用脚本分批转 → 每批等待」。

**正确分工**：代理只交付脚本与一次小样验证；**大批量执行由主代理用后台命令跑**
（`run_in_background`，不占代理额度）。派发时在简报里写死：
「产出脚本并用 3–5 个样本验证即可，**不要用它跑全量**」。

### D. 杀训练后必须两端同时清 `status.json`，否则死锁

守护的判定逻辑：`state == "finished"` 记完成；**`state` 为空才启动**；

**处置**：本机与服务器的 `status.json` **同时**改名保留
（如 `status.stale-killed-<时刻>.json`），再等守护接管。

### L2. 做「改动前后逐位等价」检查必须先固定 RNG，否则必然假阳性

2026-09-03 实测事故：验证 `training_step` 的关闭路径是否逐位等价时，
首次结果为**失败**，`max_abs_diff ≈ 0.109`。**根因不是代码，是测试方法**——
脚本没重置全局 dropout 的随机数状态，而骨干带
`attention_dropout = 0.2`、`ffn_dropout = 0.1`，两次前向的 dropout 掩码不同，
结果当然对不上。重置 RNG 后结论反转为**完全通过**（53 个参数 `.grad` 全部 `torch.equal`）。

**规则**：凡做改动前后的逐位比较（`torch.equal` 类断言），**必须在每次前向前重置
全局 RNG 到同一状态**，否则任何含 dropout／随机增强的模型都会给出假阳性失败。
看到「逐位等价失败」时，**先查 RNG 是否固定，再怀疑代码**。

### L3. 实体级 BCE 的两条已知待办（2026-09-03 任务 2 遗留）

1. **`entity_bce` 与 `entity_memory` 同时启用会被静默忽略**，未加互斥校验。
   当前四份生产配置都不触发，**但阶段 B 若同时启用两者需先补校验**。
   （`entity_bce` 与 `entity_ranking` 同开是阶段 B 的**预期用法**，不应拦。）
2. **实体级 BCE 按「微批」粒度计算，不是整个有效批**——这是对计划文本的字面实现。
   **该口径直接影响权重标定**：任务 3 要用 `‖∇L_flow‖` 与 `‖∇L_entity‖` 的量级比
   定权重，两者若统计粒度不同，比值就没有意义。**标定前须先确认两项的归一化口径一致。**

### L4. 实体级 BCE 的 `w_e = 1.0` 实际不是等权，是 `1/128` 量级

**2026-09-03 查实**：实体级 BCE 被累加器额外乘了 `M / N_flow`
（`neural_precision_runtime.py:461` 按有效流数归一），而实体项本身**已经是逐实体均值**。

当前配置 `M = 1`、`N_flow ≤ 8192`、批内实体 `≤ 64`，
故写 `w_e = 1.0` **实际被压到约 `1/128`**。

**标定权重前必须先对齐归一化口径**，否则用 `‖∇L_flow‖ / ‖∇L_entity‖` 定出的值
会差两个数量级。这条精确化了 L3.2 的「口径不同」。

### L5. `micro_batch_sequences` 不在科学身份里——已知缺陷

它只在 `runtime_projection`，不在 `science_projection`。配合 L4 的归一化因子
与非线性 top-k 聚合，**两次只改微批大小的运行会优化不同的目标，
却共享同一个 `science_identity_sha256`**。

身份哈希本应保证「同哈希 = 同科学定义」，此处不成立。
**改微批时不要依赖哈希相同就认为科学等价。** 修法二选一（未裁决）：
把微批参数移进 `science_projection`（改动小，但把运行参数升格为科学参数），
或改并入项系数使损失对微批不变（彻底，但要改归一化逻辑）。

### L6. 优化器确认为 `torch.optim.AdamW`，且原论文明确排除调度器

- **实现**：`ch3_ft_transformer_field_token_protocol_a.py:3139`，只传 `lr` 与
  `weight_decay`，`eps`／`betas` 取 PyTorch 默认。这关闭了多目标梯度冲突调研 1.5 节
  列为未决的限定条件，并据此把候选 4（DB-MTL 全局尺度 `min→max`）降为低优先级
  ——AdamW 的逐坐标二阶矩会吸收常数正缩放。
- **原论文（Gorishniy 2021）明确不用调度器**：物理页 5「do not employ…
  learning rate warmup, learning rate decay…」，物理页 6「We do not apply
  learning rate schedules」。**这是为隔离架构贡献的方法论选择，不是遗漏。**
  `lr = 1e-4`／`wd = 1e-5` 见 Table 12（物理页 18）；
  调参空间 `LogUniform[1e-5, 1e-3]` 见 Table 13，几何中位恰为 `1e-4`，
  代码注释「已知，不是笔误」经查属实。
- **六篇后续工作中五篇无调度器**（XTab、TabM、TabTransformer、Matérn-KAN、TabReD），
  唯一用衰减的 electronics-IoT 未披露机制、无消融、结构已偏离默认。
- **后期震荡不可归因于缺少 LR 衰减**：唯一报告过 FT-Transformer 训练震荡的文献
  （Matérn-KAN）归因为**数据集规模过小**。文献只能证明「不加调度器不反常」，
  **因果需本课题自己做加/不加衰减的对照实验**。
- **范围限定**：「无调度器」只对 FT-Transformer 这条线成立。
  仓库内 DistilBERT 基线、RWKV 筛选、GRANDE **确有使用**
  `CosineAnnealingLR`／`LambdaLR`，不要误读为本课题整体排斥调度器。

- **「四格全即时」裁决（2026-08-31，主代理，依据见[四格编译路径统一](2026-08-31-四格编译路径统一/)）**：原条款要求「共同逐流骨干统一走编译路径」，实测证明该要求**无法与「四格同路径」同时成立**——C00／C01 的骨干是零断裂全编译，而 C10／C11 是编译入口加 4 处断裂回退（断点已精确定位到 `ch3_ft_causal_entity_memory.py:334-337`，全部为动态布尔索引）。即 `z1` 这一维不只改变数学，还改变可编译性，`C10 − C00` 的差里混入「记忆模块导致 15 次断裂、算子融合被切碎」，**机制效应与编译效应无法分离，2×2 消融因此失效**。

- **「同一 GPU」要求已于 2026-09-01 由用户放宽**：实验室设备动态切换显卡，**只保证 32 GiB 显存**，型号不可控。故第 33 行硬门禁中的「同一 GPU」改为**只要求显存容量满足**，型号允许跨臂不同。
  **随附的科学处置（不额外花 GPU 时间）**：其一，每臂收据仍记录实际 GPU 型号，`execution_environment` 字段与 `--compare` 保持不变；其二，四格跑完后核对是否真的跨了型号，未跨则无影响；其三，跨了型号时须评估卡间数值差异对结论的威胁——已知同类量级参照是 compile 与 eager 的 logits 差 `8.94e-07` 即可使源年实体 AP 移动 `0.0015`（验证集仅 `20` 个正实体，排序易翻转），若交互项 `I` 接近该量级则在正文标注该风险；其四，确需量化时补一次零训练的跨卡前向对比（同检查点、两种卡、比 logits 与实体 AP），**不预先做**。

- **矩阵乘精度（2026-09-01 已冻结：不启用，取 `highest`）**：原条款要求「第一格启动前裁决并冻结」，本轮在 C00 重跑启动前完成该裁决。**裁决为不启用 TF32 类快速路径，`float32_matmul_precision = "highest"`，四格一致，不得中途改变。** 理由：该设置改变 float32 矩阵乘的舍入与训练轨迹，启用需额外的构造等价性检查与吞吐实测（本轮未做），在四格已统一即时执行的前提下保守取值与该方向一致。实现上由 `resolve_runtime` **显式调用** `torch.set_float32_matmul_precision`，而非依赖 PyTorch 默认——默认值可能随版本变化，显式设置才能保证四格跨时间跨机器取到同一条数值路径；实际生效值由执行路径收据的 `float32_matmul_precision` 字段记录。依据与措辞见配置 `ch3-ft-c00-bare-eager-formal-v2.json` 的 `float32_matmul_precision_evidence`。不得用 LSPR24 结果反向决定是否启用。
