### 抽样方案与验证（**已实测，非估算**）

**方案**：`{fraction: 0.2, seed: 42, positive_fraction: 1.0}`
——正实体 `239` 全保留，负实体抽 `20%`（`30,088`），共 `30,327` 实体。

## 〇之二点七点五、梯度控制器（三条结论，全文已归档）

1. **`c = min(1, ‖g_flow‖/‖g_rank⁺‖)` 是上限不是归一化**：排序梯度小于逐流时 `c = 1`
   恒等通过，**绝不放大**。「归一化到同等幅值」只在 `c < 1` 那一侧成立。
2. **C01-half 第 10 轮实测**（`step_count = 1000`）：`c_equal_one_step_count = 276`，
   即 **`72.4%` 的步排序梯度被压到 `‖g_flow‖`**；`projection_triggered_step_count = 277`。
   **不要用范数中位数之间的比值反推 `c`**——中位数不保持函数关系。
3. **判断补底座影响时看 `c_equal_one_step_count`，不看范数中位数**；
   `g_base` 比 `g_flow` 大多少**尚未实测**，该方向只是机制推理，不得作为结论。

### 派子代理的一条分工原则（2026-09-03 事故）

**代理负责「把工具写对」，不负责「用工具跑完」。**

事故：PDF 批量转换代理耗 `252k` token、`91` 次工具调用、`35` 分钟，
其中脚本产出有价值，但**大半消耗在「等第 N 批完成」的空转上**——
它把等待后台任务当成了自己的工作，每批完成报告一次。

**根因在简报**：要求它「批量转换 ＋ 固化脚本」，它就把两件事串成
「建脚本 → 用脚本分批转 → 每批等待」。

**正确分工**：代理只交付脚本与一次小样验证；**大批量执行由主代理用后台命令跑**
（`run_in_background`，不占代理额度）。派发时在简报里写死：
「产出脚本并用 3–5 个样本验证即可，**不要用它跑全量**」。

换端点形态属正常排障，换服务商才是禁止项。两种写法都见 B 条。

### B. 连服务器的固定套路（DNS 被本机代理劫持，必须 DoH 绕过）

凭据键见 `RWKV路线总控.md` 第五节。每次重新解析 IP，**不要写死**（容器重启会变）。

**写法一（2026-09-03 实测可用，优先用这条）**——域名式端点，**经系统代理**：

```
IP=$(curl -s --max-time 15 \
  "https://cloudflare-dns.com/dns-query?name=<服务器域名>&type=A" \
  -H 'accept: application/dns-json' | grep -o '"data":"[0-9.]*"' | tail -1 | grep -o '[0-9.]*')
```

**写法二（旧写法，2026-09-03 实测报 `SSL_ERROR_SYSCALL`，仅在代理配置改变后才可能恢复）**：

```
IP=$(curl -s --noproxy '*' --max-time 15 \
  "https://1.1.1.1/dns-query?name=<服务器域名>&type=A" \
  -H 'accept: application/dns-json' | grep -o '"data":"[0-9.]*"' | tail -1 | grep -o '[0-9.]*')
```

**DoH 端点形态会随本机代理配置漂移，两条都不是永久事实。**
两条都取不到时先读 `curl` 的 stderr，再用 B0 条的回退 IP，
**不要据此判定「服务器不可达」**。

export GPU_PWD_ACTIVE='<从凭据来源取>'

### D. 杀训练后必须两端同时清 `status.json`，否则死锁

守护的判定逻辑：`state == "finished"` 记完成；**`state` 为空才启动**；
读到 `"running"` 就 `break`，认为还在跑。

更糟的是：**本机回传守护是 push**，每 300 秒把本机旧副本推回服务器，
**只清服务器那份会被它推回来**。2026-09-03 因此 GPU 空转 20 分钟。

**处置**：本机与服务器的 `status.json` **同时**改名保留
（如 `status.stale-killed-<时刻>.json`），再等守护接管。

### L2. 做「改动前后逐位等价」检查必须先固定 RNG，否则必然假阳性

2026-09-03 实测事故：验证 `training_step` 的关闭路径是否逐位等价时，
首次结果为**失败**，`max_abs_diff ≈ 0.109`。**根因不是代码，是测试方法**——
脚本没重置全局 dropout 的随机数状态，而骨干带
`attention_dropout = 0.2`、`ffn_dropout = 0.1`，两次前向的 dropout 掩码不同，
结果当然对不上。重置 RNG 后结论反转为**完全通过**（53 个参数 `.grad` 全部 `torch.equal`）。

**规则**：凡做改动前后的逐位比较（`torch.equal` 类断言），**必须在每次前向前重置
全局 RNG 到同一状态**，否则任何含 dropout／随机增强的模型都会给出假阳性失败。
看到「逐位等价失败」时，**先查 RNG 是否固定，再怀疑代码**。

### L4. 实体级 BCE 的 `w_e = 1.0` 实际不是等权，是 `1/128` 量级

**2026-09-03 查实**：实体级 BCE 被累加器额外乘了 `M / N_flow`
（`neural_precision_runtime.py:461` 按有效流数归一），而实体项本身**已经是逐实体均值**。

当前配置 `M = 1`、`N_flow ≤ 8192`、批内实体 `≤ 64`，
故写 `w_e = 1.0` **实际被压到约 `1/128`**。

**标定权重前必须先对齐归一化口径**，否则用 `‖∇L_flow‖ / ‖∇L_entity‖` 定出的值
会差两个数量级。这条精确化了 L3.2 的「口径不同」。

### L5. `micro_batch_sequences` 不在科学身份里——已知缺陷

它只在 `runtime_projection`，不在 `science_projection`。配合 L4 的归一化因子
与非线性 top-k 聚合，**两次只改微批大小的运行会优化不同的目标，
却共享同一个 `science_identity_sha256`**。

身份哈希本应保证「同哈希 = 同科学定义」，此处不成立。
**改微批时不要依赖哈希相同就认为科学等价。** 修法二选一（未裁决）：
把微批参数移进 `science_projection`（改动小，但把运行参数升格为科学参数），
或改并入项系数使损失对微批不变（彻底，但要改归一化逻辑）。

### L6. 优化器确认为 `torch.optim.AdamW`，且原论文明确排除调度器

- **实现**：`ch3_ft_transformer_field_token_protocol_a.py:3139`，只传 `lr` 与

  ——AdamW 的逐坐标二阶矩会吸收常数正缩放。
- **原论文（Gorishniy 2021）明确不用调度器**：物理页 5「do not employ…
  learning rate warmup, learning rate decay…」，物理页 6「We do not apply
  learning rate schedules」。**这是为隔离架构贡献的方法论选择，不是遗漏。**
  `lr = 1e-4`／`wd = 1e-5` 见 Table 12（物理页 18）；
  调参空间 `LogUniform[1e-5, 1e-3]` 见 Table 13，几何中位恰为 `1e-4`，
  代码注释「已知，不是笔误」经查属实。

  （Matérn-KAN）归因为**数据集规模过小**。文献只能证明「不加调度器不反常」，
  **因果需本课题自己做加/不加衰减的对照实验**。
- **范围限定**：「无调度器」只对 FT-Transformer 这条线成立。
