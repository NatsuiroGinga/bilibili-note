## 一、实现摘要

### 1.1 代码结构与复用

- 新增 `tools/ch3_backbone_models.py`：从 `tools/ch3_backbone_protocolA_v2.py` 抽取
  `Model`/`RWKV7TimeMix`/`rwkv7_op`/`npar_formula`/`hid_of`/`lp_pool`/
  `split_lspr23_entity_disjoint` 为纯定义模块（无副作用，import 安全），逻辑与原实现
  逐字等价，只是换了文件位置。协议 A 与协议 B 现共用同一份模型定义，不是两份拷贝。
- 修改 `tools/ch3_backbone_protocolA_v2.py`：改为从共享模块 import 上述定义；
  数据切分改为调用 `split_lspr23_entity_disjoint`；`D` 从运行时赋值改为从共享模块导入后
  用断言核验。全部改动经逐行核对确认与原实现行为等价，未改变任何训练/选择/评价语义。
  本次改动**不影响**协议 A 已产出的历史结果（历史结果已落盘，本次只改代码结构不重跑）。
- 新增 `tools/ch3_backbone_protocolB_2x2_rerun.py`：协议 B 主体实现。
  LSPR24 实体级评价复用 `tools/ch3_full_mlp_complete_entity_lp_protocol_a_q0.py` 的
  `build_flow_entity` / `entity_scores` / `evaluate_entity_branch`（该文件已被
  `..._q0_bf16.py` 验证为可安全 import 的纯函数库）。
- 精度：`configs/neural-precision-profiles-v1.json` 的默认 profile
  `cuda-bf16-amp-fp32-sensitive-v1`，经 `tools/neural_precision_runtime.py` 的
  `autocast_context` / `fp32_island` / `validate_model_optimizer_fp32` 接入；
  未使用 `EffectiveBatchAccumulator`（单微批即完整有效批，累积步数恒为 1 时该类是恒等操作），
  服务器实测该 profile 装载正常（`compute_dtype=bfloat16 autocast=True grad_scaler=False`）。

### 1.2 两项预注册修订的实现

- **修订一（选轮指标）**：`val_metrics(net, lp)` 每 epoch 同时计算 LSPR23 验证实体 AP
  （选择信号）与验证逐流 AP（仅记录）；选择规则为「取实体 AP 最大的 epoch，并列取最早，
  不早停」，与原协议 A 的「取 epoch」语义相同，只换了比较的指标。
- **修订二（学习率网格）**：`LR_GRID = (2e-3, 3.162277660168379e-4)`（冻结数值，逐字抄自合同）。
  只在 C00 上训练两个候选并比较验证实体 AP，胜出值冻结后复制为正式格 C00（不重复训练），
  C01/C10/C11 用冻结胜出 lr 各训练一次。

### 1.3 判据实现（与合同一致，未改动）

主口径实体 AP 取 `evaluate_entity_branch` 返回的 `entity_average_precision`
（lp 格用 Lp 池化、非 lp 格退化为 max，与协议 A 的 `e_lp` 字段语义一致）：

```
crit_elp   = C01 > C00
crit_cpa   = C10 > C00
crit_joint = C11 >= max(C01, C10)
passed = crit_elp and crit_cpa and crit_joint
```

## 二、与合同/协调方指令的偏离披露（如实记录，不隐藏）

### 2.1 未采纳协调方「transformer 跳过 lr-select」的原始建议（架构不匹配）

协调方在实施中途转发「另一代理已核」的建议：transformer 骨干可直接冻结 `lr=0.002`、
跳过两候选比较，依据是 `2026-08-17-第三章实验台账.md:316` 显示 transformer 择优 `lr=0.002`。

**核验结果（本代理独立复核，未采纳原始理由）**：该台账行引用的是「**等参数基线
Transformer**」——83,105 参数，Leoste 2025 同类架构的等参数改造（台账
`2026-08-17-第三章实验台账.md` 第 353-357 行明确区分「跨基座 cnn 骨干」与
「等参数基线卷积网络」是两个不同架构；同表格结构下 GRU/Transformer 行同理），
**不是**本次重跑的「跨基座 transformer」（90,631 参数，
`ch3_backbone_models.TR_D=77/TR_HEADS=7`）。证据模型不匹配，不能直接套用其 lr 结论，
故未按该建议跳过 transformer 的 lr-select——初次实现按合同对两骨干同规则跑满 lr-select。

### 2.2 采纳协调方「GPU 窗口紧迫」的紧急操作指令（transformer 用 --fixed-lr 0.002）

实现完成、真实数据冒烟验证通过后，协调方发来第二条紧急指令：**服务器 GPU 仅余约 2 小时
可用**，要求以训练上卡为最优先，transformer 直接用 `lr=0.002` 冻结进入四格训练（不做
两候选比较），gru 仍跑完整 lr-select。这是在资源硬约束下的操作决策，与 2.1 节的证据
不匹配问题无关（不是重新采信原来的理由，而是不同的、独立的资源紧迫性理由）。

**已采纳并执行**，新增 `--fixed-lr` CLI 开关：跳过两候选比较，直接把该值当作
`WINNER_LR`，`lr_select_frozen.json` 如实记录 `mode=directive_fixed_skip_comparison`
及原因，**不冒充**已完成的两候选实体 AP 比较。C00 仍然完整训练 20 epoch（只是省去了
在 `3.162277660168379e-4` 上再训练一次 C00 的比较成本），不是「零训练成本」。

**代价（不因阻塞而消失，正式定论时仍需处理）**：transformer 骨干的判据结果将建立在
**单一 lr（协议 A 原硬编码值 2e-3）**上，未经修订二的实际两候选比较验证；若该骨干判据
不通过，无法排除「换一个 lr 是否会通过」这一可能性。

### 2.3 实现阶段发现并修复的 bug（第一轮，训练期间发现，代码层面已修复）

`val_metrics()` 最初对 `lp=False` 的格把实体级读出用的 `p_value=None`
同时当作 `best["p"]`（用于记录与目标评价阶段回载校验）返回，导致目标评价阶段
`assert abs(net.p.item() - SEL[cid]["best"]["p"]) < 1e-9` 对 C00/C10 必然
`TypeError`（`float` 减 `None`）。发现于两进程仍在训练阶段（尚未到达目标评价）时，
已修复（拆分 `p_actual`/`p_readout` 两个值，`p_actual` 恒为真实 float，提交 `f68eb47`）
并重启，服务器实测：依赖幂等断点续训，重启后已完成的格（transformer-C00 及 gru 的
lr0-C00）直接跳过、在训练中的格（transformer-C01、gru-lr1-C00）从最近 epoch 检查点继续，
基本零训练时间损失。

### 2.4 第一轮修复未覆盖历史脏数据，两进程仍崩溃（第二轮，服务器实测暴露）

第一轮修复只改了**代码**，没有改写**已经用旧代码写到磁盘上的检查点**——
transformer-C00 与 gru 的 lr0-C00 在旧代码下已完整训练完成并落盘，
其 `selected.pt` 里的 `best["p"]` 已经是 `None`。两进程重启后各自完成剩余三格训练、
进入目标评价阶段，**在服务器上实测各自崩溃于同一处断言**
（`assert abs(p - SEL[cid]["best"]["p"]) < 1e-9`，`TypeError: unsupported operand
type(s) for -: 'float' and 'NoneType'`），崩溃时间：transformer 约 20:36:35，
gru 约 20:55:08（本机时钟）。

已第二轮修复（提交 `70e791e`）：新增 `recovered_p()` 迁移垫片——记录里的 `p` 若为历史
遗留的 `None`，从该记录 `state`（模型 state_dict）的 `p_log` 参数按 `Model.p` 属性同一
公式重算真实 p；`p` 本身非 `None` 时是恒等操作。应用于四处历史检查点读取点：
lr-select 候选恢复、C00 直接加载、cells 格恢复、`train_and_select` 的 inflight 恢复路径。
**该修复未在服务器上运行验证**（见下节阻塞），只本地 `py_compile` 通过、逻辑已复核。

## 四、阻塞：GPU 服务器不可达

2026-08-27 21 时许起，到本报告完成时（本机时钟约 21:30 后）连续多次尝试连接服务器
均失败。诊断：

```
ssh -vvv ... root@connect.westc.seetacloud.com -p 44030 ...
debug1: Connecting to connect.westc.seetacloud.com [36.103.198.206] port 44030.
debug1: connect to address 36.103.198.206 port 44030: Connection refused
```

`Connection refused` 发生在 TCP 连接建立阶段（不是认证失败、不是本地代理故障——
本机通用网络出口经同一代理测试正常），即目标主机的该端口已不再监听。结合协调方此前
明确告知「GPU 仅余约 2 小时可用」，**最可能的原因是 GPU 租用窗口到期、实例被云平台
停止或回收**（AutoDL/SeetaCloud 一类按量计费实例停止后通常会关闭或重新映射 SSH
端口）。本代理没有该云实例的控制台访问权限，无法自行重启或重新映射端口，
**这是需要用户或协调方介入的基础设施问题，不是代码问题**。

若实例只是被停止（未被销毁），磁盘数据通常不会丢失，本报告第三节列出的全部检查点、
`selection_frozen.json` 以及本次两轮 bug 修复后的代码，重新拉起同一实例后应可直接
读取或以幂等断点续训方式继续，预计几分钟内即可完成剩余的目标评价并产出判据。
若实例已被销毁（磁盘一并回收），则需要在新实例上从头重跑——由于每格训练仅需
约 3–7 分钟，全部重跑预计仍在 1 小时以内。**两种情形都需要用户确认服务器状态后
再继续，本代理不擅自假设并重跑。**
