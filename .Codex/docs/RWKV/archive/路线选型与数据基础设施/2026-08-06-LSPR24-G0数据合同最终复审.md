## 1. 总体结论

## 2. 严重问题

### S1：受限封存没有冻结密码学记录格式和故障时的原子发布，原 `S4` 仍未关闭

**证据**：合同第 447—456 行规定 `lspr24-sealer-v2`、逐记录 AES-256-GCM、禁止明文临时文件和访问日志；第 574 行的 `G0-A12` 只检查授权访问计数、敏感输出计数、崩溃转储和“加密侧车已验证”。合同没有定义每条记录的 nonce 生成与唯一性、nonce／认证标签／密钥版本的存储格式、重复 nonce 拒绝条件，也没有规定磁盘写满、加密失败、日志写入失败、进程崩溃或原子重命名失败时如何撤销半成品。修订记录要求“受限封存独立故障注入复审”，但这一条件没有进入第 10 节或 `G0-A12` 的机器谓词。

**为什么严重**：同一密钥下复用 AES-GCM nonce 会破坏最终标签的机密性与认证安全；中途失败留下的部分明文侧车、未认证密文、已公开清单或不完整访问日志，会使“最终测试不可见”在成功路径之外失效。当前 `encrypted_final_sidecar_verified=true` 和 `authorized_access_count>=1` 仍可在没有证明 nonce 唯一或故障后无残留的情况下通过。

**必须修订**：

1. 冻结逐记录容器格式，至少绑定 `key_id`、96 位 nonce、密文、认证标签和现有 AAD；要求同一 `key_id` 下 nonce 全局唯一，并把重复 nonce 数为 0、全记录认证通过写入 `G0-A12`。
2. 冻结失败关闭发布协议：先在受限目录写入仅受限可见的暂存对象，完成行数、哈希、认证标签、权限和访问日志核验后原子发布；任一步失败必须使正式路径不存在或保持上一完整版本，删除残留，并把状态固定为 `NOT_READY` 或 `FAIL`。
3. 冻结访问日志完整性机制，例如哈希链加签或受控追加存储；不能只用“日志存在且不可篡改”的自然语言和访问者二进制哈希代替证明。
4. 为打开标签、解码、加密、磁盘写满、权限错误、日志写失败、校验失败、重命名失败和进程中断建立故障注入矩阵；`G0-A12` 必须要求全部故障场景均以失败关闭方式退出、敏感输出为 0、残留为 0。
5. 把授权调用清单的调用次数、命令／配置哈希和目的冻结为精确集合；`authorized_access_count>=1` 不能允许未预注册的重复授权调用。

## 3. 重要问题

### I1：正事件构造与分区／窗口隔离的先后顺序互相矛盾

**证据**：合同第 268 行要求“会话隔离和窗口隔离必须先于标签事件构造”；第 395—401 行又要求在“应用分区隔离前”的有效代表流上构造临时端点窗口和跨边界正事件，以避免用 `split_name` 制造零交叉。

**影响**：若先删除边界窗口再构造事件，真实跨界事件可能被截成两段或直接消失，`visible_true_event_crossings==0` 会成为定义上的零；若完全在隔离前构造，又会把本应由无标签会话规则整体隔离的成员带入事件。两种实现都能声称符合合同不同段落。

**必须修订**：冻结唯一顺序并在收据中保存每步输入／输出哈希。建议顺序为：时间有效性与去重 → 无标签会话分量及跨界会话隔离 → 在尚未按 `split_name` 拆分、尚未删除边界守卫窗的可见全时间轴构造正事件并审计跨界 → 通过后应用窗口归区和 32 窗守卫 → 生成评价成员。同步改写第 268 行、第 395 行和 `G0-A05`。

### I2：无标签去重会静默选择冲突标签，且关键规范值仍未唯一化

**证据**：合同第 123—131 行明确从 `content_digest` 排除全部 `Label*`，相同 `business_key/content_digest` 的物理行只保留最小 `source_row_index`；第 344—351 行只一般性要求标签审计，没有规定同一无标签重复等价类中多个标签不一致时的处理或机器计数。这样两条非标签内容相同但 `Label` 不同的行会被视为完全重复，代表行的物理顺序会决定最终标签。此外，第 119 行使用未定义的 `canonical_Flow_ID`，`canonical_l4_protocol` 的唯一源列和值映射仍推迟到运行期字段清单；两者都会改变去重类和会话连通分量。

**影响**：实现可以在不触发 `duplicate_conflict_quarantine` 的情况下丢掉冲突标签，导致窗口标签和事件数依赖物理行顺序；Rust 与 Python 也可能对 `Flow ID` 或协议别名采取不同规范化规则。

**必须修订**：

1. 无标签去重时保留每个等价类的完整 `source_record_id` 成员清单；开发标签解封后对类内 `Label/Label_src/Label_dst` 逐项审计。
2. 冻结标签冲突的唯一处置：整类隔离或直接 `NO-GO`，不得选择最小行标签、取多数或取最大值；增加冲突类数量与成员哈希的机器谓词。
3. 冻结 `Flow ID` 的源类型与字节规范化规则，以及四层协议的唯一源列、允许值映射、未知值和列间冲突处理；这些规则必须在 Rust 实现前进入合同，不应留给运行时清单改变会话语义。

### I3：`G0-A13` 仍由未定义的汇总布尔值裁决，不能唯一复算

**证据**：合同第 575 行把 `search_budget_manifest_complete`、`all_trial_counts_within_budget`、`all_retry_reasons_allowed` 和 `required_baselines_present` 直接作为真值输入，但没有给出这些布尔值对应的模式字段、精确必需基线集合或复算表达式。第 597 行又允许“及其他登记基线”，使 `required_baselines_present` 的闭集不明确。当前也未区分 G0 启动前的计划试验数与运行后的实际试验数；零次实际运行可能满足“均在预算内”。

**影响**：生产者可以先把四个汇总字段写成 `true`，而审查者无法仅凭收据独立复算；`C0-P/C0-C/B-GRN` 虽已写入设计，却未被 `G0-A13` 的显式集合和逐模型资源字段机器绑定。总状态归约公式本身唯一，但输入状态仍可能失真。

**必须修订**：列出固定必需模型标识集合，明确 `C0-P/C0-C/B-GRN` 的适用关系；把每模型计划配置数、配置清单哈希、更新数、检查点次数、重试枚举、参数差、计算差和状态字节差作为原始字段，由门禁程序复算，不接受生产者直接给出的汇总布尔值。G0 启动前只裁决冻结计划预算，运行后实际消耗另设不可覆盖的执行收据。
