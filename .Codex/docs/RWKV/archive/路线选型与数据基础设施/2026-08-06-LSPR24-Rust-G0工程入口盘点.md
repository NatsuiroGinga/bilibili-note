## 5. 2.77 GB Parquet 的流式时间读取

本次只读元数据检查得到：

| 项目 | 值 |
| --- | --- |
| 文件 | `thesis/experiments/llm_probe/data/raw/lspr24-v1/lspr24_v2.parquet` |
| 总行数 | `20,227,356` |
| 行组数 | `21` |
| 单行组行数范围 | `536,195` 至 `1,095,122` |
| `mTimestampStart` | 可空 `int64`，叶列索引 6 |
| `mTimestampLast` | 可空 `int64`，叶列索引 7 |
| 两列压缩列块合计 | `280,221,035` 字节 |

因此不能按 2.77 GB 整表读取，也不能把时间列收集为一个全局 Arrow 表。推荐流程如下：

1. 使用 `ParquetRecordBatchReaderBuilder<File>` 打开文件，按精确字段名解析叶列索引并断言两列都是可空 `Int64`；索引 6/7 只用于本次元数据证据，生产代码不得硬编码位置。
2. 使用 `ProjectionMask::leaves` 只投影合同允许的第一遍列，时间审计的最小投影只含两列；使用固定资源参数 `with_batch_size(65_536)`，不加行过滤器，不调用并行迭代器。
3. 默认行组顺序为 `0..21`。在过滤、隔离或去重之前为每个物理行分配 `source_row_index`；顺序读取时使用单调全局计数器，并在结束时断言计数等于 Parquet 元数据行数。
4. 若以后按行组并行，先从元数据计算每组前缀行数，令 `source_row_index = row_group_prefix + row_in_group`；每组只写独立、带行组编号的排序段，最后执行确定性归并。首个 G0-A 实现不建议并行读取。
5. Parquet 原始顺序只定义 `source_row_index`，不等于合同稳定顺序。通过时间合法性和端点归属后，将完整合同稳定键写入有界排序段；每段按完整键排序，再用最小堆做多路归并。完整键包含最终兜底的 `source_row_index`，不能只按时间排序。
6. 排序段应写入本次新建的 `.partial/work/`，文件名固定为 `run-000000.parquet` 等零填充编号；正式输出成功后原子发布，失败只清理本次目录。标签阶段不得把明文标签写入普通排序段或日志。

两列是无单位的普通 `int64`，Arrow 模式本身不能证明时间单位。`time.rs` 必须使用最终 G0 合同给出的单位与有效性规则，禁止从数值范围猜测秒、毫秒、微秒或纳秒。

稳定性必须由测试证明：同一人工夹具使用批大小 1、3、65,536，使用单行组和多行组布局，得到的 `source_row_index`、完整稳定顺序、行哈希和数据集哈希必须完全一致。Parquet 容器字节哈希不作为上述一致性的替代。
