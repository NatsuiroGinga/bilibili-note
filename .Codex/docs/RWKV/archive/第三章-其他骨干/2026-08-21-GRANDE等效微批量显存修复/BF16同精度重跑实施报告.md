# GRANDE G-A/G-B 同精度 BF16 重跑实施报告

## 一、裁决与运行身份

- 用户于 2026-08-21 明确授权使用 BF16 重新运行 GRANDE。
- 独立运行身份：`ch3-grande-c00-protocolA-source-q0-seed42-v1-bf16-v1`。
- 独立输出根：`runs/diagnostics/ch3-grande-c00-protocolA-source-q0-seed42-v1-bf16-v1/`。
- 独立持久会话：`ch3-grande-pa-bf16-s42-v1`。
- 本运行不复用 FP32 G-A；G-A 与 G-B 均从头使用同一精度档案训练，随后才允许科学选优。
- 本轮不访问服务器、不启动实验，当前结论为工程实现就绪、实验待证。

## 二、冻结精度档案

精度档案标识为 `cuda-bf16-amp-fp32-sensitive-v1`：

- CUDA 大型路由张量与 `einsum` 允许在 `torch.amp.autocast` 下使用 BF16。
- 模型参数和 Adam 优化器状态保持 FP32。
- 分裂选择 softmax、树权重 softmax、随机失活后的树权重归一化和最终树输出求和保持 FP32。
- 二元交叉熵的 `sum`、除以原始优化步全部有效流数的归一化及损失诊断保持 FP32。
- 路由熵的截断与对数、CPA/ELP 可达性诊断、验证和指标计算保持 FP32。
- 不使用 `GradScaler`。
- G-A 与 G-B 必须逐结构记录相同的精度档案；任一结构记录不符，启动器最终输出门失败。

用户授权字段固定为：

```text
user_authorized_bf16_for_runtime=true
authorization_reference=2026-08-21-user-explicit-bf16-rerun-decision
selection_metrics_used_for_precision_choice=false
```

精度切换来自本轮用户明确运行裁决，不读取验证 AP、实体 AP 或目标年标签，也不要求 FP32 微批再次显存溢出。

## 三、训练与显存合同

- 两个结构均保持原模型深度、树数、随机失活和优化配方。
- 原始有效批仍为 64 条序列，每条最多 128 个流。
- 每个原始优化步固定一次序列采样并确定全部有效流数。
- 流微批上限继续固定为 2048，不按 BF16 指标、吞吐或最终结果调整。
- 每微批执行带类别权重的 `BCE sum / total_valid_flows` 并反向传播。
- 每个原始优化步只执行一次清梯度、一次梯度裁剪和一次优化器更新。
- G-A 和 G-B 都训练 20 周期，每周期 1000 个原始优化步；无时长上限。
- 优化步起点原子保存模型、优化器、最佳模型、历史、计数、采样位置和随机数状态；微批中断时重放整个原始优化步，不保存半梯度。

## 四、激活检查点边界

- 当前 BF16 正式配置关闭激活检查点。
- 只有本独立 BF16 微批运行仍出现显存溢出时，才允许另立显式工程分支并使用 `use_reentrant=False`。
- 当前运行不静默开启激活检查点，也不把它与 BF16 同时作为未登记变量切换。

## 六、静态验证与边界

- `py_compile`：共享工具与 vendor 核心通过。
- 导入检查：`BF16_RUN_ID` 与 `BF16_PRECISION_PROFILE` 可见，结果为 `BF16_IMPORT_OK`。
- `--help`：命令入口解析通过。
- `--validate-config`：独立 BF16 配置通过。
- `bash -n`：共享启动器和 BF16 包装启动器通过。
- 配置机械核验：独立身份、禁止迁移、用户授权、共享精度档案、2048 流微批、64 序列、20×1000 步均通过。
- 损失归一化静态核验：完整均值梯度与分块 `sum / total_valid_flows` 累积梯度一致。
- vendor 清单：核心文件 SHA-256 与清单一致。
- 本地环境没有 PyTorch，因此不得把本地导入成功误写成真实 CUDA BF16 前向通过。
- 真实 GPU 兼容性、峰值显存、吞吐、梯度门与两个结构的科学指标仍须由独立运行原始制品裁决。
- 旧 FP32 失败运行、FP32 G-A 完成制品和 FP32 微批 `rerun1` 均不修改、不覆盖、不混入本次选优。
