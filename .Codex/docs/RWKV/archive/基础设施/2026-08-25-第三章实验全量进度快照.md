## 三、重大发现：`dijk-repro` 缓存不是 raw83 原始数据（必须写进故障预防）

**这是当日最重要的一条，优先级高于任何指标读数。**

### 3.1 结论

`runs/diagnostics/dijk-repro/cache/X23.npy` 与 `X24.npy`
**不是 Dijk 83 字段原值，是 dijk 复现管线自己拟合的标准化特征矩阵**，
也不等于协议 A 的任一候选视图。

### 3.2 LSPR23 上的实测对照【已核】

把缓存 `X23.npy` 与协议 A 冻结 `lspr23-raw83.npy` 逐单元比对，
两者同为 `float32 (16353511, 83)`、**文件字节数相同**：

| 观测 | 数值 |
| --- | --- |
| 有限值不同的单元数 | `1,224,589,881` |
| 只有产品侧非有限（NaN）的单元数 | `18,276,864` |
| 缓存侧非有限单元数 | `0` |
| 与 raw83 的最大绝对差（前 20 万行样本） | `251799984.0` |
| 相对差 `>1e-3` 的单元比例 | `0.913` |

逐列样例（第 0 列 `SrcPort`）：缓存 `-0.3009…`，raw83 `48778.0`，协议 A 候选 A 视图 `0.0932…`。

诊断脚本：`runs/diagnostics/ch3-cuda-rwkv-lspr24-inmemory-descriptive-eval-v1/diagnostics/diagnose_cache_vs_product.py`
与 `diagnose_x23_nature.py`，日志 `diagnose.log`、`diagnose-x23.log`。

### 3.3 为什么这条特别危险

**形状一样（`float32 (16353511, 83)`）、文件字节数一样，肉眼与 `ls` 都看不出差别。**
把它喂进按 `raw83 → 候选A → 候选B` 拟合的模型，模型会看到训练时从未见过的输入分布，
**结果无效，却看起来完全正常**——不报错、不产生非有限值、指标也在合理量级。

同时确认缓存与协议 A 产品在**流行序上一致**（这正是它容易骗过检查的原因）：
`I23`、`M23` 逐字节相同；`y23` 转 `int8` 后的内容摘要等于源年清单登记的 `label_content_sha256`；
`t23_flow` 只是把同一开始时刻列存成 `float64`（值相同，故文件摘要不同）。

### 3.4 已产生的实际后果

**表格 ResNet 的 LSPR24 评价（提交 `66873dd`）用了该缓存，其结果口径存疑，必须重跑。**

本次已在源码逐行确认该因果链【已核】：

- `tools/ch3_tabular_resnet_lspr24_zero_train_descriptive_eval.py` 第 `321` 行
  `raw = np.load(cache_root / "X24.npy", ...)`，随后在 `build_target_view` 内
  对每个行块调用 `apply_arm(..., arm, a_state, b_state, transformer)`，
  即**把在 raw83 上拟合的候选 A/B 变换叠加到已经标准化过的矩阵上**；
  默认 `--cache-root` 就是 `runs/diagnostics/dijk-repro/cache`（第 `606` 行）。
- 而 ResNet 源年配置 `configs/ch3-tabular-resnet-paper-recipe-protocol-a-seed42-v1.json`
  的 `source_dataset_manifest` 指向共享 Raw83 产品
  `runs/data-prepared/ch3-protocol-a-raw83-shared-v1/generations/source-v1/dataset-manifest.json`。

**训练侧走 raw83、评价侧走标准化缓存 —— 两侧不同源，这是硬缺陷，不是口径分歧。**

### 3.5 CUDA-RWKV 评价代理当场验出并改走正确路径

正确路径是：**直读冻结 Parquet ＋ 内存内重建候选 B 视图，全程零物化。**
从冻结的 `data/raw/lspr24-v1/lspr24_v2.parquet`（`sha256=1d96f0a0…`，`20,227,356` 行、
`21` 行组、`101` 字段）按行组流式读取，逐批
`_canonicalize_raw83 → _transform_a → _transform_b`，结果只驻内存（约 `6.7 GiB`）。

该代理做了三道证据【已核】：

1. **变换重建逐字节验证**：从冻结 `lspr23-raw83.npy` 重建候选 B 视图，
   与已封印的 `lspr23-candidate-b-quantile.npy` 逐单元比对，`mismatched_cells = 0`。
2. **源年复算与封印对表**：同一套打分与聚合代码在 LSPR23 验证区
   （`22,444` 序列、`1,238,500` 流）复算四格，与 `source-units/*/source-metrics.json` 对表，
   七项指标（`flow_average_precision`、`entity_average_precision`、
   `maximum_entity_average_precision`、`flow_count`、`entity_count`、
   `positive_entity_count`、`pooling_power`）**最大绝对差为 `0.0`**。
   四格复算实体 AP 分别为 `0.9000640331890333`、`0.9343514328808447`、
   `0.8779761904761905`、`0.9390105459057073`。
3. **LSPR24 实体常量全部命中**：实体数 `47,115`、正实体数 `752` 等于冻结常量；
   缓存 `y24` 等于 Parquet 标签、缓存 `t24` 等于 Parquet 开始时刻均为 `true`
   —— 这两项证明冻结的 `I24`/`M24` 索引的正是 Parquet 行序。

### 3.6 应写入故障手册的规则

> 任何后续工具若需要 Dijk 83 字段原值，必须回到 `lspr23-raw83.npy` 或 LSPR24 Parquet。
> `dijk-repro` 缓存的 `X23`/`X24` 不可作为 raw83 使用。
> **形状与文件字节数相同不构成同源证据**；判定同源必须比对内容摘要或逐单元差异。
> 反过来，若某模型的源年训练本身就消费该缓存（如 GRANDE，见第 1.7 节），
> 则其评价使用同一缓存是自洽的 —— **判据是「训练侧与评价侧是否同源」，不是「是否用了缓存」。**

**`b46950a` TabM32 分位数自检探针**【已核】：症状是 `select-input` 阶段退出码 `1`，
报「训练区中位数映射后最大绝对值 `0.521619` 超过绊线 `0.1`」。
根因是探针自身口径错配 —— 中位数取自**未加噪的干净列**，而 `quantiles_` 拟合在**加噪列**上；
字段过半数行取同一值时，干净中位数落在加噪并列平台正中，被映到平台中点分位而非 `0.5`。
真实数据前提：`83` 个字段中有 `5` 个字段最高频值占比超过 `50%`，
`External_src` 最高频值占比达 `0.7387` 且只有 `2` 个唯一值。
证伪实验：合成算例平台占 `60%` 时得 `+0.522099`，与真实报错的 `0.521619` 同量级；
平台占 `40%` 与几乎无并列的两个对照均映到约 `0`，证明变换本身正确。
修法改用**地标恒等式** `transform(quantiles_[k]) == Φ⁻¹(references_[k])`，
实跑覆盖 `78832` 个地标，**最大绝对偏差为 `0`**。

**`639710b` RWKV 核自身门探针**【已核】：症状是 `large` 容量自身门报「前向或损失非有限」。
根因是探针把同一条 `linspace(-0.25, 0.25)` 缩放后同时喂给语义完全不同的 `6` 个核参数
`(r, w, k, v, a, b)`；状态递推 `S ← S·diag(w) + S·(a⊗b) + v⊗k` 中秩一项 `a⊗b`
必须满足范数约束（官方取 `a = -kk`、`b = kk·c`，`kk` 逐头 L2 归一化），
探针破坏该约束导致状态沿时间维指数放大。
实测：旧探针下 `small`（head=16、ch=112）输出 `|max| = 49.75` **侥幸通过**；
`large`（head=64、ch=768）输出 `|max| = 2.031e+24`（本身仍有限），
但 `output.float().square().mean()` 约 `4e48` 超过 float32 上限 `3.4e38` 才变 `inf`。
改用官方范数约束后同一个 `large` 核输出 `|max| = 0.0718`，**相差 25 个数量级**。
修复后 `small` 与 `large` 两道自身门均真跑通过，输出形状 `[1, 128, 112]` 与 `[1, 128, 768]`。

> **教训（已写入规则）**：一个探针在小规模下「通过」不构成它正确的证据。
> `small` 通过而 `large` 失败，极易被误读成「大容量不稳定，需要调超参」。

  且该阶段输出被重定向到 `shell-init.log`，屏幕上什么也看不到，表现为「启动器一声不响地没了」。
  修法：加载 `.bashrc` 期间临时 `set +u +e`，加载完成后恢复。
- **FT 启动器磁盘百分比与 TabM32 互斥两处**。
- **ResNet 启动器补 `PYTHONPATH`**。根因【已核】：`src/` 通过可编辑安装的 `.pth` 文件进入导入路径，
  `tools/` 不在其中；而 `protocol_a_raw83` 依赖位于 `tools/` 下的
  `dijk2026_replication.dijk_fields`，依赖闭包导入在预检阶段就失败。

【已核】工作树当前共 `71` 项未提交改动（`git status --short | wc -l`），
其中绝大多数属于其他代理与用户，本次快照任务**只提交本文件与恢复卡两份文档**。
