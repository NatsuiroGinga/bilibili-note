# C56 三进程并发内存耗尽事故取证

<!-- RESEARCH_ROUTE=RWKV -->

- **日期**：2026-08-12
- **性质**：运行事故取证与工程缺陷记录。不是科学失败，不影响任何候选的证据等级。
- **结果**：C56 容器内存耗尽，用户手动重启；三个并发运行全部死亡，`screen` 全部为 `Dead`。
- **取证脚本**：`runs/diagnostics/oom_forensics.sh`（只读，已推送至服务器并执行）

## 1. 结论

**根因：三个互不知情的实验进程各自把同一份大特征矩阵载入自己的地址空间，合计超过容器 90 GiB 上限；三个启动器的资源门禁都不检查内存，也没有任何跨运行的内存准入控制。**

这是工程缺陷，不是科学结果。三个运行都没有产生无效科学结论，只是被中断。

### 3.2 峰值推断（标为推论，未直接测得）

**重要更正**：初版本节曾把 A 线峰值写成 `56–70 GiB`，依据是「Arrow 整表与后续展平矩阵同时驻留」。**该依据经核对源码已证伪**——A 线原实现在 `a1_error_anatomy.py:235`、C 线原实现在 `cpu_gate.py:362` 都有 `del feat_tbl`，Arrow 整表在展平矩阵构造前已释放，两个阶段是顺序而非叠加。修正后的核算如下。

A 线两个阶段分别取峰值：

| 阶段 | 同时驻留对象 | 峰值 |
| --- | --- | --- |
| 阶段一 特征载入 | Arrow 整表 + `F` | 源列 float32 时 `24.16 GiB`；float64 时 `36.24 GiB`（**列物理 dtype 未核实**） |
| 阶段二 展平与训练 | `F` + `X_tr` + `X_va` | `12.08 + 16.90 + 7.06 = 36.04 GiB`，再加 `QuantileDMatrix` 量化副本约 `4.2 GiB` |

**A 线全脚本峰值 ≈ `36–40 GiB`**，不是 `56–70 GiB`。

C 线死亡时日志末行是「载入 408 维特征矩阵」，即**正处于阶段一峰值**：Arrow 整表 + `F` = `24.16`–`36.24 GiB`。

TL1 实测 `VmHWM = 1.93 GiB`。

**死亡时刻三者合计 ≈ `62`–`74 GiB`**，再加上 cgroup v2 **会把页缓存计入 `memory.current`**（两个进程同时流式读取 `3.52 GiB` 宽表与 `1.48 GiB` 关系表），越过 `90 GiB` 上限。

**未直接测得峰值 RSS**：容器重启后 `memory.events` 的 `oom_kill` 计数已归零，`dmesg` 在容器内不可读，宿主机 OOM killer 记录不可得。上述峰值是按行列数和 dtype 计算的推论，不是实测。**特征列的 parquet 物理 dtype 未核实**，它决定阶段一峰值落在 `24` 还是 `36 GiB`，是本核算中最大的未定量。

## 4. 确认的工程缺陷

### 4.1 资源门禁完全不检查内存（主因）

三个启动器写出的 `resource-gate.json` 字段完全相同：

```json
{"disk_free_gib": 40.70, "disk_usage_fraction": 0.593, "gpu_free_gib": 31.36, "passed": true}
```

只有磁盘和显存，**没有任何内存字段**。而 TL1 配置里声明了：

```json
"resources": {"maximum_process_memory_gib": 8.0, "maximum_disk_usage_fraction": 0.8}
```

**声明了 8 GiB 上限，门禁既没有在启动前估算，也没有在运行期强制。** 声明值形同注释。

### 4.2 内存余量读宿主机而非 cgroup 上限

`free` 在该容器内报告 `754 GiB`，真实上限是 `90 GiB`，差 `8.4` 倍。任何基于 `free`、`psutil.virtual_memory()` 或 `/proc/meminfo` 的余量判断都会得到严重乐观的结果。必须读 `/sys/fs/cgroup/memory.max`（cgroup v2）或 `/sys/fs/cgroup/memory/memory.limit_in_bytes`（v1），并与 `memory.current` 相减得到真实余量。

### 4.3 没有跨运行的内存准入控制

三个启动器各有独立的 `worker.lock`，只防自己重复启动，**互相不可见**。没有共享预算、没有全局并发闸、没有排队。llm_probe 规则第 43 条允许"显存和内存按保守峰值计算后仍有安全余量时默认并行"，但没有任何机制实现"按保守峰值计算"这件事。

### 4.4 心跳没有业务进度，也不含内存

TL1 心跳 18 分钟只有一种形态：

```
P0 心跳：阶段=完整流水线 累计=1083秒 GPU=0, 599, 32607 输出=...
```

违反 `llm_probe/AGENTS.md` 第 58 条要求的"已处理量、总量、吞吐、预计剩余时间"。**阶段名恒为"完整流水线"，无法区分 `fit_anchor`/`source_freeze`/`adapt_seal`/`evaluate`；且完全不记录内存。** 事故前 8 分钟内存正在爬升，心跳里看不到任何征兆。

### 4.5 运行根 `status.json` 的阶段字段不推进

TL1 运行根 `status.json` 死亡时仍写 `"stage": "audit"`，而启动器 `status.json` 写 `"stage": "q0-pipeline"`。审计早在 `14:06:22` 就结束（`audit-command-exit-code.txt` 已落盘），阶段推进时没有回写运行根状态。两个 `status.json` 互相矛盾。

## 5. 已排除的原因

### 5.1 `np.add.at` 不是瓶颈（本轮证伪）

事故前曾假设 `crossyear_protected_partial_ot.py:490` 的 `np.add.at` 是 TL1 慢的原因。按真实形状本机实测（`numpy 2.0.2`，脚本 `scratchpad/bench_scatter.py`）：

| 实现 | 单树耗时 | 折合 300 树 |
| --- | ---: | ---: |
| `np.add.at`（现行） | `15.68 ms` | `4.70 s` |
| `np.bincount` | `15.38 ms` | `4.61 s` |
| 花式索引直写 | `12.49 ms` | `3.75 s` |

**加速比仅 `1.0×` 与 `1.3×`**，不是先前推测的一到两个量级。原因是该内核中每行每树只命中一个桶，索引无重复，`np.add.at` 的重复索引惩罚不触发。13 次调用合计约 61 秒，占 18 分钟的不到 6%。**该假设已证伪，不得写入故障手册或作为优化依据。**

TL1 在 `source_freeze` 停留 18 分钟的真实原因**尚未定位**：候选是 `_prototype_set` 中 `MiniBatchKMeans(n_clusters≤1024, n_init=3, max_iter=100)` 的拟合与 `predict`，以及第 537–543 行按簇的 Python 循环（每簇一次全量 `np.flatnonzero(assignment == cluster)`）。**未经测量，标为待验证假设。**

### 5.2 单个进程超限不足以解释

A 线单独运行过一次（`lspr24-a1-history-tree-ceiling-v1`，`14:04` 完成，AP=`0.9807915803958434`），未发生内存问题。**是并发而非单进程规模导致越界。**

## 6. 事故中幸存的科学结果

C 线在死亡前完成了锚点普查，结果写在 `runs/candidates/lspr24-early-warning-cpu-gate-v1/run.log`，**这部分证据有效**。

### 6.1 合同切分键核验失败（重要）

```
活动窗起始去重数=20716
推导60%边界=1709758690000000000
validation_min=1709774230000000000
train_max=1709774225000000000
核验=失败
```

按活动窗起始时间去重后推导的 60% 边界，与视图中 `validation` 的实际最小时间不一致。**共享筛选视图的切分边界与"去重活动时间键 60%"这一口径对不上**，需要独立核实视图物化器实际使用的切分规则。

### 6.2 修正边界后 B 任务硬门禁通过

C 线用新旧两套边界各做了一次锚点普查：

| 段 | 新边界（活动键）合法 / 正 / 簇 | 旧边界（行分位）合法 / 正 / 簇 |
| --- | --- | --- |
| seg0 | `184,691` / `2,883` / `1,025` | `409,777` / `4,907` / `1,797` |
| seg1 | `146,282` / `1,968` / `753` | `171,684` / `150` / `62` |
| seg2 | `416,345` / `356` / `158` | `165,801` / `155` / `72` |

**`新边界 gate_b pass=True`。** 方案册 §8.1.5 要求训练拟合段 ≥`512` 个严格正风险锚点、选择/确认段各 ≥`128`、每段 ≥`10` 个独立前体簇——新边界下三段分别是 `2883/1968/356` 正锚点与 `1025/753/158` 簇，**全部满足且裕量充足**。

旧行分位边界下 seg1 仅 `150` 正锚点 `62` 簇、seg2 仅 `155`/`72`，勉强过线。**先前基于 gate-0 旧边界得出的"B 门濒临不过"判断被推翻。**

### 6.3 事件与关系统计

- 正类连续段 `11,125` 个，按 `G_event=1` 合并后事件 `9,221` 个。
- `temporal-relations.parquet` 中 `lag<=4` 关系 `103,213,263` 行，**冲突 0**。
- 历史掩码：跨端点剔除 `0`，跨切分剔除 `4,470`。

**先前"seg1/seg2 合格事件全为单窗口"的结论来自旧边界的 gate-0，需在新边界下重测后才能沿用。**

## 7. 强制处置

1. **恢复运行前必须先修资源门禁**，不得原样重启三个运行。最小修复：门禁读 cgroup 上限而非 `free`；按行数 × 列数 × dtype 估算峰值并与余量比较；估算超限即拒绝启动。
2. **跨运行内存预算**：同时运行多个 llm_probe 实验前，由主进程统一估算各进程峰值之和，留至少 30% 安全余量；否则串行。
3. **心跳必须含内存**：长任务心跳加入当前进程 RSS 与容器剩余量，使内存爬升在事故前可见。
4. **A 线展平矩阵需要分块或降精度**：`23.96 GiB` 的稠密矩阵不应一次性构造。可选路径为按段分块拟合、改用 `QuantileDMatrix` 的迭代式输入，或只在需要的行子集上展平。
5. TL1 `source_freeze` 的真实热点需要一次带计时的定位再决定是否优化，**禁止依据已证伪的 `np.add.at` 假设改代码**。
