# PBC 父运行恢复证明修复实施计划

> **执行要求**：实现代理必须使用子代理驱动开发与日常编码规范，严格按本计划逐项执行。

## 目标

在不伪造第三章父运行原始 `manifest.json`、不改变 PBC 算法合同的前提下，为已核验但中断的父运行建立独立恢复证明，使第四章 PBC 单种子快速实验能够被审计地启动。

## 根因

- 父运行在 LSPR24 `semantic168` 构造期间中断，因此从未生成 `xgb_cpa_elp_results.json` 与原始 `manifest.json`。
- 父运行的选择收据、有效配置收据、11 个 800 树模型均存在；PBC 实际只依赖其中两个最终模型和三份 `semantic168` 折外模型。
- 直接补写一个名为 `manifest.json` 的兼容文件会掩盖父运行未完成事实，违反制品真实性要求。

## 单一可证伪假设

若 PBC 改为读取独立的 `parent-recovery-proof.json`，并逐项核验父运行中断状态、固定选择收据、有效配置收据、两个最终模型及三份 `semantic168` 折外模型的摘要和 800 树计数，则无需伪造父清单也能满足 PBC 的真实输入依赖；任何摘要、模型树数或父身份不一致都必须在读取目标年数据前失败。

## 实施步骤

- [x] 阶段一：只读核验父运行中断位置、缺失制品与现存模型。
- [ ] 阶段二：实现恢复证明生成器，固定父身份、输入文件清单、摘要、字节数、模型树数、父状态与中断事实。
- [ ] 阶段三：把 PBC 输入门改为显式读取恢复证明，移除对父原始 `manifest.json` 的错误强制依赖。

- [ ] 阶段五：执行语法、导入、命令入口、配置解析、Shell 语法、静态检查和限定差异检查；不得运行人工测试、冒烟或真实实验。
- [ ] 阶段六：主进程同步三个生产文件与恢复证明生成器，在 B76 生成真实恢复证明并启动 PBC。

## 验收条件

- 恢复证明明确记录父运行未完成，且不得使用 `manifest.json` 作为文件名。
- PBC 不再要求父原始清单，但仍核验全部实际依赖的固定摘要与模型树数。
- 恢复证明与 PBC 选择阶段均在加载任何 LSPR24 标签前完成。
- 不改变 PBC 的四方法、先导比例、预算网格、回退规则、评价指标和运行身份。
- 生产代码只执行仓库允许的静态入口检查；真实验证由 B76 冻结数据快速实验完成。
