## 一、数值路径与编译开关的裁决全过程（原第二节）

**结论已固化在卡上，本节只保留推导与实测依据。** `torch.compile` 已在代码层统一停用、
`float32_matmul_precision = "highest"`、四格全即时执行——这三条是当前合同，
**不需要再在计划或配置层讨论编译开关**。

### 原文（逐条）

- **编译与检查点动态图库径（当前实测边界）**：早期将 `torch.compile` 与 C11 变长深度微批检查点重算组合的运行，因张量元数据不一致而**硬失败**，没有可用指标、检查点或有效结果。当前 C11 将实体排序检查点固定为即时执行；常规逐流骨干部分走编译，记忆注意力中的动态布尔索引发生图断裂并回退到即时执行。该回退预期保持数学语义，但可能改变 BF16 舍入、归约顺序、训练轨迹和性能，不能凭配置项或有限梯度检查宣称其与其他格严格同路径。
- **当前四格结果的口径限制**：旧 C00／C01 为编译路径，旧 C10 为即时执行，当前 C11 为上述混合路径。因此当前 C11 只能用于机制信号和工程可运行性验证，**不得与旧三格合并为论文正式 `2×2`**，也不得声称严格同数值路径或公平工程效率比较。
- **论文正式定稿前硬门禁（必须提醒并执行，2026-08-31 已按实测裁决更新）**：在同一代码提交、PyTorch／CUDA、BF16、数据版本和种子下从头重跑 C00、C01、C10、C11（**GPU 型号不作要求**，2026-09-01 用户裁决：实验室设备动态切换显卡，只保证 32 GiB 显存）；**四格统一走即时执行（`torch.compile` 全格关闭）**。每臂运行收据须记录实际调用路径、图断裂与回退，而非只记录 `torch.compile` 配置。未满足本门禁不得声称严格同路径或正式四格；四格按源年 LSPR23 封印后，才可读取 LSPR24 作同批描述性评价。
- **「四格全即时」裁决（2026-08-31，主代理，依据见[四格编译路径统一](2026-08-31-四格编译路径统一/)）**：原条款要求「共同逐流骨干统一走编译路径」，实测证明该要求**无法与「四格同路径」同时成立**——C00／C01 的骨干是零断裂全编译，而 C10／C11 是编译入口加 4 处断裂回退（断点已精确定位到 `ch3_ft_causal_entity_memory.py:334-337`，全部为动态布尔索引）。即 `z1` 这一维不只改变数学，还改变可编译性，`C10 − C00` 的差里混入「记忆模块导致 15 次断裂、算子融合被切碎」，**机制效应与编译效应无法分离，2×2 消融因此失效**。
  裁决采纳全即时，代价可接受：编译对记忆臂本就无收益（即时／编译比 C10 为 `0.986`、C11 为 `1.003`），损失只落在两个裸骨干臂各约 `+30%` 墙钟，四臂显存上界几乎不变（`19,773` → `19,715 MiB`）。
  **两条随附的不确定（实测代理标注，未验证，不得写成结论）**：其一，「图断裂改变 BF16 舍入与归约顺序」是推论——已冻结的 `8.94e-07` 出自裸骨干且在 5090 上测得，未测过含记忆路径上编译与即时的 logits 数值差；其二，墙钟外推用的是前向吞吐而非训练步吞吐，两条独立测量互相印证（前向 `1.28–1.31×` 对 5090 训练步 `1.316×`）但仍是外推。
- **「同一 GPU」要求已于 2026-09-01 由用户放宽**：实验室设备动态切换显卡，**只保证 32 GiB 显存**，型号不可控。故上条硬门禁中的「同一 GPU」改为**只要求显存容量满足**，型号允许跨臂不同。
  **随附的科学处置（不额外花 GPU 时间）**：其一，每臂收据仍记录实际 GPU 型号，`execution_environment` 字段与 `--compare` 保持不变；其二，四格跑完后核对是否真的跨了型号，未跨则无影响；其三，跨了型号时须评估卡间数值差异对结论的威胁——已知同类量级参照是 compile 与 eager 的 logits 差 `8.94e-07` 即可使源年实体 AP 移动 `0.0015`（验证集仅 `20` 个正实体，排序易翻转），若交互项 `I` 接近该量级则在正文标注该风险；其四，确需量化时补一次零训练的跨卡前向对比（同检查点、两种卡、比 logits 与实体 AP），**不预先做**。
- **旧三格无论如何都不满足硬门禁**：旧三格跑在 5090（`sm_120`）且既有收据未记录 GPU 型号，加之走编译路径，与当前全即时、TF32 冻结的数值合同不一致，仍须全部重跑。
- **矩阵乘精度（2026-09-01 已冻结：不启用，取 `highest`）**：原条款要求「第一格启动前裁决并冻结」，本轮在 C00 重跑启动前完成该裁决。**裁决为不启用 TF32 类快速路径，`float32_matmul_precision = "highest"`，四格一致，不得中途改变。** 理由：该设置改变 float32 矩阵乘的舍入与训练轨迹，启用需额外的构造等价性检查与吞吐实测（本轮未做），在四格已统一即时执行的前提下保守取值与该方向一致。实现上由 `resolve_runtime` **显式调用** `torch.set_float32_matmul_precision`，而非依赖 PyTorch 默认——默认值可能随版本变化，显式设置才能保证四格跨时间跨机器取到同一条数值路径；实际生效值由执行路径收据的 `float32_matmul_precision` 字段记录。依据与措辞见配置 `ch3-ft-c00-bare-eager-formal-v2.json` 的 `float32_matmul_precision_evidence`。不得用 LSPR24 结果反向决定是否启用。
- **`torch.compile` 已在代码层统一停用（2026-09-01 用户裁决）**：不再逐配置开关。`maybe_compile` 无条件早退返回未编译模型；对仍写 `enabled=true` 的旧配置只打印披露、不阻断——已跑完运行的配置是冻结证据不修改，实际路径以执行路径收据为准。提交 `20ba306`。此后不需要再在计划或配置层讨论编译开关。

## 七、梯度控制器的已确认事实（原〇之二点七点五，2026-09-03，读代码＋读收据）

### 7.1 `c_scaling` 是上限，不是归一化

`tools/ch3_ft_gradient_controller.py:45` 的 `combine_gradients`：

```
c = min(1.0, ‖g_flow‖ / ‖g_rank_projected‖)
combined = g_flow + c * g_rank_projected
```

- 排序梯度**大于**逐流时：压到 `‖g_flow‖`（`c < 1`）
- 排序梯度**小于**逐流时：`c = 1`，**原样保留，绝不放大**

**「归一化到同等幅值」这个说法只在 `c < 1` 的那一侧成立**，另一侧是恒等通过。
历史上曾把它整体读作「归一化」，据此推出的结论须重核。

### 7.2 C01-half 第 10 轮的逐步统计（`step_count = 1000`）

| 推得：被上限卡住的步 | **`724`（`72.4%`）** | 多数步排序梯度超过 `‖g_flow‖` |

**三者能同时成立，说明排序梯度的逐步分布极度偏斜**：少数步极大（拉低 `c` 的中位数），

中位数不保持函数关系，`median(c) ≠ min(1, median(‖g_f‖)/median(‖g_r⁺‖))`。

### 7.3 判断补底座影响时该看哪个量

**`c_equal_one_step_count` 是核心指标**，不是范数中位数。补底座后 `g_flow → g_base`，
范数变大 ⇒ 上限提高 ⇒ 被卡住的步里排序梯度能过得更多。
**该方向为机制推理，未经实验，不得作为结论**——`g_base` 比 `g_flow` 大多少取决于
`w_e` 与实体梯度量级，二者尚未实测（实测任务因本机死机中断，须挪服务器）。

## 八、本机改造的失败记录与资源基线（原〇之二点六点二前两小节）

### 8.1 三次起跑失败与修法（每条都是实测）

| # | 失败现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | MPS OOM：分配 `18.07 GiB` 撞 `20.13 GiB` 上限 | 微批 `64`（＝`64×128 = 8192` 行）在 `16 GB` 统一内存上过大 | **微批 `8` ＋ 累积 `8`**，有效批仍 `64`，数学等价 |
| 2 | 数据准备卡 `14` 分钟不进训练，内存空闲 `79%→29%` | 本机磁盘读速仅 **`6 MB/s`**，全量 `5.51 GB` 读不完，且训练期每步取批还要随机读盘 | **抽样**（方案见恢复卡〇之二点六点二） |
| 3 | 正负同比抽 `20%` 后正实体只剩 `48` 个 | 正实体全量仅 `239`，占 `0.16%` | **正实体全保留，只抽负实体** |

### 8.2 本机资源实测基线

| 项 | 值 |
| --- | --- |
| 物理内存 | `16 GB`，M 系列**统一内存，无独立显存** |
| 磁盘读速 | **`6`–`41 MB/s`**（这是主要瓶颈） |
| 模型单步（批 `64`，`d=96`） | `59` ms |
| **训练峰值显存**（批 `64`／`512`／`4096`） | `1088`／`2200`／**`13221` MB** |
| `mmap` 加载 `1635` 万 × `83` | `0.01` 秒，RSS `0.20 GB` |
| 取一个 `8192` 行批 | `1.22` 秒，RSS 升至 `0.33 GB` |
| 批上 MPS | `1.25` 秒 |
| **瓶颈** | **随机行访问的磁盘 IO，不是内存** |

**注意 `3 MB` 那个数字是误导**——它是 `backward()` **之后**读的（激活已释放，只剩参数＋梯度）。
**真实训练峰值随批量近似线性**，批 `4096` 就要 `13 GB`。

**数据规模**：`16,353,511` 流／`150,680` 实体／正流 `1,644,599`（正例率 `10.0565%`）。

**看资源的方法**（Mac 无 `nvidia-smi`）：
`torch.mps.current_allocated_memory()` 最准；外部看用
`memory_pressure | head -5`（整机空闲低于 `10%` 即停手）或活动监视器 `⌘4` 的 GPU 历史。

### 8.3 本机实验规则的修订（`4bb8384`）

原「禁止本机执行实验计算」**反应过度**——死机真因是三个重任务并发
（torch 计算 ＋ 4 并发 API 转换 ＋ 重复启动的第二轮），非单个小模型训练。
现改为：**并发上限 1、数据必须 `mmap`、模型 `≤ 100` 万参数、结果只用于排序与止损**。
详见根 `AGENTS.md`「本机资源保护」节。
