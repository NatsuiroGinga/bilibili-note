## 一、档位定义

**档位名**：`local_screening_sixth_width_single_layer`
（常量 `WIDTH_PROFILE_LOCAL_SCREENING_SIXTH_WIDTH_SINGLE_LAYER`，
落在 `tools/ch3_ft_c00_dual_selection.py`）。

`sixth_width` 与既有 `half` 同口径，都是相对官方默认配方宽度 `192` 的分数
（`192 // 6 == 32`）；名称同时写出用途（本机筛选）与被改的两个维度（宽度、层数），
不用纯字母数字代号。

| 项 | 值 | 来源 |
| --- | ---: | --- |
| `d_token` | `32` | `base.D_TOKEN // 6` |
| `n_layers` | `1` | `SINGLE_LAYER_N_LAYERS` |
| `d_ffn_hidden` | `42` | `int(32 * 1.333333333333333)`，与官方 `int(192*1.333…)=255` 同式 |
| `n_heads` | `8`（不变） | 见下 |
| **参数量** | **`14261`** | `base.expected_parameter_count(81, 2, 14, d_token=32, n_layers=1)` |

**取值依据**（主代理 2026-09-03 转达的本机实测加速比，相对 `d=96`／3 层）：
`d=32` 得 `8.47×`（四格约 21 小时）、`d=48` 只有 `6.02×`、`d=24` 反而更慢
（已进固定开销受限区）。

**参数量分项**（`base.parameter_count_decomposition` 实测输出）：
`feature_tokenizer=5728`、`transformer_blocks=8372`、`layer_normalizations=128`、
`prediction_head=33`、`token_count=84`、`ffn_hidden_size=42`，合计 `14261`。
三档对照：`full=924283`、`half=240955`、本档 `14261`。

## 二、头数为什么不动

核实了两处约束，结论是**必须保持官方 `n_heads = 8`**：

1. `ch3_ft_transformer_field_token_protocol_a.py:2153` 的 `MultiheadAttention`
   只要求 `d_token % n_heads == 0`。`32 % 8 == 0`，头宽 `32/8 = 4`，可整除，
   前向按 `d//n_heads` 切头不会报形状错误，**不需要调头数**。
2. 同文件 `1131` 行硬断言 `architecture.n_heads == N_HEADS`（「论文明写不调头数」）。
   该断言在 `effective_base_config` 里对**覆写前**的 `base_config` 执行，
   改头数会让全部 31 份配置在此失败。

依据已写进代码注释。本档因此只改 `d_token`、`d_ffn_hidden`、`n_layers` 三项，
其余 `architecture` 字段逐位沿用官方默认配方（第三节冒烟已实测确认）。

## 三、回归核验结论

**全部通过：31 份绑定本工具的既有配置，三项指纹改动前后逐位不变。**

核验对象是 `configs/*.json` 中 `schema_version == "ch3-ft-c00-dual-selection-config-v1"`
的**全部 31 份**（简报所说的 21 份是其真子集），逐份比较四项：

| 指纹 | 结果 |
| --- | --- |
| `science_identity_sha256`（`canonical_sha256(science_projection(cfg))`） | 31/31 逐位不变 |
| `runtime_identity_sha256`（`canonical_sha256(runtime_projection(cfg))`） | 31/31 逐位不变 |
| `effective_base_config(cfg)` 规范 JSON 的 sha256 | 31/31 逐位不变 |
| `validate_config(cfg)` 是否通过 | 31/31 改动前后均为 `ok` |

**为什么要单独比 `effective_base_config`**：`--validate-config` 只打印两个身份哈希，
**不调用 `effective_base_config`**，只跑它无法证明骨干架构没被改动。
故用脚本直接对该函数的返回值取规范摘要，把简报要求的「`effective_base_config` 逐位不变」
真正测出来，而不是从身份哈希不变去推。

方法：改动前在 `HEAD` 干净工作树上抓一次全量快照，改动后再抓一次，逐键比较。
两次快照与比较脚本在会话临时目录（`identity_snapshot.py`、`baseline.json`、
`after_d32.json`），随任务清理，不入仓库。

**不变性的机械理由**（与实测一致）：`WIDTH_PROFILES` 只用于成员检查；
`bare_ft_expected_parameter_count` 与 `effective_base_config` 的 `full`／`half`
分支一字未动；新档位只增加一条 `elif`，既有配置全部走不到。

## 四、冒烟核验（内存态，不落配置文件）

以 `configs/ch3-ft-LOCAL-mps-s0-timing-probe-v1.json` 为底，在内存中把
`width_profile` 换成新档位、`expected_parameter_count` 换成闭式值：

- `validate_config` **通过**（模型合同断言认得新档位，`model` 块期望字典正确带上
  `width_profile` 键）。
- `effective_base_config` 相对 `base_config` **只改三项**：
  `n_layers 3→1`、`d_token 192→32`、`d_ffn_hidden 255→42`；
  其余 `architecture` 字段逐位一致（实测 `True`）。

`n_layers=1` 下闭式仍成立：LayerNorm 计数 `4*d*L` 依据是每层 `norm1` + 除首层外的
`norm0` + 一个 `last_normalization` 共 `2L` 个；`L=1` 时为 `norm1` 与
`last_normalization` 两个（首块按 `first_block_skips_first_normalization=True`
跳过 `norm0`），恰为 `2L`。

## 五、疑点（发现但未擅自改）

1. **`thesis/methods/第三章定案.md` §4.1 的参数量 `23,041` 与闭式对不上。**
   该行写「`d_token=48`、层数 `1`、参数量 `23,041`、由同一闭式算得」，
   但 `base.expected_parameter_count(81, 2, 14, d_token=48, n_layers=1)` 实测为
   **`27,487`**。差值 `4,446` 无法由 `ffn_hidden` 取整口径（`63` vs 精确 `64`）或
   `token_bias` 开关解释——两种口径下反解出的分词器项都不是 `48` 的整数倍，
   说明 `23,041` 不出自本闭式的任何一组参数。该档位已随本轮裁定改为 `d=32`
   （闭式 `14,261`），`23,041` 因此不再被使用，但**定案文档里的这个数仍是错的**，
   建议下轮更新该文档时一并订正。我按简报要求未改该文档。
2. **既有潜在缺陷：机制一／M-E 臂的参数量期望写死 `base.D_TOKEN`。**
   `ch3_ft_c00_dual_selection.py` 第 `465`、`478` 行分别用
   `entity_memory_parameter_count(base.D_TOKEN, slots)` 与
   `entity_gated_ple_parameter_count(..., base.D_TOKEN, ...)` 算期望参数量，
   **不看 `model.width_profile`**。当前没有任何配置同时启用缩容档与这两个机制，
   故不触发；但缩容档四格若将来要跑 `entity_memory` 或 `entity_gated_ple` 臂，
   这两处会算出按 `d=192` 的期望值而在运行时断言失败。这是随 `half` 档引入的既有
   问题，不是本轮改动带来的，**未擅自修改**。
3. **建配置时须注意恢复卡 L5**：`micro_batch_sequences` 只进 `runtime_projection`、
   不进 `science_projection`，配合 L4 的归一化因子与非线性 top-k 聚合，
   只改微批的两次运行会优化不同目标却共享同一 `science_identity_sha256`。
   本机 MPS 已实测微批 `64` 会 OOM（须走微批 `8` ＋ 累积 `8`），
   故新四格配置与服务器 half 档配置**不能靠身份哈希相同来主张科学等价**。
