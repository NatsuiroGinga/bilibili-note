### 1.2 两个输入候选

| 顺序 | 展示名 | 内部键 | 数值 76 | 离散 5 | 布尔 2 | 输入维 |
| --- | --- | --- | --- | --- | --- | --- |

**关闭的三项待定**：

1. **存储视图**：七个字段 `integer_like` 全为 `False`，取值域形如 `-3.92 ~ 0.94`、`-0.55 ~ 10`。**缓存中确为标准化浮点，不是原始端口号**。本计划 1.2 节先前依据 `dijk_ingest.py` 只做 `float32` 强制转换而写的「本仓库入库环节未做统计变换」只覆盖入库那一环，真正的 `X23.npy` 由别的管线产出且已标准化，该推断在本处**予以更正**。Codex 在看板的提醒正确。所幸实现不依赖该解释——词表键用 `float32` 位模式、只要求映射单射且确定，故无需改动。
2. **缺失指示位**：七个字段 `missing_fraction` **全为 `0`**，故两个候选一律不引入指示位，1.3 节的条件分支恒走不引入这一支，与冻结的 `83` 维无冲突。
3. **候选二规模**：`d_in = 76 + 2 + Σ(c+1) = 67,195`，参数量 `544 × 67,195 + 950,305 = 37,504,385`。

候选一对应统一合同第 109 行 TabM 行所写的「使用 LSPR23 冻结的共享数值视图」，也是冻结配方第 156 行 `995,457` 参数量所依据的输入宽度。候选二对应论文 §D.2 的字段类型分治协议。

### 1.3 变换拟合与缺失处理

- 缓存中缺失与 `±inf` 已统一为 `NaN`（`dijk_ingest.py` 第 112 行 `np.nan_to_num`），两个候选都必须显式处理 `NaN`，不得让其进入矩阵乘法。
- 分位数规范化器只在 LSPR23 协议 A 训练区的有效流上拟合，`NaN` 不参与分位数估计；拟合完成后冻结并写入哈希；验证区、时间尾部区与 LSPR24 只应用不重新拟合。
- 独热词表只由训练区取值构成。训练区未出现的取值一律落入固定的越界桶，越界桶位置在拟合时确定并写入封印。
- 缺失值按收据的 `missing_count` 与 `missing_fraction` 处理：数值字段缺失填训练区中位数并置伴随缺失指示位；离散字段缺失并入越界桶。缺失指示位是否启用由收据显示的实际缺失率决定，若七个字段的 `missing_fraction` 全为 `0` 则不引入指示位，避免增加与数据不符的输入维度。**指示位的启用与否必须两个候选一致**，否则输入维差异会混入候选比较。
- 序列补零掩码沿用协议 A 的 `M23`，补零位置不参与损失、不参与池化、不参与分位数拟合。

### 1.4 序列与因果边界

- 序列长度 `128`，逐流 83 字段按实体内活动时间顺序排列，由 `I23` 给出流索引、`M23` 给出有效位。
- 因果前缀聚合只读取当前时刻及严格过去时刻，不读取未来流、实体最终长度或任何目标年统计。
- 实体划分为实体不相交，训练实体与验证实体交集为零，另切除时间尾部。

### 1.5 参数量与输入宽度的耦合

BatchEnsemble 单层参数量按冻结配方第 170 行 `BE(a,b,k)=a×b+k×a+k×b+k×b`。本计划已逐层核验闭合：

```
BE(83,512,32)   =  77,920
BE(512,512,32)  = 311,296
BE(1024,512,32) = 589,824
32 × Linear(512,1) = 16,416
共享 p_log      =       1
合计            = 995,457
```

与冻结配方第 156 行标注为「数学闭合，待实现复核」的 `995,457` 一致，本次核验即完成该复核。

由此解出闭式：

```
总参数量 = 544 × d_in + 950,305
```

`d_in = 83` 时恰为 `995,457`。**冻结的 `995,457` 只在候选一成立**；候选二的参数量随独热总宽变化，须按上式计算并单独封印。统一合同第 114 行已把约 9 万参数版本定为效率锚，把完成矩阵规定输入与配方身份的版本定为有资格裁决预注册配方的版本，因此参数量高于效率锚不构成公平性问题；需要处理的只是冻结值随候选分支这一点，见第二节冲突三。

## 二、待 Codex 裁决的冲突登记

下列四项均由本方在读取冻结制品时实测发现，本方只登记事实与建议，未擅自处置。任一项未裁决时，实现按「本方建议」落地并在配置中留显式开关，裁决到达后只改配置不改代码。

### 冲突一：停止规则

| 来源 | 规定 | 位置 |
| --- | --- | --- |
| 冻结配方 | 无固定轮数上限，验证逐流 AP 耐心 `16`，无学习率调度 | 骨干专属论文配方冻结.md 第 155 行 |
| 协议 A | `epochs=20`、`steps_per_epoch=1000` 跑满不早停，选最早最大轮次 | ch3_resmlp2_tabm_protocol_a_2x2.py 第 178、179、188 行与第 980 行运行期封印文本 |

两者不可同时满足。耐心 16 会让四格训练轮数各不相同，破坏共同预算，也使新结果无法与已完成的 ResMLP2、TabM4、全容量 MLP、GRANDE 在同一停止规则下对表。

**本方建议取协议 A**：任务名与看板 N-12 条目都写「协议 A」，四格可比性与总表对表依赖同一停止规则。偏离配方停止项这一点写入实施报告与选择封印，不隐瞒。

### 冲突二：权重衰减与学习率不能照抄协议 A

协议 A 的 `expected_training` 固定 `learning_rate=0.002`、`weight_decay=0.01`（第 174 至 191 行，不完全相等即抛错）。冻结配方的两个优化器候选是 `0.002 / 0.0003` 与 `0.0007071067811865476 / 0`。协议 A 的 `weight_decay=0.01` **与两个候选都不同**。

**本方建议**：新工具是独立文件，不受既有工具内部断言约束。学习率与权重衰减由优化器候选决定，其余协议项（种子、序列长度、有效批量、轮数、每轮步数、梯度裁剪、辅助损失权重、验证比例、时间尾部比例、选择指标、选择规则）逐字照抄协议 A。

### 冲突三：参数量冻结值随输入候选分支

冻结配方第 156 行把 `995,457` 写为冻结值，但该值只在 `d_in=83` 成立。候选二一旦入选，参数量必然不等于 `995,457`。

**本方建议**：参数量断言按候选分支——候选一断言恰等于 `995,457`；候选二断言恰等于 `544 × d_in + 950,305`，其中 `d_in` 由基数收据算出并写入封印。两者都在运行时用实际 `sum(p.numel() for p in model.parameters() if p.requires_grad)` 三方比对。

### 冲突四：既有资源合同数值已失效

既有 TabM4 配置写 `observed_tabm_single_job_peak_gpu_memory_mib: 8244`、`minimum_free_gpu_memory_mib: 8244`，而 D-1 实测 N-02 峰值为 `13646.41 MiB`。

本方按协议 A 的形状断言核算了峰值构成：`X23` 为 `(16353511, 83)` fp32 即 `5.06 GiB`，`X24` 为 `(20227356, 83)` fp32 即 `6.25 GiB`，`I23` 为 `(271815, 128)` int64 即 `0.26 GiB`，合计双年常驻约 `11.66 GiB`，占 `13646.41 MiB` 的 `88%`。**峰值由数据常驻主导，模型与激活占比小**：TabM32 单个 fp32 隐藏张量为 `4 × 128 × 32 × 512 × 4 = 32 MiB`、CPA 拼接 `64 MiB`，与冻结配方第 150 行的资源推导逐字一致；参数加梯度加 Adam 两态仅 `15.2 MiB`。

**本方建议**：不在配置中写死任何预测峰值。工具在数据上卡后立即记录实测常驻字节并写入日志，分配模型前机械断言剩余显存足够；启动器仍须过 `tools/memory_admission_gate.sh`。配置中的 `minimum_free_gpu_memory_mib` 由 Codex 依据本节核算与实测重新裁定。

### 冲突五：共享精度合同与协议 A 同精度可比性

Codex 于提交 `b74d858` 建立了共享精度合同 `configs/neural-precision-profiles-v1.json`，`default_profile` 为 `cuda-bf16-amp-fp32-sensitive-v1`，看板 N-12 行同步登记为统一默认精度。

**冲突事实**（全部为本方实测，非转述）：

| 骨干 | 工具 | `autocast`/`GradScaler`/`bfloat16`/`float16` 命中数 | 实际精度 |
| --- | --- | --- | --- |
| ResMLP2 与 TabM4 协议 A 四格 | `ch3_resmlp2_tabm_protocol_a_2x2.py` | `0` | 纯 `FP32` |
| 全容量 MLP 源年筛选 | `ch3_full_capacity_mlp_source_screen.py` | `0` | 纯 `FP32` |
| 严格过去 CPA | `ch3_full_mlp_strict_past_cpa_protocol_a_q0.py` | `0` | 纯 `FP32` |
| GRANDE | `ch3_grande_protocol_a_source_q0.py` | `7` | 可选，`allowed_modes` 为 `["fp32", "cuda_bf16_autocast"]` |

三个已完成的协议 A 骨干都是纯 `FP32`。而 `thesis/experiments/llm_probe/AGENTS.md` 第 35 行规定「结构比较必须同精度；异精度只作工程资格观察，除非补同精度对照」。

**合同内部的堵点**：精度档案中唯一的 CUDA `FP32` 档 `cuda-fp32-numerical-fallback-v1` 其 `scientific_status` 为 `numerical_anomaly_fallback_only`，即只能在出现数值异常时作回退，**不能因可比性主动选用**。因此现有档案不提供「为对表而选 FP32」的合法路径。

**本方的量化判据**：按协议 A 的形状断言与冻结配方的张量口径核算，

| 项 | 值 | 占 D-1 实测峰值 `13646.41 MiB` |
| --- | --- | --- |
| 双年数据常驻 | `11.66 GiB` | `87.5%` |
| TabM32 激活上界 | `0.34 GiB` | `2.6%` |
| 参数加梯度加 Adam 两态 | `0.015 GiB` | 可忽略 |

`autocast` 不改变由 `.npy` 载入的 `float32` 常驻数据，档案本身也把 `parameter_dtype` 写死为 `float32`，因此改 `BF16` 只把激活减半，**可省约 `0.17 GiB`，占峰值 `1.3%`**。

**本方建议**（已被否决，保留备查）：本运行取 `FP32`，理由是 `BF16` 在本运行的显存收益仅 `1.3%`，却要付出与三个 `FP32` 协议 A 骨干失去同精度可比性的代价。

### 冲突五的裁决结果（Codex 提交 `c758763`，2026-08-21 13:01）

Codex 在 `thesis/experiments/llm_probe/AGENTS.md` 中直接裁决，原文：

> B76 RTX 5090 的新神经训练默认使用 `configs/neural-precision-profiles-v1.json` 中的 `cuda-bf16-amp-fp32-sensitive-v1`，并通过 `tools/neural_precision_runtime.py` 接入：BF16 autocast，参数、优化器状态和敏感计算保持 FP32，BF16 不使用 `GradScaler`，有效批固定且只按资源选择数学等效微批与累积。FP32、FP16 和 activation checkpointing 只能作为有收据的显式例外；同族结构、机制和选型的科学比较必须使用同一 profile，跨 profile 只作完整系统或工程 Pareto，活动旧运行不得中途切换精度。

**裁决要点与本计划的落地**：

| 裁决 | 本计划的执行 |
| --- | --- |
| 默认 `cuda-bf16-amp-fp32-sensitive-v1` | 配置 `precision_profile_id` 取该值，删除 `precision_pending_ruling` |
| 必须经 `tools/neural_precision_runtime.py` 接入 | 不自写 autocast、梯度累积、资源采集与检查点状态，一律复用该模块 |
| 参数与优化器状态保持 FP32 | 用 `validate_model_optimizer_fp32` 启动断言 |
| 敏感计算保持 FP32 | 成员 BCE 损失、32 个 sigmoid 概率算术平均、ELP 的 `clamp` 与幂运算、CPA 的 `cumsum`（属 `reduction`）一律放进 `fp32_island` |
| 不使用 `GradScaler` | 经 `create_grad_scaler` 取值，BF16 下应为 `None` |
| 有效批固定，只按资源选微批与累积 | 有效批 `64`、微批 `4`、累积 `16` 仍以 N-12 合同为准，看板明确「不继承共享示例数值」；先经 `validate_microbatch_plan` 校验自洽 |
| 同族比较须同 profile | TabM32 四格与其候选选择彼此同 profile，成立 |
| **跨 profile 只作完整系统或工程 Pareto** | **本运行与三个既有 `FP32` 骨干的比较属跨 profile**，用 `validate_comparison_profiles` 约束；模块常量 `CROSS_PROFILE_CLAIMS` 仅含 `complete_system_pareto` 与 `engineering_observation` |

**须记入实施报告与选择封印的后果**：TabM32 在 `BF16` 下的四格结果，**不能与 ResMLP2、TabM4、全容量 MLP、严格过去 CPA 这四个纯 `FP32` 骨干作结构比较**，只能作完整系统或工程 Pareto 陈述。第三章全模型指标总表在同表并列这两类结果时，必须标注精度 profile 差异，不得直接据此声称某骨干「全面领先」。该限制是裁决的直接推论，不是本方保留意见。

```python
def load_cardinality_receipt(path: str, config: dict[str, Any]) -> dict[str, Any]:
    """读取并机械校验 LSPR23 训练区字段基数收据。

    收据由 Codex 的独立诊断工具产出，本工具只消费不产出。

    receipt_path = Path(path)
    if not receipt_path.exists():
        raise FileNotFoundError(
            f"缺少字段基数收据：{receipt_path}。"
            "输入适配封印前必须等待 Codex 产出该收据，见看板 N-12 的 "
            "WAITING_FOR_CODEX_CARDINALITY_RECEIPT"
        )
    receipt = json.loads(receipt_path.read_text(encoding="utf-8"))
    if not receipt.get("complete"):
        raise RuntimeError("字段基数收据未标记完成，拒绝消费")
    expected_fields = (
        list(config["field_groups"]["categorical"])
        + list(config["field_groups"]["boolean"])
    )
    if list(receipt["fields"].keys()) != expected_fields:
        raise RuntimeError(f"收据字段清单或顺序不符：{list(receipt['fields'].keys())}")
    split = receipt["protocol_a_source_split"]
```

**词表来源必须是训练区数据本身，不是收据**。收据的 `top_values` 只含前二十个取值（`ch3_lspr23_field_cardinality_receipt.py` 第 113 行 `top_k_values` 为 `20`，第 263 行 `ordered[:top_k]`），而 `unique_count` 可能远大于二十，靠收据建不出完整词表。收据在本任务中的作用是三项断言与容量核算，不是词表数据源：

- 拟合完成后断言各字段词表长度恰等于收据的 `unique_count`；不等即说明拟合区与收据的切分身份不一致，抛错停止。

- 用 `finite_count`、`missing_count` 与 `training_effective_flows` 交叉校验拟合覆盖的行数。

**存储视图的既定事实**（由本方核验 `tools/dijk2026_replication/dijk_ingest.py` 第 102 至 114 行的 `_to_float32_matrix`）：83 列一律按 `DIJK_FEATURES` 顺序强制转为 `float32`，**不施加任何统计量变换**；缺失与 `±inf` 统一化为 `NaN`。因此缓存中的离散列是原值的 float32 表示，端口号取值不超过 `65535`，小于 `float32` 的精确整数上界 `2^24`，可精确往返。

Codex 在看板消息中提示「端口列为标准化浮点视图，基数可用于候选与资源核算，但不能直接解释为原始端口号」。本方核验只能证明本仓库的入库环节未做统计变换，**不能排除上游 LSPR 发布版本自身已对端口列做过映射**。据此定下不依赖该解释的实现方式：

- 独热只要求「同一原值映射到同一列」，即映射单射且确定。这一点由 float32 位模式相等判定，不需要知道该浮点数对应哪个真实端口号。
- 因此 `integer_like` 为假**不作为候选二的停止条件**。计划早前写的「`integer_like` 为假即抛错停止」是缺陷，已修正：该字段只写入封印作为事实记录，不参与分支。
- 真正的停止条件是收据显示 `unique_count` 使输出维超出显存可行性核算，或某字段 `finite_count` 加 `missing_count` 不等于训练区有效流数（收据自身第 248 行已有等价校验）。
- 词表键统一用 `np.float32` 的位模式，避免十进制往返带来的比较歧义。`NaN` 不进词表，单独并入越界桶。
