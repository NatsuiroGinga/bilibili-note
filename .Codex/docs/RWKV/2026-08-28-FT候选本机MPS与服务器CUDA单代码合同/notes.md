## 二、共享精度配置已经具备的基础

`neural-precision-profiles-v1.json` 已同时登记：

- `cuda-bf16-amp-fp32-sensitive-v1`：CUDA、BF16 自动混合精度、FP32 参数与优化器状态、无梯度缩放器。
- `mps-fp32-v1`：MPS、FP32、关闭自动混合精度、无梯度缩放器。
- 两个 profile 使用相同 FP32 敏感计算清单，包括 softmax、对数、概率归一化、损失、归约、指标、递归状态和路由。
- 有效批合同已经要求微批量为有效批的机械因子，每个完整有效批只清梯度一次、只更新一次优化器。
- 检查点合同已经要求保存精度、有效批、微批、累积步数、随机状态与完整优化器步边界。

共享运行时也已支持按设备解析 profile；MPS FP32 会返回空自动混合精度上下文，资源收据对非 CUDA 设备允许 CUDA 专用字段为空。

## 三、当前 FT 工具的 CUDA 写死点

| 位置 | 当前行为 | 所需最小改造 |
| --- | --- | --- |
| `PRECISION_PROFILE_ID` | 常量写死 CUDA BF16 | 从配置读取并由共享运行时核验 |
| `resolve_precision_profile` | 解析到非 CUDA profile 即失败 | 接受配置显式指定的 MPS 或 CUDA profile，禁止自动回退 |
| `validate_config` | 只接受 CUDA BF16 | 把科学合同校验与运行 profile 校验分离 |
| `GPU_FREE_MEMORY_MINIMUM_MIB` | 只表达 CUDA 空闲显存 | 改为设备资源策略对象，本机预算来自真实 MPS 收据 |
| `_resolve_device` | 只有 CUDA 分支 | 改为按配置严格解析 `mps` 或 `cuda` |
| `gpu_memory_snapshot` | 非 CUDA 直接失败 | 改为通用资源快照接口，设备专用字段按能力登记 |
| 随机状态 | 保存 CPU 与 CUDA 状态，没有 MPS 状态 | 检查点模式增加统一加速器随机状态字段 |
| 恢复 | 只恢复 CUDA 随机状态 | 按检查点设备类型恢复对应加速器状态 |
| 首步与峰值统计 | 只调用 CUDA 峰值接口 | 通过设备运行时适配器采样，MPS 用采样峰值和进程峰值 |
| `load_source_arrays` | `X23` 用普通 `np.load` | `X23` 强制只读内存映射，按微批取行 |
| `load_target_arrays` | `X24` 用普通 `np.load` | `X24` 强制只读内存映射，评价按批取行 |
| 主机传输 | 直接 `torch.from_numpy(...).to(device)`，无页锁定策略 | 页锁定与异步传输归入设备运行配置；MPS 禁用页锁定 |

当前工具中输入变换拟合已经对 `X23` 使用 `mmap_mode="r"`，训练和目标评价加载路径尚未沿用这一做法。

## 四、身份缺口

当前运行身份包含配置文件哈希、代码哈希、源数据清单哈希和字段基数收据哈希。它适合阻止同一运行目录的制品混用，但不能直接证明本机与服务器科学身份一致：

- 本机与服务器配置必然因 profile、微批量、预算和 `run_id` 不同而具有不同完整配置哈希。
- 现有数据清单使用文件字节数和修改时间；相同数据复制到另一台机器后修改时间可能不同。
- 当前身份没有单独的模型结构哈希、机制哈希、损失与指标哈希、检查点模式哈希。

统一合同因此需要同时保存：

- `science_identity_sha256`：只覆盖不允许跨设备变化的科学字段。
- `runtime_identity_sha256`：覆盖 profile、设备、微批量、预算、资源采样和 `run_id`。
- `data_semantic_sha256`：来自权威清单的内容或语义哈希，不使用路径和修改时间作为跨机器同一性的依据。

## 五、跨设备结果的科学边界

- MPS FP32 与 CUDA BF16 属不同 profile。按神经训练合同，二者不能直接用于同族结构、机制、消融或选型的科学因果比较。
- MPS 结果只可决定代码是否可运行、张量与梯度是否有限、资源是否安全，以及是否值得增加 CUDA 计算。
- 即使 MPS 筛选方向为正，也不能写入正文、正式表格、路线总控的“实验支持”或替代 CUDA 正式运行。
- CUDA 正式运行必须使用新身份从头训练。MPS 模型、优化器、选中轮次和随机状态均不得作为正式初始化。

## 六、第三方接口核验状态

本轮尝试通过 Context7 查询 PyTorch 的 MPS 同步、内存、随机状态、页锁定和断点加载接口。首次查询因外网域名解析失败，提权重试被用户中止，未取得在线文档结果。

因此本文冻结的是设备运行时的**行为接口**，不是未经核验的具体 PyTorch 签名。生产代码实施前必须在本机和服务器分别记录实际 PyTorch 版本，并用该版本官方文档或 Context7 核验 MPS/CUDA 适配器调用；配额或网络继续阻断时应向用户披露，不能凭记忆静默实现。

## 七、合同设计结论

- 使用一个 Python 工具、一个模型构造器、一个数据加载器、一个机制实现、一个指标实现和一个检查点模式。
- 用显式 `runtime` 配置选择 MPS 或 CUDA，不根据“哪个设备可用”自动降级。
- 有效批量与科学归一化语义保持一致；微批量和累积步数可按设备变化，但乘积必须等于冻结有效批量。
- MPS 预算先以真实数据完成一个完整优化步并采样资源，再冻结筛选配置；未有收据前不得填入猜测值。
- 正式 CUDA 预算继承候选正式实验计划，不从 MPS 耗时或效果反推超参数。
