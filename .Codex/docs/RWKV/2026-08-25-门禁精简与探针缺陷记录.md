## 一、已修的两个探针缺陷

### 1. TabM32 分位数自检探针（提交 `b46950a`）

**症状**：`select-input` 阶段退出码 `1`，报「训练区中位数映射后最大绝对值 `0.521619` 超过绊线 `0.1`」。

**根因**：中位数取自**未加噪的干净列**（NaN 填补需要），而 `quantiles_` 拟合在**加噪列**上。当字段过半数行取同一值时，干净中位数落在加噪并列平台的正中，被映到平台中点对应的分位，而不是 `0.5`。也就是说，探针比较的两个量本来就不在同一个坐标系里，报错反映的是探针自身的口径错配，不是变换实现有误。

**证伪实验**：合成算例中平台占 `60%` 时得到 `+0.522099`，与真实报错的 `0.521619` 同量级，复现了失效模式。两个对照——平台占 `40%`（中位数不落在平台内）与几乎无并列的列——均映到约 `0`，证明分位数变换本身正确。

**真实数据前提**：`83` 个字段中有 `5` 个字段的最高频值占比超过 `50%`；`External_src` 的最高频值占比达 `0.7387`，且该字段只有 `2` 个唯一值。这类字段必然触发上述平台效应。

**修法**：放弃「干净中位数应映到 0.5」这一错配判据，改用**地标恒等式**——在严格递增的地标上，`transform(quantiles_[k])` 必须等于 `Φ⁻¹(references_[k])`。该判据只涉及拟合本身的自洽性，与是否加噪无关。实跑覆盖 `78832` 个地标，最大绝对偏差为 `0`。

### 2. RWKV 核自身门探针（提交 `639710b`）

**症状**：`large` 容量的自身门报「前向或损失非有限」。

**根因**：探针把同一条 `linspace(-0.25, 0.25)` 缩放后同时喂给语义完全不同的 `6` 个核参数 `(r, w, k, v, a, b)`。RWKV-7 的状态递推为

```
S ← S·diag(w) + S·(a⊗b) + v⊗k
```

其中秩一项 `a⊗b` 必须满足范数约束才不会让状态发散。官方实现取 `a = -kk`、`b = kk·c`，其中 `kk` 逐头做 L2 归一化。探针用同一条等差数列冒充 `a` 和 `b`，破坏了这个约束，于是状态在时间维上指数放大。

**实测数据**：
- 旧探针下 `small`（head=16、ch=112）输出 `|max| = 49.75`，**侥幸通过**——量级已经异常，只是还没溢出。
- 旧探针下 `large`（head=64、ch=768）输出 `|max| = 2.031e+24`，**本身仍是有限值**；但 `output.float().square().mean()` 得到约 `4e48`，超过 float32 上限 `3.4e38`，求平方均值这一步才变成 `inf`。报错信息指向损失非有限，真正的病灶在更前面。
- 改用官方范数约束后，同一个 `large` 核输出 `|max| = 0.0718`，与 `2.031e+24` 相差 **25 个数量级**。

**修复后验证**：`small` 与 `large` 两道自身门均**真跑**通过，输出形状分别为 `[1, 128, 112]` 与 `[1, 128, 768]`。

**教训**：`small` 通过而 `large` 失败，很容易被误读成「大容量不稳定，需要调超参」。实际上两者用的都是错的探针输入，只是 `small` 的放大倍数还没顶到 float32 天花板。一个探针在小规模下「通过」不构成它正确的证据。

## 二、本轮废弃的五道冗余门禁

以下五处均属「用第二道门重复检查第一道门已经保证的事」，或「用与安全无关的百分比阻断一次安全的运行」。本轮改动**尚未提交**（改动位于其他代理持有的启动器与工具文件中，不在本次提交范围内）。

| 位置 | 原行为 | 改为 |
| --- | --- | --- |
| RWKV 启动器 `compute_pids` 非空即 `return 1` | GPU 上存在任何计算进程就拒绝启动 | 打印并发进程清单后继续 |
| `_gpu_admission_measurement` 的 `free < 需要 or compute_pids` | 同上，与显存余量检查重复 | 只在 `free` 不足时抛错 |
| `_process_admission_measurement` 匹配到其他 llm_probe 进程即抛错 | 与内存门重复 | 写入收据字段 `resource_contention` |
| FT 启动器磁盘门 `used_percent >= 80` | 可用 `19.45 GiB` 远超要求的 `10 GiB` 却被拦下 | 百分比只打印，不阻断 |
| FT 启动器硬编码禁止与 TabM32 并存 | 与提交 `992d825` 确立的并发披露规则直接冲突 | 记录并发对象后继续 |

判据说明：`gpu_free_mib < 20480` 已经保证显存安全，`compute_pids` 非空只说明卡上有别人，不说明本次会 OOM；`available_kib >= minimum_kib` 已经保证磁盘安全，`used_percent >= 80` 只是一个与本次写入量无关的比例。两者都属于第三条判据「禁止用多个门检查同一件事」的典型反例，已作为反例原文写入规则。

## 三、三个环境类缺陷

### 1. S0 启动器静默退出

`set -Eeuo pipefail` 撞上 `.bashrc:9` 的 `PS1: unbound variable`。关键点是 `|| true` **只吞退出码，不吞 `set -u` 在 source 内部触发的中止**——脚本在 source 阶段就整体终止，`|| true` 根本没有机会生效。同时该阶段的输出被重定向到 `shell-init.log`，屏幕上什么也看不到，表现为「启动器一声不响地没了」。

修法：加载 `.bashrc` 期间临时 `set +u +e`，加载完成后恢复。

### 2. ResNet 启动器缺 `PYTHONPATH`

`src/` 是通过可编辑安装的 `.pth` 文件进入导入路径的，`tools/` 不在其中。而 `protocol_a_raw83` 依赖 `dijk2026_replication.dijk_fields`，该模块位于 `tools/` 下，于是依赖闭包导入在预检阶段就失败。

修法：启动器显式设置 `PYTHONPATH` 覆盖 `tools/`。

### 3. 陈旧 screen 死会话占槽

日期为 `07/07/26` 的同名死会话占住了会话名，导致新的 `screen -dmS` 建不起来。表现极具迷惑性：所有门禁都通过，运行目录里 `state=prepared`，但**没有任何工作进程**。`screen -wipe` 清掉死会话即解。

## 四、我自己的查错失误

以下三条是本次会话中我犯的查错错误，记录在案以防复发。

1. **查错了运行根目录**。ResNet 实际跑在 `...-seed42-v2`，我一直在查 `v1`，据此误判为「没起来」。实际上它早已完成源年资格封印。
2. **没有第一时间读日志文件**。S0 静默退出时，全部证据一直躺在 `shell-init.log` 里，我绕了三四轮才想到去读它。
3. **凭记忆写交付物名**。派发子代理时把 ResNet 交付物名写成 `ch3_tabular_resnet_protocol_a`，实际名称是 `ch3_tabular_resnet_paper_recipe_protocol_a`，几乎造成重复实现。

**共同教训**：报错后的第一个动作应当是**找到并读完整的日志文件**，而不是反复重跑、猜测原因，或凭记忆断言路径与名称。前三条失误全部可以由「先把日志读完」这一个动作避免。
