# 2026-08-18 序列排序键核实：第三章 CPA-ELP 实际用的是哪个时间字段

任务：锁死正文 3.4.2 与 2026-08-11 跨年度冻结合同第 5 节末的不一致。
方式：只读核查（本机读码 + 服务器只读 CPU 审计），不改任何生产脚本、不启动任何 GPU 作业、不 kill 任何进程。

## 1. 判定

**第三章全部实验的序列排序键是 `mTimestampStart`（流起始时间），不是合同要求的 `available_ns = mTimestampLast × 1000`。**

因此：

- **正文 3.4.2 第 43 行的描述是正确的**，一个字都不用改；3.3 节第 7 行、3.6 节第 15 行与第 227 行的同类表述同样正确。
- **未被实现的是 2026-08-11 冻结合同第 5 节末的因果性条款**。该条款约束的是 Rust 跨年度物化器
  （`tools/lspr24_g0/src/lspr_crossyear.rs`，排序键 `(pair_key, available_ns, start_ns, source_row_index)`），
  而第三章 CPA-ELP 走的是另一条流水线：`runs/diagnostics/dijk-repro/cache` 的 Python 缓存，
  沿用 Dijk 2026 正文口径（83 字段 + 起始时间排序）。两条线从未合并。
- 后果不是数据泄漏，而是 **3.5.1 定理 3-1 的在线可计算性论断在部署语义上被高估**：
  按起始时间排序时，前缀里可能存在「结束时刻晚于当前流」的流，其完整流统计在当前流结束时尚不可见。
  实测这类位置占 LSPR24 的 **43.70%**、LSPR23 的 **47.67%**（见第 4 节）。
- 需要用户裁决的不是「正文怎么写」，而是「补一句边界说明 / 加一次排序键消融 / 全量重跑」三选一（见第 6 节）。

任务简报中提到的 `T24.npy` **不存在**。缓存里没有 LSPR24 的逐序列时间数组；LSPR24 的逐流起始时间存在 `t24.npy`。

### 3.1 建缓存的脚本

- 第 57 行，分组与时间列清单：

- 第 74 行（LSPR23 分支）与第 87 行（LSPR24 分支），时间向量 `ts` 的唯一来源：

- 第 111–126 行，序列构造函数，排序键在第 115 行，`T23` 的取值在第 124 行：
  ```python
  def seqs_full(s, d, ts):
      """返回序列索引、掩码、所属实体、序列起始时间。"""
      key = np.array([a + "|" + b if a <= b else b + "|" + a for a, b in zip(s, d)], object)
      _, inv = np.unique(key, return_inverse=True)
      order = np.lexsort((ts, inv)); iv = inv[order]        # ← 主键 inv=实体，次键 ts=mTimestampStart
      bnd = np.flatnonzero(np.r_[True, iv[1:] != iv[:-1], True])
      I, M, E, T = [], [], [], []
      for a, b in zip(bnd[:-1], bnd[1:]):
          seg = order[a:b]; eid = iv[a]
          for i in range(0, len(seg), L):
              ch = seg[i:i + L]; p = L - len(ch)
              I.append(np.r_[ch, np.zeros(p, np.int64)])
              M.append(np.r_[np.ones(len(ch), np.float32), np.zeros(p, np.float32)])
              E.append(eid); T.append(ts[ch[0]])            # ← T23 = 段首流的起始时间
  ```
- 第 46–51 行的 `DROP` 集合把 `mTimestampLast` 直接丢弃，该列在本流水线里从未被读入内存。
- `np.lexsort` 是稳定排序，同一 `ts` 的流保持原始行序——与正文 3.4.2「时间戳相同的流按其在原始流表中的出现顺序稳定排序」一致。

## 5. 为什么会分叉

2026-08-11 冻结合同第 5 节末的条款针对的是合同自身的 Rust 物化链（77 字段、155 维、`available_ns` 排序、47,133 条候选序列）。
第三章 CPA-ELP 的实验不走这条链：它按 2026-08-13 用户裁决改用 Dijk 2026 附录 A 的 83 字段口径
（见 `thesis/AGENTS.md` 与 `.Codex/docs/RWKV/2026-08-13-Dijk2026协议逐项审计.md`），
数据入口是原始 CSV/parquet，序列由上述 Python 脚本现场构造。
字段预算这一条已被 2026-08-13 裁决显式取代，**排序键这一条则是随流水线切换被默默带走的，从未被显式裁决**。
这就是正文与合同对不上的成因：正文如实描述了实际跑的那条链。

## 6. 三个可选处置与代价

### 选项 A：只补边界说明，零重跑

- 3.4.2 第 43 行保留原句，其后补一句：序列顺序由流的开始时刻定义，同一实体内先后关系与流的开始次序一致。
- 3.5.1 第 41 行与第 43 行的在线论断加限定：`\tilde{s}_t` 与 `s_t` 相等的前提是前缀各流的完整统计均已就绪；
  按开始时刻排序时，实测 43.70%（LSPR24）位置的前缀含结束更晚的流，实际部署需等待这些流完成后才能给出该位置的分数。
- 3.6 的协议差异处登记：本章排序键与 2026-08-11 跨年度合同第 5 节不同，与 Dijk 2026 正文一致。
- 代价：约半天写作，无 GPU。**保住与 Dijk 的口径对位**（Dijk 正文即按 `mTimestampStart` 排序）。

### 选项 B：改按 `available_ns` 全量重跑

- 改排序键是一行改动，但缓存 `I23/M23/E23/T23/I24/M24` 必须重建（约 5 分钟 CPU，
  参照 `select_signal.log` 的 256 秒全解析），随后第三章全部数字失效。
- 已落盘的第三、四章实验日志末行耗时累计 **46,835 秒 ≈ 13.0 GPU 小时**
  （取 `runs/diagnostics/` 下 `ch3-*`、`ch4-*`、`dijk-repro` 各日志末行的 `[ Xs]`，扣除与 `run.log` 重复的 `controller.log`，未计 247 秒以下的短日志）
  （最大几项：`ch3-backbone-protocolA` 9,963.8 s、`ch3-hparam-fairsel-v2` 6,323.5 s、
  `ch3-baselines-param-matched` 4,242.6 s、`ch3-e5e6-v2` 4,223.1 s、`ch3-baselines-full/neural` 4,011.5 s），
  加上尚未回来的五骨干与 C11 权重再冻结、全部表与图重做，实际重跑代价按 **15–20 GPU 小时 + 数天返工** 估。
- 额外代价：与 Dijk 2026 的排序口径分叉，3.6 第 37 行的量级参照要重新措辞。

### 选项 C（建议）：主结果保持起始时间，另加一次排序键消融

- 用同一批代码把排序键换成 `mTimestampLast`，只重建 `I/M/E` 三个索引数组（`X/y` 不动，约 5 分钟 CPU），
  在冻结的 C11 配置上按种子 42 各跑一次，对比跨年度实体 AP。
- 单次训练参照 `dijk-repro/ch3_main.log` 的 566 秒、`interact_dijk.log` 的 588 秒，
  五骨干各一次约 **1 GPU 小时**；只做主骨干则约 10 分钟。
- 收益：把 3.5.1 的因果性从「论证」升级为「实测」——直接回答排序键对跨年度 AP 影响多大，
  同时保留与 Dijk 的口径对位。这是三者中证据密度最高、代价最低的路径。

无论选哪个，2026-08-11 合同第 5 节末应加一句适用范围注记：该条款约束 Rust 跨年度物化链，
第三章 CPA-ELP 的 dijk-repro 链按 Dijk 正文口径使用起始时间排序。
