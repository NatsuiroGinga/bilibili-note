# 服务器磁盘盘点与清理（2026-09-01）

## 结论摘要

**本次清理未能缓解 `/root/autodl-tmp` 的空间紧张**。原因是该盘（`/dev/md0`，100G，第三章四格实验的数据与运行制品所在处）与包管理器缓存、`/tmp`、`/root/.cache` 所在的容器根文件系统（`overlay`，30G）是**两个完全独立的挂载点**，清理后者不会释放前者的空间。

| 挂载点 | 用途 | 清理前 | 清理后 |
| --- | --- | --- | --- |
| `/dev/md0` → `/root/autodl-tmp` | 项目数据、`runs/`、`.venv`、原始数据 | 100G，已用 74G，余 27G | **100G，已用 74G，余 27G（无变化）** |
| `overlay` → `/`（含 `/root/.cache`、`/tmp`） | 系统盘、包管理器缓存 | 30G，已用约 12.5G | 30G，已用 2.8G，余 28G |

`/root/autodl-tmp` 的 27G 可用空间**未发生变化**。已确认安全删除的对象全部位于系统盘一侧，实际释放约 **10.1G**（系统盘），但对第三章四格实验真正需要的数据盘没有帮助。数据盘一侧目前没有找到任何落入"包管理器缓存 / `__pycache__` / `/tmp` 残留"这三类明确可删对象；找到的候选空间几乎全部是实验运行制品或确证重复文件，均已列入待裁决清单，未擅自删除。

## 阶段一：只读盘点

### 挂载结构（实测，避免了 `md0` 命名混淆）

```
/dev/md0 on /autodl-pub type xfs (ro, ...)          # 只读共享网盘，14T，与本任务无关
/dev/md0 on /root/autodl-tmp type xfs (rw, ...)     # 读写数据盘，100G，本任务目标
overlay on / type overlay (rw, ...)                 # 容器系统盘，30G，含 /root/.cache 与 /tmp
```

两个挂载点巧合地共享设备名 `md0`（AutoDL 环境的多卷命名方式），但容量、用途完全不同。裸 `df -h`（不带路径参数）会对同设备号做去重，只显示其中一条，曾一度造成"清理后用量未变"的误判——已用 `df -h /root/autodl-tmp /` 显式指定两个路径核实。

### 2. data-prepared 与受保护的 dijk-repro/cache 存在部分重复，但不建议动 data-prepared 一侧

`runs/data-prepared/ch3-protocol-a-raw83-shared-v1/generations/source-v1/split/M23.npy`（139169408 字节）与 `runs/diagnostics/dijk-repro/cache/M23.npy` sha256 完全一致（`b972447e...4b8617`）；`.../split/I23.npy`（278338688 字节）与 `dijk-repro/cache/I23.npy` 同样完全一致（`4a24b100...2f42d21`）。合计约 398M。

`dijk-repro/cache` 一侧任务已明确禁止删除，**唯一可能的操作是删除 `data-prepared/.../split/` 一侧的这两个文件**。但已核实同一目录下同名量级更大的 `raw/lspr23-raw83.npy`（5.06G）与 `views/lspr23-candidate-{a-standard,b-quantile}.npy`（各 5.06G）虽然文件大小与 `dijk-repro/cache/X23.npy` 完全相同，**sha256 全部不同**（分别为 `f581074a...`、`3f459cb6...`、`c59c6c90...`、`3c823cb1...`），说明这是标准化/分位数变换等不同预处理产生的不同数据视图，**不是重复文件**，不可删除。鉴于 `ch3-protocol-a-raw83-shared-v1` 这个目录名直接对应即将开跑的第三章 protocol-a 四格实验，即使 `split/M23.npy`、`split/I23.npy` 确证重复，仍建议不要在实验开跑前改动该目录，风险与收益（仅 398M）不成比例。

### 3. `runs/data-prepared`（22.00G）——判定为实验数据物化制品，未列入删除候选

内部最大项 `ch3-protocol-a-raw83-shared-v1`（15.79G）从目录名看直接对应即将开跑的第三章四格实验（protocol-a）。这类"物化数据"理论上可从原始数据重新生成，但重新生成需要重跑数据准备流水线、耗时未知，且目录名与即将开跑的实验强相关，**判定为不建议删除**，仅供知悉其占用体量。

### 4. `runs/candidates`（6.33G）与 `runs/baselines`（5.81G）——训练运行制品，未列入删除候选

除上述确证重复文件外，两目录下均为不同候选方案/基线的独立训练输出（检查点、表征缓存、日志），无法在不理解各目录科研含义的前提下判定"哪个已废弃、哪个仍需要"，全部保留。

### 5. `/root/autodl-tmp/ab-pilot`（167M）——独立于 `runs/` 的旧试点，性质不明

位于 `/root/autodl-tmp` 根目录，不属于 `thesis/experiments/llm_probe` 项目结构，包含 `.py` 脚本、`.log` 日志、两个 `.zip` 数据包（`TQH-C2_features_D.zip`、`TQH-C2_features_v110.zip`）与一个 `.npz` 缓存文件。最新文件时间戳 2026-08-08（约 3 周前）。因其中含疑似原始特征数据的 zip 包和脚本源码，不落入"明确可再生"范畴，**未删除**，仅供知悉。若确认是已废弃的一次性试点、其 zip 数据在别处有留存，可考虑整体清理，释放 167M。

### 6. `/root/miniconda3`（5.7G）——疑似未使用的基础环境，风险较高，未处理

`conda env list` 显示只有 `base` 环境（`/root/miniconda3`），`/root/miniconda3/envs/` 为空，自 2026-06-18 起无新环境创建痕迹。项目实际使用的是 `thesis/experiments/llm_probe/.venv`（uv 管理），与 miniconda3 base 环境无关联证据。`miniconda3/pkgs`（conda 自身的包缓存）仅 0.21G，真正占空间的是 `miniconda3/lib`（5.23G，base 环境的已安装包本身），**这不属于"conda 缓存目录"，而是完整的环境安装**，不落入本次授权的自主删除范围。**这是当前发现的单项最大潜在可释放空间（5.7G）**，但删除整个 conda 发行版风险明显高于本次授权的四类对象，需要用户确认该 base 环境确实未被任何脚本引用后再处置。
