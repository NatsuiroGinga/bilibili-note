# 规则注入 hook 实现报告

## 任务

写一个 `PreToolUse` hook：检测到特定命令时**注入提示**（不拦截），把「做 X 时必须注意 Y」
这类局部注意事项从「写进 AGENTS.md 全文常驻」改成「命中命令/路径时才送达」。
根因：本仓库规则加载路径已逼近 Codex 32,768 字节组合上限，且当天反复踩中同一批坑，
写进恢复卡也没能防止复发。

## 一、注入格式的确认依据（先查后写，非凭记忆）

`daily-coding` 技能明确要求：语法检查、导入检查、「以前见过这个接口」都不能证明运行时
属性存在，首次使用第三方接口必须先查文档。`PreToolUse` 是否支持"只注入不拦截"、注入字段
叫什么、是否依赖 `permissionDecision`，均属此类不确定接口，逐项查证如下。

**查证工具与来源**：`npx ctx7@latest library "Claude Code"` 定位到
`/websites/code_claude`（Source Reputation: High，Benchmark 86.7）后用
`npx ctx7@latest docs` 检索，命中片段指向 `https://code.claude.com/docs/en/hooks`；
随后 `curl -sL https://code.claude.com/docs/en/hooks.md` 直接拉取该页官方 Markdown 源
（3771 行），用 `grep -n` 定位并逐段核对，避免 WebFetch 摘要化丢失字段细节的问题
（WebFetch 对同一页面的摘要曾漏报关键表格，弃用其结论，只用于确认 URL）。

**核心结论（三条，均为原文逐字引用，出自 `hooks.md`）**：

1. **`hookSpecificOutput` 只强制要求 `hookEventName` 一项**，`permissionDecision`、
   `updatedInput`、`additionalContext` 是彼此独立的可选字段（"JSON output" 节，
   "`hookSpecificOutput` is a nested object for events that need richer control.
   It requires a `hookEventName` field set to the event name."）。
2. **"Add context for Claude" 一节的标准示例本身就只含 `hookEventName` +
   `additionalContext`，不含 `permissionDecision`**：
   ```json
   {
     "hookSpecificOutput": {
       "hookEventName": "PostToolUse",
       "additionalContext": "This file is generated. Edit src/schema.ts and run `bun generate` instead."
     }
   }
   ```
   `PreToolUse` 专属字段表（"PreToolUse decision control" 节）把 `additionalContext`
   单独列为一行，字段描述原文："String added to Claude's context alongside the tool
   result. **Ignored when `permissionDecision` is `"defer"`**."——只声明 `defer` 时被
   忽略，反证其余情况（含未设置 `permissionDecision`）下生效，二者不存在依赖关系。
3. **未输出 `permissionDecision` 时，工具调用按正常权限流程继续，既不拦截也不越权放行**：
   原文（"Structured JSON output" 一节的分步示例说明）——
   "Exit code 0 with no output means the hook has no decision to report, so the tool
   call continues through the normal permission flow. The hook can deny the call,
   but staying silent doesn't approve it."
   反面证据同样查证过：若显式设置 `permissionDecision: "allow"`，其效果是
   **"skips the permission prompt"**（跳过交互确认），这是本任务明确不要的副作用——
   本 hook 因此从不设置该字段，而不是设置成 `"allow"`。

**最终采用格式**：
```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "additionalContext": "<合并后的提醒文本>"
  }
}
```
命中即返回上述对象；不命中或任何异常均返回 `None`（等价于退出码 0 且无输出）。

## 三、新增文件

### `.Codex/hooks/on_demand_rule_reminder.py`（新建）

`PreToolUse` 命令行 hook，stdin 读 JSON，stdout 按上述格式写 JSON 或不写任何内容。
六条规则中五条作用于命令文本（`Bash`/`Shell`/`exec_command`/`functions.exec`），
一条作用于 `Edit`/`Write`/`MultiEdit`/`NotebookEdit` 的 `file_path`。

| # | 触发判定 | 判定方式 | 注入文案要点 |
| --- | --- | --- | --- |
| 1 | 命令含 `pdftotext` 或 `flash-extract` | 全文正则子串匹配 | 优先 `tools/pdf_to_fulltext.sh`（token 已配置，走 extract）；flash 限 10MB/20 页且丢公式符号 |
| 2 | `pkill -f` / `pgrep -f` 的真实调用 | `_command_segments` 拆 argv，`argv[0]` basename 属于 `{pkill,pgrep}` 且 `-f` 是独立 token（非子串误配） | 整行不得出现被匹配的完整字符串；需同时写文件拆成两次调用 |
| 3 | `git commit` 调用 | `argv[0]` basename `== "git"` 且 `argv[1] == "commit"` | 用 `-m "..." -- <路径>`，禁止 `git add .`；提交信息末尾不得有 Co-Authored-By |
| 4 | 写入 `AGENTS.md`/`CLAUDE.md` | `Edit`/`Write`/`MultiEdit`/`NotebookEdit` 的 `file_path`/`path`/`notebook_path` basename 命中 | **实测**（非估算）根到本目录规则链累计字节 / 32768 及占比 |
| 5 | 命令含 `torch.equal` 或「逐位」 | 全文正则子串匹配 | 先重置全局 RNG；骨干 `attention_dropout=0.2`/`ffn_dropout=0.1` |
| 6 | 命令含 `atomic_json` 或 `receipts/` | 全文正则子串匹配 | 数值先 `.item()`/`float()`；`torch.cuda.Event` 不可序列化，此前致 GPU 空转 15 小时 |

第 4 条的字节计算函数 `_rule_chain_bytes` 按仓库 AGENTS.md「规则发现与子域路由」节的
加载算法实现：从项目根走到目标文件所在目录，每层只取 `AGENTS.override.md`（优先）或
`AGENTS.md` 的**当前磁盘字节数**并累加，不是写死某次快照的数字——见下方验收第 5/12/13
组测试，对根目录（13760 字节，与 `wc -c AGENTS.md` 实测完全一致）与四层目录
（27996 = 13760 + 2684 + 11552，逐级用 `wc -c` 核对）两种情况分别验证。

**单命令多命中合并**：`build_additional_context` 把本次调用命中的全部规则拼进同一个
`additionalContext` 字符串（一个 `=== 头部 ===` + 若干 `[标签] 文案` 行），不产生多段
`hookSpecificOutput`。见验收第 8 组测试。

**静默失败**：`main()` 用一个 `try/except Exception` 包住 `handle_hook_input` 与 JSON
输出的全过程，任何异常直接 `return 0`，不打印、不设非零退出码，不设 `permissionDecision`，
因此既不会拦截命令，也不会因 hook 自身崩溃挡住工具调用。

### `.claude/settings.json`（修改）

改前先执行 `git status --short -- .claude/settings.json`，工作树干净，当前 `HEAD`
即改前快照，未创建空提交。在既有 `PreToolUse.Bash`（`prettier_guard.py`）条目旁新增
一个 `matcher: "Bash|Edit|Write"` 条目：

```json
{
  "matcher": "Bash|Edit|Write",
  "hooks": [
    {
      "type": "command",
      "command": "H=\"$(git rev-parse --show-toplevel)/.Codex/hooks/on_demand_rule_reminder.py\"; [ -f \"$H\" ] || H=\"$(git rev-parse --path-format=absolute --git-common-dir)/../.Codex/hooks/on_demand_rule_reminder.py\"; [ -f \"$H\" ] && python3 \"$H\" || true",
      "timeout": 5000
    }
  ]
}
```

`matcher` 语法依据同一份官方文档：正则子串匹配，`Edit` 会同时命中 `MultiEdit`、
`NotebookEdit`（文档原话："`Edit.*` matches both `Edit` and `NotebookEdit`"，本仓库
用不加锚点的 `Edit` 同理覆盖二者），故一条 matcher 覆盖全部六条规则所需的工具面。
`--git-common-dir` 回退写法照抄主仓库 `.claude/settings.json` 里 `sleep_guard.py`
条目的既有模式。JSON 语法用 `python3 -c "import json; json.load(...)"` 校验通过；
按仓库规则本仓库**禁止运行 Prettier**（`prettier_guard.py` 本身会 deny 该调用），
故未对本文件跑 `prettier --write`，仅做 JSON 语法校验。

## 五、不适合做成注入的规则及理由

任务简报给出的六条全部实现为注入，未发现需要排除的条目。但在实现过程中确认了
一个边界，记录供后续参考：**第 4 条（规则字节预算）本质是"文档写入前的资源检查"，
不是"命令语义风险提示"**，与另外五条的性质不同——它依赖对 `Edit`/`Write` 目标路径
做实时文件系统读取（而非纯文本模式匹配），如果后续要扩展到"編輯後会超限则提醒"，
需要能预估编辑后的字节增量（`Write` 的 `tool_input.content` 全量可算，`Edit` 的
`old_string`/`new_string` 只能算差值，`MultiEdit` 要求逐个 edit 累加），当前实现
只报告**编辑前**的已用量，未预测编辑后是否超限，此为已知简化，非缺陷——命中即提示
"新增前先看能否并入既有小节"已经把决策留给了执行者，不需要精确预测。

## 六、遗留风险

- 规则 1/5/6 用全文子串匹配（不做 `_command_segments` 级别的调用点识别），
  验收第 8 组已实测到一个可解释的"假阳性"：`git commit -m "pdftotext test"`
  的提交信息里出现了 `pdftotext` 字样，触发了 PDF 提取提醒。因为本 hook
  从不拦截、只注入一段可忽略的提示，此假阳性成本极低，为保持实现简单未做
  调用点级别的精确匹配（规则 2/3 因为有真实的"匹配到自身导致进程未杀"这类
  精度敏感后果，才做了 `_command_segments` 级别的 argv 解析）。
- `on_demand_rule_reminder.py` 目前只在本 worktree 分支（`codex/ch4-dtep-pbc-20260819`）
  存在。若该分支后续合并回主线或需要在其他分支/worktree 生效，需要显式同步该文件，
  `--git-common-dir` 回退逻辑只解决"脚本恰好只在主仓库存在"的情形，不解决"脚本
  只在其他 feature 分支存在"的情形。
- 未验证 Claude Code 实际运行时对 `additionalContext` 的字符长度截断行为
  （文档称超过 10,000 字符会落盘转预览），本 hook 单次注入文本远小于该阈值
  （最长的合并案例约 300 字符），未构造超限场景验证，标记为"待验证但当前场景
  用不到"。
