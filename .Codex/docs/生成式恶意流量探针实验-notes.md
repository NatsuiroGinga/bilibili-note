# 生成式恶意流量探针实验设计依据

## 已核对的本地事实

- 现有 `thesis/experiments/` 是面向 macOS/MPS 的旧实验环境，要求 Python 3.11 以上，并包含 CPU 版 PyTorch 配置。
- 旧目录的研究对象仍以 IDS2018、守恒不变量和两级检测解释为主，不能直接充当新生成式训练模型的实验入口。
- 当前研究问题卡将 H1 定义为：1.7B 探针在三个主数据集上超过多数类基线，并保持至少 95% 的结构化输出合法率。
- 数据集计划已选定 GeNIS-2025、CICIoT2023、HIKARI-2021 为三个主数据集，DEDALE-2025 为补充数据集。
- RTX 5090 服务器已有 `uv`，其独立环境位于 `/root/autodl-tmp/thesis/.venv`；后续项目仍应使用自己的 `uv.lock` 固化依赖。

## 方案比较

### 方案 A：独立可复现实验包

- 优点：隔离 Linux/CUDA 与 macOS/MPS 依赖；可以测试数据适配、划分和序列化；便于后续扩展基座和训练机制。
- 代价：首次需要建立配置、测试和产物约定。
- 裁决：采用。

### 方案 B：单文件快速脚本

- 优点：最快得到一次训练结果。
- 缺点：字段映射、数据划分和指标计算难以审计；后续多数据集和多基座实验会产生大量重复代码。
- 裁决：不采用。

### 方案 C：完全依赖外部数据集与训练接口

- 优点：下载和训练代码较少。
- 缺点：难以控制分组划分、泄漏检查、结构化输出和本地复现制品；社区镜像元数据不足时风险更高。
- 裁决：只把外部接口作为下载来源，不作为实验逻辑的唯一实现。

## 关键实验判断

### 为什么先做二分类

- 三个数据集的攻击类别体系不一致，直接统一多分类会把标签映射争议与模型可学性混在一起。
- 二分类能先回答生成式模型是否能稳定读取流量统计并输出合法标签。
- 原始攻击标签和归并后的攻击家族仍写入样本元数据，H1 通过后无需重新处理原始数据即可扩展任务。

### 为什么不生成解释和置信度

- 解释会增加输出长度、训练成本和解析失败率，但不帮助 H1 的可学性裁决。
- 自报置信度未经校准，不能直接当作可靠概率。
- 首轮输出固定为 `{"label":"benign"}` 或 `{"label":"malicious"}`，非法 JSON 直接计为错误。

### 为什么需要两种字段视图

- `canonical_core_v1` 只含三个数据集均可构造的字段，是跨数据集与主结论使用的视图。
- `dataset_full_v1` 可以保留单数据集特有字段，但只用于域内上限诊断。
- 若跨数据集输入含不同缺失字段组合，模型可能识别数据来源而不是攻击行为，导致跨域指标失真。

### 为什么禁止随机逐行划分

- 同一采集场景、会话或相邻流可能高度相似，随机逐行划分会把近重复样本分到训练集和测试集。
- 划分优先级应为采集场景、源文件、日期或会话组；无法恢复分组信息的数据源必须降低证据等级。

## 尚待实验回答的问题

- Qwen3-1.7B 的零样本能力、QLoRA 后宏平均 F1 和结构化输出合法率分别是多少？
- 共有字段视图相对特有字段视图损失多少域内性能？
- 模型收益是否在 GeNIS、CICIoT 和 HIKARI 三种环境中一致？
- 模型是否只是拟合数据集来源或单一攻击家族？
- 单次与三随机种子训练的 GPU 小时、峰值显存、吞吐率和推理 P95 延迟是多少？

## 当前不做

- 不在探针阶段引入 GRPO、RLOO 或其他强化学习算法。
- 不在探针阶段引入 PINN、Stiefel-LoRA 或 mHC。
- 不在 H1 通过前比较大量 3B 至 4B 基座。
- 不给探针方法命名，不把探针结果直接写成创新点结论。
