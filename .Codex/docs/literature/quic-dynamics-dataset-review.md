# 可启用 QUIC 动力学残差的公开数据集审查

> 完成日期：2026-08-03  
> 范围：2020—2026 年公开 QUIC 数据、官方实验归档、原始论文与 IETF 规范  
> 结论口径：数据是否支持 R2 物理残差，不评价其一般研究价值

## 结论

**没有发现一个公开数据集同时具备完整端点动力学、现代 QUIC、恶意/良性标签和无门槛下载。**当前可执行的方案不是继续等待“完美数据集”，而是采用两层证据合同：

1. **动力学教师主源：QUIC-MedNetCom。**它的字段完整 qlog 子集能提供包号、ACK、端点丢包、RTT、在途字节和拥塞窗口，体量约 0.7 GiB，最适合立即建立 R2 状态监督。
2. **现代协议补充：QUIC Interop Runner。**冻结少量现代 QUIC v1 正常、丢包、跨流和路径变化轨迹，补偿 MedNetCom 的 draft-27 年代偏差。
3. **模式兼容诊断：EPIQ 2020。**只用于不同实现和旧 qlog 格式，不作为主训练或最终安全测试。
4. **攻击标签：继续使用当前已冻结安全数据。**H23Q 虽是最强的 QUIC 攻击桥接候选，但需要人工审批且没有端点 qlog，已降为获批后追加的条件外部测试，**不得阻塞当前 R2 路线**。

上述三个 qlog 来源只能称为**条件 A 级**：每条轨迹必须通过字段完整性门禁。它们能启用本课题定义的核心 QUIC 动力学残差，但不能据此声称覆盖了 QUIC 协议栈所有控制器私有状态。

## “完整动力学”的可检验定义

本审查把 R2 所需信息分为核心和增强两层。

### 核心残差最低字段

| 残差 | 必需观测 | 不能接受的替代 |
| --- | --- | --- |
| 包号空间一致性 | Initial、Handshake、应用数据空间及包号 | 只有 UDP 序号或流内行号 |
| 确认关系 | ACK 范围或首次 `packets_acked`，能映射已发送包 | 仅通信方向翻转次数 |
| 在途字节守恒 | 发送、首次确认、端点判丢及 `bytes_in_flight` | 用总流字节或窗口吞吐代替 |
| RTT 更新 | 最新、最小、平滑 RTT 及 ACK 延迟语义 | 单纯相邻包时间差 |
| 丢包判定 | 端点 `packet_lost`、包号空间、时间或重排序触发 | PCAP 中“未看到包”或后验重传猜测 |

### 增强残差

- 拥塞窗口及拥塞状态转换；
- 探测超时、丢包定时器和重传标记；
- 拥塞控制器类型与参数；
- 路径迁移、路径最大传输单元、显式拥塞通知和多路径状态。

[IETF qlog QUIC 事件定义](https://quicwg.org/qlog/)覆盖上述多类事件，但大量字段是可选项。因此，**qlog 文件存在不等于字段完整**。[RFC 9000](https://www.rfc-editor.org/rfc/rfc9000)规定包号空间与 ACK 语义，[RFC 9002](https://www.rfc-editor.org/rfc/rfc9002)规定丢包、RTT 和拥塞控制语义；残差实现应以它们为语义基线。

## A 级候选逐项核验

### QUIC-MedNetCom：推荐主源

原始论文为 [On the Experimental Assessment of QUIC and Congestion Control Schemes in Cellular Networks](https://doi.org/10.1109/MEDCOMNET52149.2021.9501271)，官方仓库为 [Mohmoulay/QUIC-MedNetCom](https://github.com/Mohmoulay/QUIC-MedNetCom)。核验仓库提交 `f237a20360b83868a197488c5b557f53e4b7e53c`：

- 201 个受跟踪文件合计 695,847,552 字节；
- 89 个 qlog 合计 630,227,334 字节；
- 抽检样本含包号、ACK、RTT、在途字节和拥塞窗口；
- 一条抽检轨迹含 5 个明确 `recovery:packet_lost` 事件，记录丢失包号和重排序阈值触发。

优势是端点状态丰富、移动蜂窝环境真实、包含多种拥塞控制器。主要风险是 QUIC draft-27、模式老旧、无攻击标签、数据许可不明确以及字段异质性。

**接入成本：中等。**需要实现旧 qlog 事件名映射、时间单位归一化、包类型到包号空间映射、端点方向统一、字段缺失掩码及 `.json`/`.qlog` 重复去除。

### QUIC Interop Runner：推荐现代补充

原始论文为 [Automating QUIC Interoperability Testing](https://doi.org/10.1145/3405796.3405826)，官方代码为 [quic-interop-runner](https://github.com/quic-interop/quic-interop-runner)，滚动归档为 [interop.seemann.io/quic](https://interop.seemann.io/quic)。

抽检一条普通 qlog：包号 11943 次、ACK 范围 4070 次、恢复指标 541 次、在途字节 511 次、平滑 RTT 266 次。抽检 `transferloss` 服务端 qlog：68 个端点丢包事件、2437 次恢复指标、2436 次在途字节、793 次平滑 RTT、132 次拥塞窗口和 850 个 ACK 范围。

**接入成本：中等。**现代模式解析较直接，但必须自己冻结 manifest。归档路径、当前保留运行和总容量会变化；实现不支持 qlog 时相应轨迹不能纳入。

### EPIQ 2020：只作兼容诊断

原始论文为 [Same Standards, Different Decisions](https://doi.org/10.1145/3405796.3405828)，[官方数据页](https://qlog.edm.uhasselt.be/epiq/)提供原始 ZIP。实测：

- 压缩文件 19,057,641 字节，SHA-256 为 `88613d525975cb17ceb44724499d032adfd90fb7206700b192318952130342f6`；
- 解压 331,166,430 字节，共 64 项，完整性测试无错误；
- Firefox 样本没有拥塞窗口；quic-go 样本有 92 个丢包事件、丢包定时器、RTT、在途字节、拥塞窗口和包号空间。

**接入成本：中高。**数据很小，但模式和协议版本老，主要价值是验证解析器与状态模型没有绑定单一实现。

## 攻击桥接候选

### H23Q：条件备选，不阻塞主线

[H23Q 原始论文](https://doi.org/10.1016/j.cose.2022.103051)和[官方页面](https://icsdweb.aegean.gr/awid/h23q)说明数据含 10 类攻击、6 个 HTTP/3 服务端、60 个 PCAP，并提供 CSV。全文还明确说明配套 TLS 密钥随数据提供。

这使它能恢复线上 QUIC 包号、ACK 与部分帧，并近似计算 RTT 和在途字节；但它没有端点 qlog，不能给出端点首次判丢、探测超时和拥塞窗口。因此 H23Q 是 B+，不是 A。

下载需要大学或机构邮箱、用途说明和审批。当前合同不等待审批：

- 审批前：R2 使用 MedNetCom 与 Interop 做动力学教师，在现有冻结安全数据上做分类实验；
- 审批后：H23Q 只追加 QUIC/HTTP3 攻击外部测试与桥接消融；
- 审批失败：如实写明缺少公开的“攻击标签加端点状态”联合数据，不伪造替代真值。

### QUIC 隐蔽信道集：窄域诊断

[Zenodo 数据记录](https://doi.org/10.5281/zenodo.15076824)实际包含 16 个 CSV，总计 878.3 MB；页面的 31.1 GB 是累计下载流量，不是文件大小。[原始论文](https://doi.org/10.3897/jucs.154672)以 Retry Token 承载 ASCII 或 AES 隐蔽消息。它可测试协议专属安全特征，但不支持一般攻击或拥塞动力学。

## 其他 B/C 级来源为什么不进入主线

- [VisQUIC](https://arxiv.org/abs/2410.03728)有大量 PCAP 与部分密钥，但目标是 HTTP/3 响应数，缺端点恢复状态和攻击标签。
- [QUIC 旋转位数据集](https://doi.org/10.5281/zenodo.8305843)体量 17.7 GB，却只提供端点 RTT、包号和旋转位；不能补齐 ACK、丢包、在途字节或拥塞窗口。
- [CESNET-QUIC22](https://doi.org/10.5281/zenodo.7409924)和 [CESNET-QUICEXT-25](https://doi.org/10.5281/zenodo.17249078)适合服务分类和部署统计，不适合端点残差。
- [QUIC 网站指纹数据](https://github.com/jpcsmith/wf-in-the-age-of-quic)中的 QUIC 迹线是 WireGuard 隧道内的 QUIC/TCP 混合 PCAP，不含密钥或端点状态。
- [MonroeQL 论文](https://doi.org/10.1016/j.comcom.2023.01.003)说明真实实验先存 qlog，再聚合为 188 个特征；[作者官方仓](https://github.com/GCGImdea/NetPredict-Public)却只公开代码、合成数据和决策树，不含 MonroeQL 原始数据。
- [QUICsand](https://doi.org/10.5281/zenodo.5504169)明确因隐私不公开原始流量，只有软件制品。
- [RISE 实验 2](https://doi.org/10.5281/zenodo.19036616)的文件当前需要登录，元数据也没有证明包含 qlog，不能先假定可用。

## 推荐的数据合同

### 第一层：动力学教师

以“连接端点、包号空间、事件时间”为主键，将 qlog 归一为统一事件表：

- 发送包、接收包、ACK 范围、首次确认；
- 端点丢包及触发原因；
- 最新、最小、平滑 RTT；
- 在途字节、拥塞窗口、拥塞状态；
- 丢包或探测定时器；
- 实现、协议版本、控制器、路径和场景元数据。

每条轨迹生成 `field_availability_mask`。核心五项缺任何一项时降为 B，不参与完整残差训练，只参与对应的部分残差或观测诊断。

### 第二层：安全任务

安全数据继续保留现有分类标签和推理字段预算。qlog 私有状态只作为训练期教师、状态监督或残差目标，不进入分类器推理输入。

为避免标签泄漏和不公平比较：

- 路由器不能读取攻击标签、测试床名称、数据源 ID 或端点实现名；
- 基线与 R2 的分类输入必须相同；
- 只有 R2 的训练期辅助损失可以使用教师状态；
- 最终测试不参与字段门禁阈值、归一化或超参数选择。

### 第三层：桥接与外部验证

在 H23Q 未获批前，不强行合成带攻击标签的端点 qlog。可以先证明：

1. qlog 教师使独立状态误差下降；
2. 状态表征在现代 Interop 轨迹仍成立；
3. 加入物理监督后，现有恶意检测任务在固定开发集上提升且不增加良性误报；
4. 获得 H23Q 后，再检验 QUIC/HTTP3 攻击迁移。

### H23Q 条件方案

官方只给出 30 GB 总体量，没有公开文件级 manifest 或压缩率。完整保存建议预留 35—45 GB。若审批后先选 4—12/60 组，按均匀体量粗估 2—6 GB，但该数字只是预算，必须拿到清单后重算。

### 完整候选备份

MedNetCom 0.7—0.9 GiB、EPIQ 0.35 GiB、Interop 精选 1—3 GiB、H23Q 35—45 GB，总预留 45—55 GB。不要下载 17.7 GB 旋转位集、21 GB CESNET-QUIC22、28.2 GB QUICEXT 和 28 GB 网站指纹原始集，它们不能补齐核心残差。

## 可复现性与许可门禁

每个纳入文件必须记录：

- 官方 URL、下载日期、上游提交或运行时间；
- 原始 SHA-256、文件字节数和解压字节数；
- 论文 DOI、数据许可和再分发边界；
- qlog 模式版本、端点视角、时间单位与协议版本；
- 字段完整性和降级原因。

MedNetCom、EPIQ 和 Interop 的数据许可均不够明确。在论文公开结果前，应向作者确认数据再分发和派生制品许可。当前可以下载并做内部学术实验，但不能把代码许可自动解释为数据许可。

## 检索停止条件

在发现 QUIC 旋转位数据集和 QUIC 网站指纹数据后重新计数。随后连续三批检索分别覆盖：

1. “QUIC 数据、qlog、RTT、CWND、在途字节”；
2. 2020—2026 年机构仓储、测量制品和端点日志；
3. Zenodo DOI、`QLOGDIR`、`recovery:metrics_updated` 和互操作制品。

三批都只命中已知候选、工具或无关结果。端点字段、恶意标签、许可、容量、版本和访问限制等关键缺口均已核验，因此停止扩展候选池。

## 最终建议

**现在即可启动 R2 数据契约实现，无需等待 H23Q。**顺序为：

1. 下载或检出 QUIC-MedNetCom 小规模字段完整子集；
2. 建立 qlog 字段审计与统一事件表；
3. 冻结现代 Interop 补充轨迹；
4. 先验证状态误差和残差，再接入恶意分类；
5. H23Q 获批后追加攻击桥接，不改变前四步合同。

如果 MedNetCom 子集在现代 Interop 上无法迁移，应收缩为“跨实现端点状态监督”或重新生成现代受控 qlog，而不是通过修改最终测试样本来制造提升。
