# llm_probe 故障防复发手册

## 使用方式

本手册承接原 `thesis/experiments/llm_probe/AGENTS.md` 中不适合常驻上下文的详细故障案例。任务触发下列任一主题时，分析、实现、审查或恢复前必须完整读取对应章节；未触发时不默认加载全文。

通用规划、子代理开发、调试、审查和 Git 规则分别以仓库根 `AGENTS.md`、`writing-plans`、`subagent-driven-development`、`systematic-debugging`、`bug-detective`、`code-review-excellence`、`git-workflow`、`git-commit` 和 `git-push` 为准，本手册不复制技能正文。远程 Shell、同步、环境和恢复细节以同目录 `remote-script-execution-contract.md` 为准。

## 外部制品与任务边界

### 外部制品元数据

- 子代理简报引用外部数据制品时，规范网址、版本、大小和官方期望校验和必须从已批准的落盘计划逐字复制，禁止从旧下载日志或重定向地址重新推导。
- 明确区分“官方期望校验和已知”和“当前服务器文件实际校验和尚未计算”。实际校验未完成不得误写为官方元数据未知，也不得阻塞只负责实现校验逻辑的任务。

### 分派与计划冲突

- 子代理消息与已批准落盘计划的文件白名单或边界冲突时，任何编辑前暂停并向主代理确认；不得自行选择其一，也不得把口头消息默认为新版合同。
- 确认后只服从明确指定的落盘计划，将错误分派记为无效，禁止扩散到后续任务。

### 提交提醒

- 代码、配置、必要验证和防复发记录已形成职责单一、可复现范围时，主动提醒用户“当前可以提交”，说明建议范围和仍在运行的实验。
- 未获明确授权不得提交或推送，不得为等待提交阻塞实验。Git 操作必须读取对应技能，并遵守仓库根规则。

## 远程载荷与入口

### 受限网络失败归因

- 固定 SSH 或 rsync 入口在受限沙箱或审批上下文返回连接失败时，不得直接归因于服务器离线、平台链路、回环端口、SSH 配置或本机代理。
- 先对完全相同的只读命令申请获批的非沙箱网络权限并执行对照；只有非沙箱对照也失败，才能进入服务器身份、入口变化或平台状态调查。
- 非沙箱对照成功时，将先前失败记录为执行上下文限制，不得修改 SSH 配置、切换裸 SSH、刷新凭据或绕过固定入口。
- 涉及源码、配置、数据或制品传输时，每次申请必须明确引用用户对具体载荷、目的地和用途的授权。审批拒绝后停止传输，不得通过其他代理、临时协议或间接命令规避。
- 当前服务器入口切换后，正式同步前必须核对受管脚本内固定 Expect 路径与当前入口一致。若 `guarded_rsync.py` 仍硬编码旧 `/tmp/gpu-exec.exp` 或 `/tmp/gpu-rsync-push.exp`，其连接失败属于陈旧入口绑定，不得归因于当前服务器；先修复受管入口绑定并复审，禁止临时绕过统一启动器。

### 正式 GPU 入口禁止依赖同步

- 正式 GPU 包装器不得使用裸 `uv run`；裸入口会在正式运行前解析并同步项目依赖，可能直接访问包仓库，使网络超时被误报为训练卡住或科学失败。
- 已冻结环境中的正式 Python 入口统一使用 `uv run --no-sync`。依赖缺失、版本不兼容或导入失败必须由同一次正式入口运行时失败关闭并保留状态与非空日志，禁止在服务器联网补包。
- 若启动器状态长期为 `running`、日志为空、GPU 为 0 且只有 `uv run` 父进程，先只读检查进程树和最终日志。日志出现依赖元数据下载或重试时，根因属于包装器依赖同步；保留失败身份，以新包装器 SHA 和新运行身份重启，禁止复用旧目录。

### 非 ASCII Base64 载荷

- 向服务器传输含非 ASCII 文本的 Python 或 Shell 载荷时，先按 UTF-8 字节编码，禁止把 JavaScript UTF-16 码元直接当字节编码。
- 解码后先做合同允许的解释器语法检查并核对退出码；失败不得创建 `screen` 会话。内容不依赖自然语言时优先保持 ASCII。
- 日志必须区分制品编码失败与 CUDA、模型或依赖兼容失败，禁止把前者误判为计算环境问题。

### Rust 工具路径

- 从 `llm_probe` 根运行独立 Rust 工具时，发布二进制位于 `tools/<crate>/target/release/<binary>`，不是项目根 `target/release/`。
- 正式包装器从工具清单解析相对路径并在计算前断言存在。路径错误只算启动器失败，不得把未进入数据处理的退出码报告为审计失败。

### ns-3 双副本

- 场景源码同时存在项目副本 `ns3/*.cc` 与固定 ns-3 的 `scratch/*.cc` 编译副本。源码变更必须白名单同步两份文件，逐一核对相同 SHA-256，并更新受控参数中的源码摘要绑定。
- 只同步项目副本时运行器必须在计算前安全拒绝。保留原失败目录，使用新的 attempt 身份重启，禁止覆盖或复用失败目录。

## TQH-C2 B 档例外

### 触发条件

任何读取、物化、审计或审查 `dataset_version=1.0.1`、`profile=B` 或 `gate.json=FAIL` 的任务都必须应用本节。

### 接受条件

- `gate.json=FAIL` 默认拒绝。只有调用方显式声明 `dataset_version=1.0.1` 与 `profile=B`，才可评估例外。
- H1-H7 硬检查必须完整；失败集合非空且只能包含 H1、H3、H7；H4、H5、H6 必须明确通过。
- UID、五元组、元数据、标签合法性、严格整数修订计数、`invariant_violations=0` 和 `flows_malicious_c2>=50` 必须全部通过，才能签发 `accepted_b_v1_0_1_revised_counts`。
- A、C 档及未显式声明版本或档位的调用继续严格拒绝，禁止复用 B 档例外。

### 审计证据

- 正式包装器在 B 物化启动阶段必须执行与历史 `test_tqh_c2.py::test_b_gate_exception_*` 等价的运行时断言，并核对审计保留 `source_gate_status=FAIL`、原失败详情及 stale/revised 计数差。
- 历史精确节点结果只作既有证据。按当前规则不得把独立目标测试作为正式运行前步骤；除非用户重新明确授权，不单独重跑这些节点。

## SwanLab

### 动态标签长度

- 启动前用最终配置和动态运行身份构造完整标签列表，逐个断言长度不超过 `20` 个字符；只检查 YAML 静态标签不充分。
- 轮数、运行类型和协议状态使用 `epochs-<数值>`、`run-<类型>`、`protocol-complete` 或 `protocol-partial` 等短标签；完整语义保存在配置快照和运行元数据。

### 云端指标验收

- SwanLab `0.9.0` 的 `swanlab api run columns` 已弃用，可能对有指标的运行返回 `total=0`，禁止以此判断图表无数据。
- 云端先用 `run info` 确认运行存在且状态完成，再用 `run summary` 发现并核对标量键；只有需要逐点核查时才对已知键调用 `run metrics`，并实际检查图表页可见性。
- 本地 `swanlab_metrics.json`、上传完成提示或弃用接口中的任一单项证据都不能替代上述组合验收。

### 同进程多运行 401 与恢复

- SwanLab `0.9.0` 不得在同一 Python 进程中依次创建多个正式在线运行。已观察到首个运行 `finish` 后，第二次 `init` 复用失效 HTTP 客户端并返回 `401 Unauthorized`；每个“种子 × 变体”固定使用独立 Python 进程和独立 SwanLab 运行。
- 每个新在线运行初始化前必须在同一正式包装器内实际执行 `swanlab ping` 与 `swanlab verify`，保存短时门禁收据、两条命令的独立日志和退出码；只检查环境变量、配置文本或历史登录状态不算通过。
- 若凭据门禁连续失败，按凭据、权限或连通性故障停止；若首运行已经云端完成、第二运行初始化 401，且新进程中的 `ping` 与 `verify` 成功，则归类为进程内客户端状态或瞬时鉴权故障，不得作废已完成运行，也不得记为科学失败。
- 初始化 401 只能在保留本地失败状态和日志后，以新 Python 进程执行一次有界重试；禁止在同一进程反复 `init`、无限刷新凭据或对非 401 错误套用重试。第二次仍失败时停止并保留两次尝试证据。
- 恢复组合实验时，完整变体必须同时核对完成摘要、冻结绑定、共同初始化摘要、最终检查点、指标和预测，核对通过后只读跳过。只有无完成摘要、无指标、无检查点和无预测的零步初始化失败目录可以原子归档后重建；已有训练证据但缺少合法恢复合同的变体必须停止，禁止覆盖或猜测续跑状态。
- 汇总只在全部变体分别完成后生成；恢复、门禁和重试不得读取最终测试集，也不得因故障归档或非阻断审查延迟已经通过门禁的无关实验。

### 历史启动器证据的 schema 漂移

- 恢复门禁读取**历史**运行留下的证据文件时，必须按该文件当时的写入版本校验，不能按当前包装器的写入格式校验。已确认故障：`scripts/run_e2_hard_domain.sh` 后来新增了 `mode=` 行，而种子 42 原始 formal 启动器的 `binding.txt` 只有 `config`/`output`/`screen`/`run_id` 四个键；恢复门禁用当前五键集合做全等比较，把合法的 401 证据判为无效，连续第三次在训练前失败。
- 判据写法：对历史证据只强制**必需键子集**并限制键的允许集合，新增字段用“存在即校验、缺失取安全默认”；禁止对跨版本证据使用 `set(keys) == {...}` 全等比较。字段缺失导致无法证明的身份属性，必须由另一条不依赖该字段的结构性证据承担（例如 formal 与 resume 启动器目录名前缀不同）。
- 用真实历史文件而不是新写的夹具验证：先取回服务器上的实际证据文件，核对本机解码与远端 `sha256sum` 逐字节一致，再据其真实形态编写回归测试，并把该形态作为具名参数化用例长期保留。仅凭按当前格式构造的夹具通过测试，不能证明恢复可用。
- 禁止绕过：不得为迁就门禁去改写、补写或重排历史 `binding.txt`、`launcher.log`、失败收据和运行状态，这些是冻结的失败证据。
- 恢复类修复连续两次在训练前失败后，第三次必须先做只读取证——列出输出根、`variants/`、`failure-history/`、`recovery-environments/` 和原 formal 启动器的实际内容，并逐条比对门禁的每个判据——再改代码；不得同参数原样重试。

## 制品枚举与忽略规则

> 本节曾作为子节挂在 `## SwanLab` 下，导致只有"排查 SwanLab 故障"时才会被路由读到，而违规发生在"编写任意包装器的制品枚举"时，因此复发。现提升为独立章节，并在 `thesis/experiments/llm_probe/AGENTS.md` 的路由触发词中加入"制品枚举"。

### `rg --files` 必须关闭忽略规则

- `runs/` 受到 Git 忽略规则控制。任何包装器用 `rg --files` 枚举输入、模型、SwanLab 日志、检查点、结果或输出哈希时必须显式加入 `--no-ignore`；仅加入 `--hidden` 仍可能返回空结果。
- 本规则适用于**每一个**包装器，不是单个脚本的一次性补丁。已两次复发：先在 DistilBERT 启动器的 swanlog 验收行，后在 `scripts/run_e2_hard_domain.sh` 的 `validate_completed_output`。第一次修复只改了当时报错的那一行，同一文件其余枚举行未同步修改，这正是复发路径。
- `swanlog/` 由 SwanLab 自动写入内容为 `*` 的 `.gitignore`，即使运行目录本身未被上层规则忽略也会被整目录排除；服务端项目根位于 Git 工作树内时该规则同样生效，不能假设"服务器没有 `.git` 所以忽略规则不适用"，须用 `git rev-parse --is-inside-work-tree` 实测。

### 两种后果必须分开判断

- **误判失败**：枚举 SwanLab 日志或检查点用于验收时返回空，把计算成功的运行标记为失败。若主命令和日志管道退出码均为 `0`，运行状态与制品清单均为 `finished`，核心制品完整，但后置枚举失败，应先对同一路径比较默认枚举和 `--no-ignore` 枚举。确认仅为忽略规则后，对既有制品重验并纠正启动器状态，禁止重训或修改实验结果。
- **静默弱化绑定**：枚举输入目录用于 `sha256sum` 或空目录判断时，被忽略的文件不会报错，只是不参与哈希或使目录"看起来为空"。这类缺陷不产生失败信号，必须靠扫描发现，且会削弱冻结输入绑定的证据强度。

### 强制检查

- 修改或新增包装器时运行：`rg -n --no-ignore "rg --files" scripts/ src/`，逐条确认每个真实枚举语句都含 `--no-ignore`。
- 在该包装器的目标测试中断言脚本内所有 `rg --files` 语句都含 `--no-ignore`（参照 `tests/test_run_e2_hard_domain_wrapper.py::test_output_validation_enumerates_artifacts_without_ignore_rules`）。散文规则没有可执行约束时不足以防复发。
- 截至 2026-08-07 仍未修复的同类潜伏点，需逐个核验语义后处理，不得批量盲改：`run_shared_b0_physics_baselines.sh:220`（swanlog 验收，同一误判失败模式）、`run_e2_distilbert_formal.sh:70,73`（输入哈希）、`run_e2_seed42_baseline.sh:116`（输入哈希）、`run_shared_b0_distilbert.sh:120`（模型制品哈希）、`archive_r2_minimal_physics_fit_failure.sh:39` 与 `archive_r2_physics_fit_checkpoint_for_rebind.sh:53`（非空判断，可能把非空目录判为空）。

## 包聚合、时间与哈希

### 共享观察掩码与重复投影列

- 配置中的多个物理状态可以合法复用同一个观察掩码字段。构造 Parquet 投影列时必须按首次出现顺序稳定去重，禁止把配置列表的重复字段直接传给数据框选择器。
- 数据加载入口必须分别核验原始 Parquet、主键合并结果和 `concat` 前后列名唯一。失败收据至少记录源阶段和全部重复列名，不能只保留 Pandas 的通用 `InvalidIndexError`。
- 出现 `Reindexing only valid with uniquely valued Index objects` 时，先区分“Parquet 模式原生重复”与“字段投影人工重复”。不得改写冻结 Parquet、删除状态字段或修改公式来掩盖加载器投影缺陷。

### 交错样本

- 不得假设真实包表的 `sample_id` 在单个 Parquet 行组内连续。合法输入可以交错，但每个样本按 `packet_index` 恢复后必须连续。
- 聚合验证必须覆盖“`sample_id` 交错但 `packet_index` 连续”。大量处理前先冻结实际使用的 `sample_id` 再过滤聚合，除非合同明确要求全量。

### 时间字段合同

- `relative_time_ns` 与 `delta_time_us` 不可机械互推。旧提取器会把会话起点前但在 `1 ms` 匹配容差内的相对时间截断为 `0`，也会把 PCAP 时间戳回退造成的负间隔截断为 `0`。
- 聚合断言必须复现：首包间隔为 `0`；时间回退时后包间隔为 `0`；前一包相对时间为 `0` 时允许差值处于匹配容差；其余相邻包才要求精确量化一致。
- 禁止为追求单调时间改写冻结包行、重算旧序列哈希或丢弃合法包。

### 旧序列哈希类型

- TQH-C2 冻结候选的旧序列哈希保留历史数据框类型语义：含 UDP 空值的整行组读取后，非空 `tcp_flags` 以浮点数写入 JSON 哈希。
- 只在旧哈希兼容层复现该编码；发布包字段和新序列哈希仍使用整数语义，禁止为通过旧哈希改写正式字段。

## 固定合同与协议

### 真实清单优先

- 合成分配夹具只能验证算法行为，不能替代版本库中的真实固定清单。运行依赖受版本控制的 JSON 或 YAML 合同时，正式包装器必须直接加载真实配置，断言硬覆盖以及至少包含抽样算法、源样本总数的元数据。
- 真实配置的运行时断言和独立复审通过前不得物化。当前规则禁止为此另起独立目标测试；已有测试证据保留，用户重新授权时才补跑。

### 双重哈希绑定

- 测试或诊断若故意改写同时受协议文件和外部固定配置双重哈希绑定的制品，必须先更新夹具中的全部预期哈希，才能检查更下游的泄漏、重复或划分门禁。
- 漏更新任一绑定时，预期行为是先报哈希不一致；不得据此修改生产代码或放松校验。

### 冻结协议参数

- 用 `load_frozen_protocol` 审计 `data-protocol-v1.0-rc1/provisional/theory_selection` 候选时，显式传入候选版本、状态和阶段；默认参数只接受 `data-protocol-v1.0/frozen/final_tuning`。
- 出现“协议版本不一致”先读取 `protocol.yaml` 并比较调用参数。禁止改写已完成双物化的协议文件，也不得把候选状态伪装成最终冻结状态。

## 模型视图与生成式评测

### PINN 残差零坍缩与物理指标口径

- 协议物理残差不得经过可训练的状态转移头或残差投影；否则模型可把残差算子自身缩为零，而不满足物理方程。残差算子必须由固定方程组成，可训练参数量为 0，但必须显式包含模型预测状态并对该状态产生非零梯度。
- 正式物理训练入口必须先落零坍缩收据，证明旧投影不存在、非平凡构造输入的残差大于 0、预测状态梯度非零；任一协议缺少闭合方程所需字段时写明缺失字段并在训练前失败，禁止用状态平滑、有序性或真值常数差冒充动力学。
- UDP 的计划发送量与实际发送量之差只属于数据审计。只有引入预测应用积压状态，并具备窗口起止积压、计划、实际发送和应用丢弃量后，才可使用离散应用队列守恒残差。
- G3 主指标固定为训练区统计量标准化后的状态 MSE 与无量纲残差 MSE。逐簇制品必须保存逐状态或逐方程平方和、有效计数、单位和聚合定义；禁止仅改字段名，或把 MAE、RMSE 混入冻结 MSE 裁决。

### 新模型视图

- 新增确定性模型视图时，同时登记数据物化配置与 `ProbeConfig` 字段视图白名单；正式包装器必须直接解析真实训练配置并在加载模型前失败。
- 出现“未知字段视图”先比较配置值与白名单，不得改回语义不一致的旧名称绕过门禁。
- 进入生成式评测前逐条核对 `prompt`、真实标签来源、`completion` 单键 JSON 合同和解析器期望键。旧视图 `label` 与共享视图 `binary_label` 按各自合同严格解析，不得同时接受任意键。
- 禁止等全部 GPU 生成后才读取标签或发现字段缺失。相关检查属于正式启动阶段运行时断言，不另起独立预检或目标测试。

### 大规模评测加速

- 超过 `1000` 条样本的评测，在非最终测试样本上依次探测批大小 `8/16/32/64`，核对批量与单条贪心预测逐样本一致，记录吞吐、GPU 利用率、峰值显存和预计总耗时。
- 批量实现按输入长度分桶，输出按冻结 `sample_id` 顺序还原；每批增量写预测和完成清单，支持断点续评。仍逐条 `model.generate`、GPU 明显闲置或故障会丢失全部内存结果时不得启动全量，除非用户已知耗时和重算风险后明确保留串行基线。
- 批量通过后优先验证 PyTorch 缩放点积注意力；FlashAttention 只有兼容性与实测收益都成立才启用。候选答案似然评分可作受约束分类的额外效率结果，不能替代自由生成结构化输出有效率。
- 加速不得改变标签合同、测试清单、最大生成长度、评价指标或最终测试集用途。

## TCP 事件级阈值与在途字节快照配对

- 触发条件：ns-3 的 `SlowStartThreshold`、`CongState`、`BytesInFlight` 与 `Retransmission` trace 在同一仿真时刻先后触发，并用 NewReno 收缩方程计算事件级固定残差。
- 已确认根因：若阈值候选只保存新旧阈值，却在后续 `CA_LOSS`、`CA_RECOVERY` 或重传回调中读取可变的当前在途字节，读取值可能已经降为 0 或 1 个 MSS，造成跨事件时刻错配。该问题不是浮点容差、单位或 NewReno 方程错误。
- 正确做法：创建阈值候选时同时冻结在途字节及其观测标志；所有消费路径只读取同一候选快照，并以单一已消费标志保证恰好记录一次。
- 最小验证：先重跑历史失败配置和因分片停止而未运行的配置；全部通过后，只要场景源码锁变化，就必须用同一新源码锁从零重跑完整矩阵，禁止把旧成功收据与新结果拼接为正式池。
- 必须保留：旧失败根、失败配置的 CSV、矩阵状态、修复后目标集合状态、完整重跑状态、源码锁、逐配置收据和退出码。
- 禁止绕过：不得放宽 `1e-18` 门禁、修改 NewReno 方程或单位、删除失败配置、只补跑缺失项后宣称完整正式池。

## 容器内存上限、并发准入与大矩阵载入

- 触发条件：在同一台服务器上同时运行两个及以上会把宽表特征矩阵载入内存的实验（表格基线、展平历史矩阵、树模型 `DMatrix` 构造），或单个实验一次性构造行数乘列数超过十亿元素的稠密矩阵。
- 已确认根因：**资源门禁只检查磁盘与显存，不检查内存**，且余量判断读宿主机 `free` 而非容器 cgroup 上限。2026-08-12 C56 上 `free -g` 报 `754 GiB`，真实上限 `/sys/fs/cgroup/memory.max = 96,636,764,160` 字节即 `90 GiB`，相差 `8.4` 倍；三个启动器各写出仅含 `disk_free_gib`、`disk_usage_fraction`、`gpu_free_gib` 的 `resource-gate.json` 并全部 `passed=true`，随后整机内存耗尽重启。该问题不是单进程实现缺陷，也不是磁盘或显存不足。
- 排除的相近原因：`np.add.at` 散射慢不是原因。按真实形状实测 `np.add.at` 与 `np.bincount` 耗时比为 `1.0×`（`15.68 ms` 对 `15.38 ms`，单树 `261,839` 行 `64` 维），该内核每行每树只命中一个桶、索引无重复，重复索引惩罚不触发。禁止据此假设改代码。
- 正确做法：
  - 内存余量一律读 `/sys/fs/cgroup/memory.max` 与 `memory.current`（v2）或 `memory.limit_in_bytes` 与 `memory.usage_in_bytes`（v1）。**禁止使用 `free`、`/proc/meminfo` 或 `psutil.virtual_memory()` 判断容器余量**；读不到 cgroup 上限时拒绝启动，不得回退。
  - 启动前按 `行数 × 列数 × dtype字节` 估算稠密矩阵峰值并写入门禁收据，与实测余量比较，至少留 `30%` 安全余量。配置里声明 `maximum_process_memory_gib` 而门禁不测量，等同于没有上限。
  - 跨运行准入：不同启动器的 `worker.lock` 只防自身重复启动，互相不可见。并发前必须由统一入口检查是否已有 `flow_probe` 进程在运行，默认拒绝并发，需显式放行标志才允许。单入口实现见 `tools/memory_admission_gate.sh`。
  - 大矩阵优先用 `np.load(..., mmap_mode="r")` 而非全量读入。实测对照：使用 mmap 的进程 `VmPeak=22.92 GiB` 而 `VmHWM` 仅 `1.93 GiB`，常驻内存低 `12` 倍；未用 mmap 的同类进程需常驻 `12.08 GiB` 起。
  - 心跳必须记录当前进程 `VmRSS` 与容器剩余量。只记 GPU 与累计秒数的心跳无法在事故前暴露内存爬升。
- 最小验证：门禁脚本在无并发时返回 `0` 并打印真实 cgroup 上限；在有 `flow_probe` 进程运行时返回 `11` 并列出占用进程与合计 RSS；估算峰值超过余量时返回 `10`。三种分支都要用真实进程状态触发一次。
- 必须保留：`resource-gate.json`（含内存字段）、门禁标准输出、事故前后的 `run.log`（改名保留不覆盖）、`/proc/<pid>/status` 的 `VmHWM` 与 `VmPeak` 读数、cgroup 上限与 `memory.current` 读数。
- 禁止绕过：不得为让实验跑起来而调大声明上限却不测量；不得在读不到 cgroup 时按宿主机内存放行；不得把"上次单独跑通过"当作并发安全依据；不得因为容器重启后 `memory.events` 的 `oom_kill` 计数归零就断言未发生 OOM。
- 完整取证：[C56 三进程并发内存耗尽事故取证](../RWKV/2026-08-12-C56三进程并发内存耗尽事故取证.md)。

## 多变体训练脚本沿用单进程形态导致的串行浪费

- 触发条件：新写或扩写一个要跑多个相互独立训练变体的脚本（多骨干、多机制格、多学习率档、多消融配置），
  且该脚本是照着既有单变体或小规模脚本扩写的。变体数乘以单变体耗时超过 `30` 分钟时必查。
- 已确认根因：**照搬既有脚本的进程形态，没有针对本次运行规模重新判断并发**。
  `llm_probe/AGENTS.md` 第 43 行规定相互独立的训练变体**默认并行**，串行属例外且必须在收据记录精确原因；
  实际写出的却是单进程逐格顺序循环，既未并行也未记原因。
  2026-08-18 卷积 2×2 运行实测：`26` 次训练、每次 `20` 轮 `1000` 步，串行墙钟约 `114` 分钟；
  单格显存 `9,339 MiB`、卡上限 `32,607 MiB`，两格并行余量 `43%` 安全，可压到约 `57` 分钟。
- **同根因的前一次事故**：2026-08-17 跨骨干运行因逐字复制一个为 `30` 分钟运行写的脚本而无断点续训，
  实例重启后 `2` 小时 `46` 分、`14` 个格的结果全部丢失。两次的共同点都是沿用形态而非按规模设计。
- 排除的相近原因：**不是 GPU 慢，也不是数据加载瓶颈**。实测同一运行中数据已全量预载显存
  （`X23`、`I23`、`M23` 均 `.to(dev)`），取批为纯 GPU 索引，无宿主机数据通路；
  `BS=64`、`L=128`、模型约 `90` 千参数时单步 `10.7 ms`，此时功耗 `311.5 W` 对上限 `575 W`、
  利用率采样到 `0%`，瓶颈是核启动开销而非浮点运算。**据此调大批量或换更强的卡都无效**，
  且调批量会改变优化轨迹使跨骨干对照失效。
- 正确做法：
  - 写多变体脚本前先算 `单变体峰值显存 × 并发数 ÷ 总显存`。**余量不低于 `20%` 的最大并发数即为应取值**，
    低于 `20%` 的并发档一律不取。按 2026-08-18 实测，`9,339 MiB` 单格在 `32,607 MiB` 卡上应取 `2` 路，
    `3` 路余量只剩 `14%`，不得启用。
  - 启动器提供可配置最大并发数、独立状态锁与已完成幂等跳过，这三项是 `AGENTS.md` 第 43 行的明文要求。
  - 变体间只要共享可变制品、需隔离测量单进程效率、或存在 I/O 瓶颈才可串行，
    **并在状态收据写明精确原因**。非阻断审查与归档不构成串行理由。
  - 训练预算（批大小、序列长度、轮数、步数）属先注册的科学合同，**并行化不得触碰它们**。
    提速只能来自进程编排、核启动开销消除与调度，不得来自改变优化轨迹的参数。
- 最小验证：启动前打印每变体峰值显存估算、拟用并发数与余量比例；
  运行中至少一次采样确认并发进程数与显存占用符合估算；串行时收据中存在非空的串行原因字段。
- 必须保留：并发决策的估算记录、`nvidia-smi` 的显存与功耗采样、逐变体墙钟、以及串行原因（若串行）。
- 禁止绕过：不得因「既有脚本就是这么写的」而跳过并发判断；
  不得用调大批量、缩短轮数或减少变体来替代并行；不得在未记录原因的情况下串行。

## 在饱和的选择信号上断言跨运行复现

- 触发条件：门禁或断言要求「本次运行选出的超参数／检查点／档位」等于历史运行的同一选择，
  而该选择所依据的验证信号已饱和。**判据是可机械计算的**：
  候选之间的验证指标差小于该指标的逐 epoch 波动时，即属饱和，此时选择结果接近噪声。
- 已确认根因：**把在噪声上做出的选择当作可复现的确定量去断言**。
  2026-08-18 卷积 2×2 运行实测：`ch3_cnn_backbone_2x2.py` 第 `1165` 行断言
  `C00` 择优学习率必须等于预注册的 `2e-3`，本次实测选出 `5e-3`，`AssertionError` 退出码 `1`。
  而该运行的四格源年验证 AP 全部落在 `0.9998` 至 `0.9999`、逐 epoch 波动约 `3e-4`，
  候选间差异与波动同量级，**哪一档胜出本就不可复现**。
- **同脚本内的自相矛盾是最强的诊断信号**：同一事实在第 `944` 行的 `regression_gate_cell_selection`
  中只作 `differences.append(...)` 记录，在第 `1165` 行却致命。
  当同一判据在一处是诊断、在另一处是断言时，先查哪一处违反了已记录的合同，而不是先改数据或重跑。
  本例中恢复卡的合同明写「历史复现差异只作诊断，同次运行 `C00` 是科学基线」，故致命的一处是错的。
- **同类前科**：同一脚本的旧运行已因「源年验证 AP 高于历史值」被绝对复现门误判失败一次。
  两次都是把跨运行的数值一致性当作正确性条件。
- 排除的相近原因：不是训练发散、不是数据漂移、不是实现缺陷。
  六个机制格全部正常完成并落盘检查点，验证 AP 在 `0.99976` 至 `0.99994`，无异常。
- 正确做法：
  - 跨运行的选择差异**默认记为诊断并写入收据**，只有在会使结果无效时才致命
    （泄漏、划分错误、标签错误、字段不一致、设计签名不符属于会使结果无效）。
  - 需要与历史严格对齐的量，绑定的应是**设计与数据**（字段清单、切分、样本身份、
    训练预算、设计签名），不是**在饱和信号上选出的结果**。
  - 派生量必须取本次运行的实测值。本例中重复训练格用于刻画本骨干的波动幅度，
    必须与它所刻画的 `C00` 同配置，因此取本次择优值而非历史值；取历史值会去刻画一个
    本次运行中并不存在的配置。
  - 写断言前问一句：**这个量在重跑时会变吗？** 会变就不能断言相等。
- 最小验证：构造一次择优结果与历史不同的运行，确认脚本打印诊断行并继续，
  收据中存在该差异记录，且后续派生步骤使用的是本次值。
- **改脚本前必须先证检查点不会作废**：`DESIGN_SIGNATURE` 的输入字段决定检查点能否复用。
  本例实测该签名由格定义、规格、融合算子、`aux_w`、学习率网格、`phi_seed` 与训练预算算出，
  **不含脚本源码**，故修改控制流后签名仍为 `0508ebd8a57a338d`，六个格零重训。
  同步前用只执行到签名计算那一行的探测脚本比对新旧签名，不得凭「我只改了逻辑」推断。
- 必须保留：失败时的 `run.log` 另存不覆盖（本例为 `run.log.failed-assert-1644`）、
  断言的完整回溯、`progress.jsonl` 中已完成格的记录、以及新旧设计签名的比对结果。
- 禁止绕过：不得为通过断言而改动本次运行的选择结果；不得删除或移走检查点重跑；
  不得把「与历史不一致」直接写成实验失败或机制无效。

## 用先验概率替代可执行的核验

- 触发条件：下级代理或工具明确报告「某批检查项未核验」，而核验所需的制品可在数条命令内取得。
  **判据**：当「未核验项数」乘以「单项核验成本」低于一次事故的返工成本时，必须核，不得估。
- 已确认根因：**把「先验上不太可能出错」当作核验结论**。
  2026-08-18 差值审计实测：写作代理如实报告「八个可核验差值中一处分歧，另十七个因本地无全精度制品未核验」，
  主代理据此判断「已核的八个里七个一致，先验上不太可能有系统性错误」，未去核。
  服务器恢复后实际核验：三骨干的六个增益与交互全部吻合，
  但已发表基线的六个差值中**两个是错的**（`16.48` 应为 `16.47`、`10.88` 应为 `10.87`），
  与此前已发现的 `22.67` 应为 `22.66` 同根因，即用印刷值相减而非原始值。
  **三个错误全部落在「未核验」那一批里，先验判断的方向完全相反。**
- 加重情节：错误值 `16.48` 在同一轮对话中被主代理向用户复述至少五次，
  每次复述都增加它进入正式文档的机会。**未核验的数字不得反复复述，复述会使其获得未经证实的可信度。**
- 排除的相近原因：不是下级代理失职。它明确标注了未核验范围与原因（本地无全精度制品），
  边界给得准确。失败发生在主代理对该标注的处置。
- 正确做法：
  - **下级代理标注「未核验」时，主代理的默认动作是核，不是判断要不要核。**
    只有在制品确实不可达（服务器离线、数据已销毁、需重跑实验）时才允许暂缓，
    并把它登记为待办而非关闭项。
  - 制品不可达时**明确写成「待核验」并保留在阻断清单中**，不得写成「先验上无问题」。
  - 差值一律由原始值相减后取两位。**印刷值相减是一个独立的、会系统性偏差 `0.01` 的错误源**，
    它在单项上看不出来，只有逐项与原始值比对才能暴露。
  - 数值核验脚本应同时输出两法结果与判定，而不是只输出一种。
- 最小验证：取全精度制品重算全部差值，逐项打印「原始值相减／印刷值相减／文中所报／判定」四列；
  判定不一致项必须逐个订正并重新扫描全文命中。
- 必须保留：全精度制品的键路径与取值、两法对照表、订正前后的行号与原句。
- 禁止绕过：不得以「量级很小」「不影响结论」为由跳过订正——本例中三处订正确实都不改变结论，
  但这一点只有核完才知道，不能作为不核的理由。

## 用文件名、形状或字节数判断数据身份

- 触发条件：任何一次「打开一个 `.npy`／`.parquet`／目录就直接送模型或送变换」。
  **判据**：只要还没查到这份数据的变换谱系，或还没做过抽样逐单元对照，就属于身份未知，不得消费。
- 已确认根因：**把「同名、同形状、同 dtype、同文件字节数」当成「同内容」**。
  2026-08-25 实测：`runs/diagnostics/dijk-repro/cache/X23.npy` 与协议A冻结 `lspr23-raw83.npy`
  同为 `float32 (16353511, 83)`，文件字节数同为 `5,429,365,780`
  （`16353511 × 83 × 4 = 5,429,365,652` 加 `128` 字节 npy 头），
  `ls -la` 与 `shape` 完全看不出差别，但**有 `1,224,589,881` 个有限值单元不同**：
  产品侧 NaN `18,276,864` 个而缓存侧 `0` 个，前 20 万行最大绝对差 `251799984.0`，
  相对差 `>1e-3` 的单元占 `0.913`。第 0 列 `SrcPort` 同一单元：缓存 `-0.3009…`、raw83 `48778.0`、
  协议A候选A视图 `0.0932…`，三值互不相同。
  根因是该缓存的 X 已被 dijk 复现管线变换过：非有限值置 0 → 按 LSPR23 逐列均值和标准差标准化 →
  裁剪 `[-10, 10]`（可执行定义在 `tools/ch3_final_weights_assets/inference.py` 第 109–110 行）。
- 加重情节：目录名 `dijk-repro/cache` 不提示已被变换，且**该目录没有任何 `dataset-manifest.json`
  或 `cache-manifest.json`**；`X23`／`X24` 也没有被任何冻结合同登记哈希，
  而同目录的 `I24`／`M24`／`y24`／`s24`／`d24` 都有登记。有登记的成员反而让人误以为整目录都可信。
- 已发生的损失：同日两个子代理都被误导。表格 ResNet 的 LSPR24 评价（提交 `66873dd`）
  从 `X24.npy` 取特征后再叠加候选 A/B 变换，等于变换两次，与其源年训练消费的共享 Raw83 产品不同源，
  该轮结果口径存疑须重跑；CUDA-RWKV 因先做了抽样对照才当场发现。
- 排除的相近原因：不是「用了缓存」本身有错。判据是**训练侧与评价侧是否同源**：
  GRANDE 与 XGBoost 系列源年就训练在这份缓存上，继续读它口径自洽；
  表格 ResNet、CUDA-RWKV 按 `raw83 → 候选A → 候选B` 拟合，读它即错。
  也不是形状校验写漏了——`raw.shape != (N_FLOW, N_RAW_FEATURE)` 这类断言对本故障完全无效，
  因为两侧形状本来就相同。
- 正确做法：
  - 消费任何数据目录前先读该目录的 `README.md`；没有 `README.md` 也没有 manifest 的目录，
    **默认判为身份未知**，先补身份说明再消费。
  - 身份说明的权威副本放在 `.Codex/docs/RWKV/数据目录身份说明/`，
    文件名按 `README-<目标路径用连字符替换斜杠>.md` 命名，并部署到服务器对应目录。
    目前已有 `runs/diagnostics/dijk-repro/cache`、`runs/data-frozen`、
    `runs/data-prepared/lspr23-lspr24-bounded-quick-q0-v1` 三份。
  - 新建任何数据目录时**同时**写 `README.md`，第一句直接说明它是什么、不是什么。
  - 生产代码里每个读取该数据的位置留两三行注释说明数据身份，不要只靠目录级文档。
- 最小验证：取同一行同一列，打印「缓存值／raw83 值／目标候选视图值」三列；
  再统计 `np.isfinite` 计数与 `mismatched_cells`。三值不同或非有限计数不同即判定不同源。
  成本是一次 `mmap` 读几万行，远低于一次重跑。
- 必须保留：对照脚本路径、对照日志、两侧文件的绝对路径与 SHA-256、
  以及「训练侧消费的是哪份视图」的证据（配置里的 `cache_root` 或产品清单路径）。
- 禁止绕过：不得因为「形状对上了」「字节数一样」「以前就是这么读的」跳过对照；
  不得把标准化后的矩阵再送进候选变换；不得在没有身份说明的情况下把某个目录的结果写入总表或正文。

## 新增故障记录模板

根因定位和最小验证完成后，在本手册新增或合并一节，至少记录：

- 触发条件与受影响范围；
- 已确认根因及排除的相近原因；
- 正式包装器中的运行时断言或任务开始前必须读取的合同；
- 当前规则允许的最小验证和证据路径；
- 失败时必须保留的状态、日志、退出码和制品；
- 禁止采用的绕过方式。

只写可复用规则，不复制长日志。若规则已由远程合同、技能或上级 `AGENTS.md` 完整覆盖，只增加明确路由，避免重复常驻内容。
