## 1. 结论与推荐

### 1.1 两个链接的关系

**两者无直接关联，是两个不同数据集。**

- DOI `10.26249/FK2/MOCIY8` 指向德国奥斯纳布吕克大学的 **WEB-IDS23**。它的配套原始报告是 [arXiv:2502.03909](https://arxiv.org/abs/2502.03909)，不是 `2410.03728`。
- arXiv `2410.03728` 指向以色列 Technion 团队的 **VisQUIC**，全量入口由[VisQUIC 官方 GitHub 仓库](https://github.com/robshahla/VisQUIC)链接到 Dropbox。
- 两篇论文作者、机构、采集目标、数据格式和标签任务均不同，参考文献也未相互引用。

### 1.2 明确角色裁决

| 数据集          | 推荐角色              | 理由                                                                                                                           | 当前不应做的事                                      |
| --------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| **GeNIS-2025**  | **主训练/域内主证据** | 已有 PCAPNG、流 ID、起止时间、场景与分层攻击标签；当前 Qwen 分层任务和防泄漏前向切分已围绕它建立                               | 不把随机行级官方划分当正式证据                      |
| **WEB-IDS23**   | **域外测试**          | 具有 HTTPS/HTTP 成对 Web 攻击、SSH 攻击、细粒度标签与 HIKARI 同源 FlowMeter 字段；可检查冻结 GeNIS 模型在加密 Web 攻击上的迁移 | 不混入当前主训练；不用随机行级切分；不用它监督 PINN |
| **HIKARI-2021** | **次级诊断**          | 包含真实背景与加密合成攻击，但当前汇总 CSV 无绝对时间戳，只有弱端点分组                                                        | 不承担四窗口、时间外推或主结论                      |
| **VisQUIC**     | **仅参考**            | 有 QUIC/HTTP/3 PCAP、包时序、方向与配套密钥，可参考加密协议表征；但无恶意/良性标签                                             | 从当前恶意检测主训练和主性能表中排除；不全量下载    |
| **ns-3**        | **PINN 机制真值**     | 唯一提供队列、容量、入队、出队和丢弃真值的当前数据源                                                                           | 不替代公开数据的恶意检测证据                        |

**推荐顺序**：继续以 GeNIS 为主训练和域内证据；将 WEB-IDS23 作为冻结模型的二元域外加密攻击测试；HIKARI 保持次级诊断；VisQUIC 仅用于 QUIC 协议可观测表征参考。

## 3. WEB-IDS23

### 3.1 身份、作者、版本与许可

- **数据标题**：`WEB-IDS23 Dataset`。
- **作者**：Eric Lanfer、Dominik Brockmann、Nils Aschenbruck，奥斯纳布吕克大学。
- **Dataverse 版本**：1.0，2025-02-07 发布；创建时间 2025-02-06。
- **论文**：`Technical Report: Generating the WEB-IDS23 Dataset`，arXiv:2502.03909v1，2025-02-06。
- **许可**：Dataverse API 的标准 `license` 字段为 `NONE`，但自定义 `termsOfUse` 和官方 README 都显式指向 **CC BY-SA 4.0**。下载和派生数据时应按 CC BY-SA 4.0 处理，同时保留 API 字段差异记录。

### 3.2 格式、规模和采集环境

- **发布格式**：22 个按类拆分的 CSV 和 2 个说明文件；没有发布 PCAP。
- **总文件量**：3,285,730,370 字节，约 3.06 GiB。
- **样本数**：12,059,749 条 Zeek FlowMeter 流。
- **特征**：80 个 FlowMeter 特征，加 `service` 和 `traffic_direction` 为 82 个流量特征；另有 `uid`、`ts`、双向 IP 和标签元数据。
- **环境**：OpenStack 虚拟云，外部区 5 客户端，内部区 5 服务器（Web、SMTP、SSH、DNS、FTP），中间路由器使用 Zeek 捕获。
- **真实性边界**：客户端访问外部互联网，但攻击和主要良性动作由自建生成器在虚拟环境中产生；不是真实企业入侵记录。

### 3.3 加密范围

WEB-IDS23 是混合协议数据，不是纯加密流量数据集。

| 范围            | 内容                                                | 可确认的攻击流数 |
| --------------- | --------------------------------------------------- | ---------------: |
| HTTPS/TLS       | 暴力破解、拒绝服务、SQL 注入、反向 Shell、SSRF、XSS |        1,021,519 |
| SSH             | 暴力破解失败和成功登录                              |           68,525 |
| 明文/未声明加密 | HTTP、FTP、SMTP、端口扫描、主机扫描                 |   不计入加密子集 |
| 不包含          | QUIC、HTTP/3、VPN                                   |                0 |

良性文件未按协议公布计数，不能从总数反推加密良性流数。

### 3.4 标签与类别分布

- `attack`：二元攻击指示。
- `attack_type`：细粒度攻击类别。
- 文件名也直接编码类别，例如 `web-ids23_bruteforce_https.csv`。

**发布契约存在一处明确矛盾**：论文和 README 声称“21 类，20 种攻击”，但论文表 II、README 标签表和 Dataverse 文件均列出 **22 个实际文件标签：21 个攻击标签加 1 个良性标签**。

分布极不平衡：

- `portscan`：5,046,406（41.85%）；
- `hostsweep_Pn`：3,492,290（28.96%）；
- 前两类占 70.80%；
- `benign`：825,187（6.84%）；
- `smtp_enum`：仅 7 条。

不能用总准确率或随机行级宏平衡掩盖这种差异。正式评估必须报告每类召回、宏平均 F1、良性误报和按攻击运行的簇自助区间。

### 3.5 时间、主机与会话切分能力

| 维度     | 已有字段/结构            | 能做什么                        | 缺失                                               |
| -------- | ------------------------ | ------------------------------- | -------------------------------------------------- |
| 时间     | `ts`、`flow_duration`    | 排序、时间块和前向测试          | 没有官方训练/测试日期或攻击运行边界                |
| 主机     | `id.orig_h`、`id.resp_h` | 原始客户端/服务器分组和捷径审计 | 只有 5 个客户端和 5 个服务器，主机留出的独立单元少 |
| 流       | `uid`                    | 单流去重                        | `uid` 是单流 ID，不是多流攻击运行 ID               |
| 多流攻击 | 无显式关系               | 只能用端点和时间间隔推断        | 反向 Shell/SSRF 触发流与结果流的因果链未记录       |

**裁决**：它可用于冻结的跨数据集外测，但在发布方补充运行 ID 或原始捕获清单之前，不宜用于自身的主训练/测试性能声称。

### 3.6 已知泄漏与可学性风险

1. **文件身份泄漏**：每个 CSV 只存一类，文件名、加载顺序和 `source_file` 都不得进入提示或特征。
2. **显式标签泄漏**：`attack`、`attack_type` 只能作真值。
3. **端点与时间捷径**：IP、端口、绝对时间和服务类型可能与生成器迭代强关联。当前八字段提示不包这些身份字段，应继续保持。
4. **运行交叉**：随机行级划分会将同一攻击运行的相关流分到两侧。
5. **单流不可辨**：作者明确警告反向 Shell 和 SSRF 需要结果流。如果单流模型高分识别它们，应首先视为捷径学习候选证据，而不是性能优势。
6. **合成域过拟合**：攻击工具、版本、延迟随机化策略和固定服务器形成单一生成域。

### 3.7 论文基线

**无。**技术报告只介绍数据生成、分布和解读限制，没有分类器、数据切分、随机种子或性能数字。因此不存在可复用的“官方基线”。

## 4. VisQUIC

### 4.1 身份、作者、版本与许可

- **标题**：`Exploring QUIC Dynamics: A Large-Scale Dataset for Encrypted Traffic Analysis`。
- **作者**：PDF 题名页为 Barak Gahtan、Robert J. Shahla、Reuven Cohen、Alex M. Bronstein，Technion。arXiv Atom 元数据将 Cohen 和 Bronstein 顺序调换；报告以 PDF 题名页为主。
- **版本**：2024-09-30 首发 v1；2025-05-24 更新至 v6。
- **代码许可**：GitHub `LICENSE` 为 MIT。
- **数据许可**：Dropbox 数据未单独声明许可。不应在没有明文的情况下将代码 MIT 许可扩展到数据。
- **仓库版本性**：2026-04-07 默认分支提交 `e5febcc6a4867ba33a450a793d291869133bef31`，无标签或数据版本清单。

### 4.2 格式、规模和采集环境

- **原始格式**：每条迹线一个 QUIC PCAP 和同名 `.key`。
- **派生格式**：从 PCAP 转为 QUIC CSV，再转为按时间、包长和方向编码的 RGB PNG。官方全量分发说明只明确列出 PCAP/KEY ZIP 和 PNG ZIP，未明确说全量中包含中间 CSV。
- **规模**：100,664 条迹线，论文表 I 合计 44,514 个网页项；0.1 秒窗生成 5,408,166 张图像，0.3 秒窗生成 1,932,275 张图像。
- **采集**：两个跨洲住宅网络，四个月、覆盖全天不同时段；Headless Chrome 无痕模式、关闭缓存和会话恢复，顺序访问 Tranco URL。
- **协议**：QUIC + HTTP/3，不含 TLS-over-TCP、VPN 或恶意 QUIC 场景。
- **实现范围**：客户端固定为 Chrome；论文的 Chromium QUIC、Meta `mvfst` 和 Cloudflare `quiche` 多实现覆盖主要来自服务器端。

### 4.3 文件清单、总量和哈希的阻塞

官方 README 仅给出：

- PCAP/KEY 归档前缀 `VisQUIC`；
- PNG 归档前缀 `rgb_images`；
- GitHub 样例来自 `VisQUIC1.zip` 和 `rgb_images1.zip`。

本轮对两个官方 Dropbox 共享参数和 HEAD 请求均遇到对端连接重置，当前环境也没有可用的交互式浏览器。仓库和论文都没有备用的全量清单、字节数或哈希。

**因此，当前不能提供 VisQUIC 全量归档的精确文件名、大小和哈希，也不建议用户批准全量下载。**启动下载前应要求作者或共享页先提供：归档列表、逐文件字节数、SHA-256、数据许可、可解密迹线数和版本日期。

另有一处口径不一致：论文表 I 的“Websites”合计 44,514，当前仓库 `all_websites.txt` 只有 9,075 行。两者可能分别是成功网页项和当前 URL 清单，也可能属于不同数据版本；官方未说明，报告不做静默合并。

### 4.4 标签、类别分布与密钥边界

- **不存在恶意/良性标签。**
- 迹线目录保留服务器组、网页 URL 和迹线编号。
- 图像标签是通过解密获得的**窗内 HTTP/3 响应数**。
- Cloudflare 组有 44,700 条迹线，占 44.41%；前五个服务器组占 83.32%。
- 0.1 秒窗的训练分布中，响应数 0 和 1 约占 55.6%，15–20 合并尾组约占 1.5%。
- README 声称每个 PCAP 配同名 `.key`，但同时承认部分迹线由数据中未提供的其他密钥加密，不是全部迹线都能完整解密。

### 4.5 时间、主机与会话切分能力

| 维度      | 已有结构                               | 安全单元             | 问题                                              |
| --------- | -------------------------------------- | -------------------- | ------------------------------------------------- |
| 迹线/会话 | 每次顺序网页请求一个 PCAP              | **完整 PCAP**        | 不能把一个 PCAP 的图像分到多个分区                |
| 网站      | `server_name/website_name` 目录        | **完整 URL/网页**    | 同一 URL 有多次迹线，迹线随机切分仍可泄漏网页身份 |
| 时间      | PCAP 包时间戳，论文只报告“四个月”      | 时间前向的完整网页组 | 未公布精确采集日期或官方时间分区                  |
| 采集站    | 论文说两个住宅网络                     | 采集站整体留出       | 目录与 README 未公开站点 ID                       |
| QUIC 实现 | 论文称覆盖 Chromium、`mvfst`、`quiche` | 服务器实现留出       | 未发现逐迹线实现清单                              |

### 4.6 论文基线及其正确解读

论文将 32×32 RGB 图像用于预测 0.1 或 0.3 秒窗内的 HTTP/3 响应数。五次随机切分的窗口级 CAP 如下：

| 切分 | 0.1 秒 `CAP±1` | 0.1 秒 `CAP±2` | 0.3 秒 `CAP±1` | 0.3 秒 `CAP±2` |
| ---: | -------------: | -------------: | -------------: | -------------: |
|    1 |           0.93 |           0.97 |           0.91 |           0.96 |
|    2 |           0.92 |           0.96 |           0.90 |           0.97 |
|    3 |           0.93 |           0.98 |           0.91 |           0.95 |
|    4 |           0.94 |           0.97 |           0.92 |           0.93 |
|    5 |           0.91 |           0.96 |           0.92 |           0.94 |

`CAP±k` 是预测与真值相差不超过 `k` 的比例。因此摘要中的“97% accuracy”不是精确分类准确率，而是允许 ±2 个响应误差的容差准确率。

迹线级将窗口预测求和后，在 ±3 响应容差下：

- 0.1 秒窗：12,520 条测试迹线，平均 21.2 图/迹线，92.6%；
- 0.3 秒窗：12,142 条测试迹线，平均 7.5 图/迹线，71.0%。

### 4.8 已知泄漏与可学性风险

1. **同 URL 交叉**：同一网页有多次迹线，迹线随机切分仍可让模型记住网页内容和服务器。
2. **同 PCAP 图像交叉**：当前代码对图像随机切分，可以将同一迹线的时序片段放入两侧。
3. **高重叠窗口**：图像生成器支持 90% 重叠。若先生成再随机分图，会产生近重复样本泄漏。
4. **网站/实现/采集地共线**：服务器组、QUIC 实现、地理网络和网页内容之间存在关联，单一随机切分不能支持跨实现或跨地理泛化。
5. **标签不完整**：部分迹线不能用所给 key 解密，需要明确可用标签清单。

## 5. 与 GeNIS、HIKARI 和当前 Qwen + PINN 接口的比较

### 5.1 数据契约比较

| 维度          | GeNIS-2025             | HIKARI-2021                       | WEB-IDS23                           | VisQUIC                         |
| ------------- | ---------------------- | --------------------------------- | ----------------------------------- | ------------------------------- |
| 主任务        | 二元+攻击家族+子类     | 二元+六类                         | 二元+细粒度攻击                     | HTTP/3 响应数/网站元数据        |
| 恶意标签      | 有                     | 有                                | 有                                  | **无**                          |
| 加密范围      | 非加密专项             | HTTPS 良性与加密合成攻击          | HTTPS/HTTP 成对攻击 + SSH           | QUIC/HTTP/3                     |
| 原始包        | PCAPNG                 | PCAP 存在，当前工程主要用汇总 CSV | **未发布**                          | PCAP + key                      |
| 流表          | 125 字段 Argus/HERA    | 86 正式字段 Zeek FlowMeter        | 82 流特征 + 元数据/标签             | PCAP 转 QUIC CSV 为中间步骤     |
| 时间          | `StartTime`/`LastTime` | 当前汇总 CSV 无绝对时间           | `ts` + 流时长                       | PCAP 包时间，未发布官方日期分区 |
| 强分组        | FlowID + 场景 + 时间   | 当前只有端点对弱分组              | 流 UID + 端点 + 时间，无攻击运行 ID | PCAP + URL，采集站元数据未公开  |
| 真实性        | CyberRange 企业模拟    | 真实背景 + 合成攻击               | 虚拟环境全合成为主                  | 真实网站 + 受控浏览器，无攻击   |
| PINN 队列真值 | 无                     | 无                                | 无                                  | 无                              |
| 当前角色      | 主训练/主证据          | 次级诊断                          | 域外测试                            | 仅参考                          |

WEB-IDS23 相对 HIKARI 的增量是：更新的 Web 攻击、显式 HTTP/HTTPS 配对、绝对时间戳和更多攻击子类。HIKARI 的优势是真实背景流量与已审计的原始 PCAP/汇总 CSV，但当前汇总 CSV 无法恢复强时间分组。因此 WEB-IDS23 可取代 HIKARI 的部分“加密 Web 攻击域外测试”角色，但不取代 GeNIS 主证据。

| 目标字段         | WEB-IDS23                     | VisQUIC             | 语义边界                                        |
| ---------------- | ----------------------------- | ------------------- | ----------------------------------------------- |
| `total_packets`  | `fwd_pkts_tot + bwd_pkts_tot` | PCAP 包数           | 流对话 vs. 完整迹线/窗口                        |
| `total_bytes`    | 双向 payload 总字节           | 公开包长求和        | payload 字节 vs. 帧/IP/UDP 字节，必须选定统一层 |
| 包长均/最小/最大 | FlowMeter 双向载荷统计        | PCAP 包长统计       | 载荷长 vs. 网络包长                             |
| `iat_mean_ms`    | `flow_iat.avg` 需单位审计     | PCAP 时间戳差       | WEB-IDS23 README 未给出全部时间单位             |
| `packet_rate`    | `flow_pkts_per_sec`           | 包数/迹线或窗口时长 | 分母必须明确                                    |
| `byte_rate`      | `payload_bytes_per_second`    | 公开包字节/时长     | payload 层 vs. 网络层                           |

WEB-IDS23 与 HIKARI 字段同源，映射成本低；VisQUIC 需要新的 PCAP 提取管线。两者都不能因为“量纲相同”就宣称与 ns-3 的 0.1 秒 L3 瓶颈窗口物理语义一致。

### 5.3 分层生成标签空间

当前 GeNIS 主协议的家族标签只有 `benign`、`bruteforce`、`dos`，子类为 `benign`、`ftp`、`smb`、`ssh`、`hulk`、`slowloris`，域外子类为 `dos-icmp`、`dos-pushack`、`dos-udp`。

- WEB-IDS23 的暴力破解与 DoS 可映射到已有家族。
- SQL 注入、XSS、SSRF、反向 Shell、扫描、版本指纹和用户枚举没有当前家族标签。
- 不修改任务本体时，WEB-IDS23 只能做**二元域外测试**；不能静默把新攻击强行并入 DoS 或暴力破解。
- VisQUIC 没有任何可映射的恶意标签。

### 5.4 PINN 接口

当前 PINN 需要预测五个队列锚点，并使用容量积分、接收、入队、出队、入队前丢弃和出队后丢弃等监督量构造有限队列守恒残差。

WEB-IDS23 和 VisQUIC 都没有这些量。TCP 重传、流损失特征或 QUIC 包间隔都不等于瓶颈队列真值。两者可用于检测外测或公开观测表征，PINN 监督仍必须来自 ns-3。

## 6. 最小可执行采样与防泄漏方案

### 6.1 WEB-IDS23：冻结二元域外小样本

#### 下载门禁

本轮不下载。若用户后续批准，只下载以下 15 个 CSV：

- 6 个 HTTPS 攻击文件；
- 对应的 6 个 HTTP 对照文件；
- `ssh_login`、`ssh_login_successful`；
- `benign`。

总计 **884,728,230 字节（843.74 MiB）**。下载后必须先按第 8 节 MD5 逐文件验证，任何一个不一致就停止采样。

#### 输入审计

1. 只从数值 FlowMeter 字段派生当前 8 字段视图。
2. `uid`、`ts`、IP、端口、`service`、`traffic_direction`、`attack`、`attack_type`、文件名和行号只用于分组、审计和真值，不进入提示。
3. 报告每个源字段的缺失率、非有限值、单位和映射公式。`flow_iat.avg` 的单位未通过真实 CSV 核验前，不写死为毫秒或微秒。

#### 分组规则

WEB-IDS23 不用于本轮训练、阈值拟合或温度校准，因此不做 WEB-IDS23 内部随机训练/测试切分。模型、适配器和阈值从 GeNIS 完全冻结。

为避免重复运行支配统计，对每个类文件：

1. 按 `id.orig_h`、`id.resp_h`、`ts` 排序。
2. 以 `attack_type + id.orig_h + id.resp_h` 为基础键，相邻流时间差超过 30 分钟时启动新的 `capture_block`。
3. 样本只能以整个 `capture_block` 为统计簇；不对行做独立自助。
4. 如果任一类不能构成至少 5 个不重叠 `capture_block`，标记“分组信息不足”并停止该类性能声称，不回退到随机行抽样。

30 分钟是小样本审计的保守连续活动阈值，不是作者公布的运行边界。正式论文若使用 WEB-IDS23，仍应要求作者提供真实运行 ID 或重建原始捕获清单。

#### 最小样本量

- 14 个攻击文件每类 100 条，每个 `capture_block` 最多 20 条：1,400 条。
- 从 `benign` 中按 `service` 取 HTTP、SSL/HTTPS、SSH 各 100 条，同样至少 5 个块、每块最多 20 条：300 条。
- **总计 1,700 条**，作为一次性可行性外测。

如果良性文件的 `service` 值不能明确区分 HTTP、TLS/SSL 和 SSH，不用端口或 IP 猜测，而是停止服务匹配对照并记录字段契约阻塞。

#### 评估与停止条件

- 只评估二元 `benign/malicious`，不静默改家族或子类标签空间。
- 报告攻击宏平均召回、每类召回、良性误报、结构化输出合法率，以及六组 HTTP/HTTPS 召回差。
- 置信区间按 `capture_block` 做簇自助，不按流行自助。
- 该 1,700 条平衡小样本只裁决“是否值得做正式域外测试”，不支持自然比例或总体性能声称。
- 若发现 IP、时间、文件名或标签进入提示，或者任一类分组不足 5 个块，立即停止，不用降低分组标准补救。

### 6.2 VisQUIC：只做表征可行性检查

#### 全量下载门禁

在作者提供以下信息之前，不下载 Dropbox 全量数据：

1. 逐 ZIP 文件名、字节数和 SHA-256；
2. 数据许可是否与代码 MIT 许可相同；
3. 可成功解密迹线数和失败清单；
4. 迹线到采集站、绝对时间和 QUIC 服务器实现的元数据；
5. 论文 v6 数字所对应的代码提交、分区清单和种子。

#### 可用的最小检查

官方 GitHub `dataset-samples/` 已提供少量 PCAP/KEY 与对应图像。若后续只检查表征可行性，使用这个样例即可：

1. 将**完整 PCAP**视为不可拆分的最小单元。
2. 公开输入只从加密包的时间、长度和方向派生；`.key` 和解密 HTTP/3 字段只用于真值。
3. 以 PCAP 目录中的 URL/网页为上层组，不把同 URL 的不同迹线分到两侧。
4. 不对当前样例报告恶意检测指标；只记录八字段可提取性、单位、密钥解密成功率和窗口表征差异。

若将来作者提供全量清单，正式划分至少必须按**网页 URL 整体留出**，并对完整 PCAP 原子化；有采集站元数据时再增加跨站点外测。图像级 `random_split` 和 90% 重叠窗口交叉必须禁止。
