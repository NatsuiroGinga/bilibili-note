## 官方语义摘录

- 模型库第 32.2 节：流量控制层位于网络层与网络设备之间；根队列规则先入队，再运行并向设备发送，设备发送队列满时通过流控停止队列规则。
- 模型库第 32.2 节给出恒等式：`received = dropped before enqueue + enqueued`、`queued = enqueued - dequeued`。
- 模型库第 32.2.2 节：自定义根队列规则必须在地址分配前安装，否则地址助手会安装默认队列规则。
- 模型库第 32.3 节：`FifoQueueDisc` 只有一个内部 `DropTail` 队列，`MaxSize` 可按包或字节配置。
- 模型库第 27.4 节：点到点设备的设备队列入队不等于发送完成；设备队列出队才表示设备开始发送。
- 模型库第 23.2 节：接收错误模型位于概念物理层，丢弃应出现在 `PhyRxDrop`。
- 官方 `queue-disc.cc:675-704`：只有内部队列实际接受或移出项目时才触发队列规则 `Enqueue`、`Dequeue`。
- 官方 `fifo-queue-disc.cc:50-69`：超过 `MaxSize` 时调用 `DropBeforeEnqueue`，否则进入唯一内部队列。
- 官方 `point-to-point-helper.cc:34-39,241-249`：点到点助手默认启用流控，并把设备队列追踪连接到 `NetDeviceQueueInterface`。
- 官方 `point-to-point-net-device.cc:502-548`：发送前加入 2 字节 PPP 头，设备队列入队失败才触发 `MacTxDrop`；设备空闲时会立刻从设备队列取出并开始发送。
- 官方 `ipv4-queue-disc-item.cc:35-45` 与 `ppp-header.cc:67-70`：队列规则字节含 IPv4 头但不含随后加入的 2 字节 PPP 头。

## 已确认正确项

- 源码第 365 至 374 行在地址分配前安装 `FifoQueueDisc`，顺序正确，不会被默认 `FqCoDel` 覆盖。
- 源码第 355 行把设备队列设为 `1p`；结合点到点助手默认流控，可把主要积压留在 50 包根队列规则中，并避免正常路径的设备队列溢出。
- 源码第 394 至 422 行的六类回调名称和签名与 ns-3.48 类型一致。
- `offered = enqueued + dropped_before` 与源码第 177 至 181 行残差代数化简为 `Q_end - Q_start - enqueued + departed`，对根队列规则内部守恒成立。
- `DropAfterDequeue` 已在 `Dequeue` 后移出队列，不应再次从队列余额扣减；源码第 141 至 146 行的处理正确。
- 容量积分第 110 至 116、173 至 175、221 至 223 行对配置速率作分段积分；默认 6 秒突变位于 0.1 秒窗口端点时，窗口 59 的预算仍为旧容量，窗口 60 起为新容量。

## 候选发现

### 严重

1. 源码第 172 行只检查攻击开始，不检查攻击结束；攻击源在第 425、440 至 441 行于 11.5 秒停止，但 11.5 至 12.0 秒窗口仍标为攻击。固定验证契约第 24 行还把这一错误固化为窗口 50 至 119 全部恶意。
2. 源码第 94 至 101 行混合了三个不可直接相减的字节域：队列规则字节含 IP/UDP 头，设备与物理层字节另含 2 字节 PPP 头，接收端字节只含应用负载；传播时延又使事件跨窗口。只能声明根队列规则守恒，不能声明同窗端到端守恒。
3. `departed_bytes` 是队列规则出队，不是链路服务完成。`1p` 设备队列允许一个包等待，另一个包可能正在发送；因此第 175 行容量积分不能作为第 197 行 `departed_bytes` 的精确同窗服务量。容量突变时，在途包仍按旧速率完成，而积分从突变时刻立即采用新速率。
4. `scenario_id` 和 `group_id` 直接包含 `dos-udp`，绝对时间固定揭示攻击从 5 秒开始；若这些列、标签列或序列位置进入模型，构成直接或间接标签泄漏。窗口不得随机拆分，必须按完整运行分组。
5. 除随机丢包场景外，全部应用与事件均为确定性常量；改变 `seed/run` 不会改变轨迹。跨种子随机划分会产生近乎逐行重复样本，形成严重泄漏和虚假稳定性。
6. 第 177 至 181 行保存的残差是由同一组真值计数复算出的恒等式，候选矩阵中始终为零。它只能用于数据审计；若把该列直接作为 PINN 损失或输入，损失对模型参数没有梯度，不能证明物理约束训练有效。

### 高

1. 正常高负载为 4 乘 0.90 Mbps，即 3.6 Mbps 应用负载，对 5 Mbps 链路仅约 72%；UDP 攻击为 24.25 或 45.25 Mbps。缺少与攻击强度或拥塞程度匹配的良性闪拥控制，不能证明模型识别的是恶意性而非负载强度。
2. 容量突变场景能提供良性拥塞反例，随机丢包能提供下游损失反例，但条件均固定，且没有攻击加随机损失的交叉条件；不构成完整因子设计。
3. 源码没有检查 `TraceConnectWithoutContext` 返回值，也把队列模型、队列限制和容量元数据硬编码写出而未回读对象属性；追踪失效或配置漂移时可能静默生成零值或错误元数据。
4. 包模式队列限制为 50 包，但只保存队列起止字节，不保存起止包数；变长包场景无法直接验证队列是否超过 50 包。
5. 丢弃回调忽略 ns-3 提供的原因字符串，因此只能区分“入队前/出队后”，不能审计具体丢弃原因是否确为队列上限。

### 中

1. 默认仿真只支持完整 0.1 秒窗口；非整除时长的尾部不会输出，且没有显式拒绝或记录。
2. 攻击开始时间、容量突变时间、速率、队列大小和发送端数量未暴露为命令行参数，难以完成随机化、敏感性分析和独立复现。
3. `RateErrorModel` 未显式分配随机流编号；当前全局种子可复现，但对象创建顺序变化会改变随机序列。
4. 当前聚合队列没有来源级计数，无法区分良性与攻击包；只能证明受控干预下的队列响应，不能证明流级攻击归因。

## 运行证据

- 候选矩阵共 7 个场景乘 3 个种子，每组 120 个窗口，全部根队列规则残差为零，全部设备发送丢弃为零。
- `benign-capacity-shift` 三个种子的队列丢弃均为 775,324 字节，最大队列均为 52,600 字节；三个 UDP 攻击场景在三个种子下也分别给出完全相同的丢弃总量与最大队列。只有 `benign-random-loss` 的下游错误丢弃随种子变化。
- `dos-udp-high` 的窗口 116 至 119（11.6 至 12.0 秒）仍为 `malicious/dos/udp`，但队列、到达、离开、丢弃和接收均为零，直接证明尾部标签错误。
- `dos-udp-high` 窗口 113 的 `departed_bytes=63,120`，超过同窗 `service_budget_bytes=62,500`，直接证明队列规则出队不是精确链路服务完成量。
- 稳态窗口中，59 个队列规则包对应 `departed_bytes=59×1,052=62,068`、`sink_received_bytes=59×1,024=60,416`；随机丢包汇总又是 1,054 字节的整数倍，分别对应三种不同字节域。

## 启动相位扰动判断

- 每发送端加入独立的 0 至 40 毫秒启动相位扰动是必要且合适的最小修复，可以打破恒定源与 100 毫秒窗口边界的完全同相重复。
- 应显式分配 ns-3 随机流编号，并把各发送端实际相位、流编号、种子和运行号写入配置清单；匹配的基线/干预场景宜复用相同随机相位，形成共同随机数配对。
- 中等攻击首包间隔约 1.024 毫秒，高强度攻击约 0.546 毫秒；最晚 5.040 秒启动时，首包仍可在 5.05 秒窗口中点前发出。因此该范围与当前“中点状态”标签兼容。
- 5.0 至 5.1 秒仍是混合过渡窗口，不能称为全窗攻击。应输出实际攻击暴露比例或阶段标识，或从纯攻击训练样本中排除过渡窗。
- 该扰动只支持“结果对启动相位稳定”的结论，不能替代对速率、突变时刻、拓扑、包长和业务突发性的随机化，不能单独支撑广义多种子稳健性。
