# R2 存储解阻可行性审计

## 1. 裁决

**三选一裁决：需计划修订后可执行。**

本机具备读取 TQH-C2 原始源、执行任务 01 源预检和后续 TQH QUIC 派生处理的文件与软件条件；可以设计为仅把源锁和派生制品同步到服务器，从而避免上传整个约 98 GiB 的本机目录。该方案当前不能直接作为正式流程执行，因为冻结计划明确规定正式源预检、双构建和发布在服务器进行，任务 01 又把源锁代码版本仅绑定到 Git `HEAD`，而当前任务 01 和任务 03 的生产代码尚未进入该提交。

因此：

- **不是“本机可直接正式执行”**：现有冻结执行拓扑和代码来源绑定不允许。
- **是“修订计划后可执行”**：实现支持运行时外部源根，数据阶段支持纯 CPU，源锁只写逻辑路径。
- **不是“技术上必须扩容服务器”**：若正式批准本机预检、派生与校验后传输，服务器无需容纳 98 GiB 原始目录；若坚持现计划不变，则服务器仍必须释放或增加空间以满足任务 11 固定的 20 GiB 门槛。

### 4.2 源锁路径语义

任务 01 实现允许在运行时传入：

- `repository_root`
- `genis_archive`
- A/B/C `tqhc2_profile_roots`

`ExternalSourceRoots` 明确声明这些绝对路径不进入冻结源锁。`SourceArtifactLock`、GeNIS 成员锁和主源锁只序列化逻辑路径，`_assert_lock_paths` 在写出前再次拒绝绝对路径。因此，本机执行不会天然把本机路径泄漏到源锁，服务器也可以按同一逻辑路径消费派生制品。

### 4.3 Git 绑定阻塞

本机 Git `HEAD` 为：

`acdf98ba5cc776f7c19495fc53b1164e916eb33c`

但下列任务 01 文件当前均为未跟踪文件：

- `configs/r2_protocol_data_v1.yaml`
- `src/flow_probe/r2_protocol_contract.py`
- `tests/test_r2_protocol_contract.py`

任务 03 的生产文件和测试文件也为未跟踪文件。任务 01 的 `_current_git_commit` 只执行 `git rev-parse HEAD`，不会检查脏工作树，也不绑定实际执行文件的 SHA-256。因此现在在本机生成源锁，会把未进入 `HEAD` 的实现错误标记为上述提交，不能作为正式来源证明。

## 5. GeNIS 与 A/C 历史快照

### 5.1 GeNIS

本机只找到一份 `raw/datasets/GeNIS-2025/2-flows.zip`，大小为 `14,520,320 B`；正式合同要求 `380,755,720 B`。前次恢复预检已经确认本机副本损坏且禁止使用，并确认服务器正式归档大小、MD5、SHA-256、中央目录和 11 个物化成员均通过。

当前 `verify_frozen_inputs` 要求同一次调用同时核验 TQH 和 GeNIS，并在未传入 `genis_archive` 时直接失败。因此，本机若不取得可读的正式 GeNIS 归档，不能直接生成完整的三份源锁；当前实现也没有把“本机 TQH 子锁”和“服务器 GeNIS 子锁”安全合并的公开接口。

### 5.2 A/C 提取器快照

A/C 来源清单登记：

- 大小：`46,140 B`
- SHA-256：`7daa2b2de3878660bb02860f416892d5a64aba3cc7edf5de561faa575047a617`

本机唯一 `src/flow_probe/tqh_c2.py` 为 `55,523 B`，SHA-256 为 `c681639af7de97bf4902341e0e51066455492df968769be8d1e6cfaefb4fcdc0`。Git 全部分支与 reflog 对该路径只找到提交 `8160e747c4f801f2c1bc814fadb590f8537782b8`，其文件仍为 `55,523 B` 且哈希相同；未发现其他本机 `tqh_c2.py` 快照。

该快照当前不可从本机工作树或 Git 历史恢复。它不是本机预检的硬执行阻塞，因为配置已把 A/C 标为 `approved_manifest_only_blocked`，实现会把对应证据状态写为 `blocked` 而不读取不存在的旧源码；但任何正式报告都不得把 A/C 提取器改写成已实物核验。

## 6. 现计划为何不能直接采用本机方案

冻结计划虽然规定数据预检、构建、审计和验证全部支持纯 CPU，但同时作出了以下正式执行约束：

- 正式 GeNIS 原件固定为服务器路径。
- 第 8 节标题和步骤明确为“正式服务器执行顺序”。
- 正式顺序第 2 步要求在服务器运行任务 01 并生成源锁。
- 任务 01 实现报告要求由后续服务器包装器提供仓库根、TQH 根和服务器 GeNIS 原件。
- 任务 11 包装器在创建任何临时构建目录前要求可用磁盘不低于 `max(20 GiB, 3 × 预计发布字节数)`。

前次恢复预检记录服务器剩余 `15,462,395,904 B`，约 `14.40 GiB`，低于固定 20 GiB 门槛。仅把任务 01/03 移到本机而不修订任务 11、正式执行顺序和制品移交合同，仍无法按当前计划完成服务器双构建。

## 7. 最小修订动作

1. **修订正式执行拓扑。** 在计划中明确批准“本机只读源预检与 TQH QUIC 派生，服务器只读复核源锁和接收派生制品”的混合模式；同时修订第 8 节正式顺序和任务 11 的主机、磁盘及恢复语义。
2. **修复代码来源绑定。** 在正式签锁前把任务 01/03 的实际生产文件、配置和锁文件进入明确提交，并要求干净工作树；或把实际执行文件哈希、`uv.lock` 哈希和提交同时写入源锁，不能只记录 `HEAD`。
3. **选择 GeNIS 方案。** 推荐把服务器已核验的 `380,755,720 B` 正式归档以只读方式提供给本机，再由现有单进程接口生成完整源锁；另一方案是新增经审查的 TQH/GeNIS 独立子锁合并合同。禁止使用本机损坏副本。
4. **保持 A/C 阻塞证据。** 不等待不存在的旧快照才能启动，但源锁、审计和报告必须继续记录 `approved_manifest_only_blocked` / `blocked`。
5. **冻结传输回执。** 本机完成后只同步三份源锁和任务 03 派生制品；服务器按清单逐文件复核大小、SHA-256、行数、模式、列顺序和逻辑路径，禁止把“传输成功”替代正式验收。
6. **补任务 03 实物基准。** 先用批准的小型样本测量哈希桶、排序和最终 Parquet 的放大率，再冻结正式 `work_dir` 空间门槛；当前估算不能代替任务 11 的门禁修订。

## 8. 本机磁盘新增量估算

本机当前可用空间为 `63,829,420 KiB`，约 `60.87 GiB`。

- 任务 01 三份源锁：预计永久新增小于 `1 MiB`。
- 若把服务器正式 GeNIS 归档提供给本机：永久新增 `380,755,720 B`，约 `363.1 MiB`；若采用只读挂载，则本机不新增该空间。
- 任务 03：根据当前 `35,235` 个候选样本、`26,014,736` 条上游包行和 `266,795,115 B` 压缩包表，预计永久派生制品约 `0.2–0.8 GiB`，稳定哈希桶和排序临时空间约 `0.5–2.0 GiB`。
- 建议为任务 01 加任务 03 预留至少 `3 GiB` 本机峰值空间；若本机保存正式 GeNIS，再预留约 `0.36 GiB`。

该估算仅覆盖源预检和 TQH QUIC 派生，不覆盖完整 R2 双构建、ns-3 矩阵或训练。任务 03 尚未在本机原始实物上跑正式基准，永久与临时空间区间是基于现有压缩输入规模的保守工程估算。

## 9. 主要风险

- 正式预检仍需首次完整读取并哈希 `52,472,203,208 B` 合同源文件；本轮只核对存在性和大小，未证明内容哈希仍一致。
- 当前任务 01/03 代码未进入 Git `HEAD`，直接签锁会形成错误代码来源证明。
- 本机缺少有效 GeNIS 正式归档，现接口不能只凭服务器已有 GeNIS 核验结果生成完整源锁。
- A/C 提取器历史快照不可恢复，必须永久保留阻塞证据，不能提升为“已核验”。
- 本机与服务器必须固定相同 Python/PyArrow、`uv.lock`、配置和代码哈希；否则 Parquet 字节级确定性和后续双构建比较可能失败。
- 若不修订正式执行拓扑，服务器约 `14.40 GiB` 可用空间仍达不到任务 11 的 20 GiB 固定门槛，届时只能释放空间或扩容。

## 10. 终点

本审计的终点是确认替代路径的可行性，不是启动执行。结论为：**批准并审查上述最小计划修订后，可以在本机完成 TQH 源预检和 QUIC 派生，只同步小型源锁与派生制品，从而避免上传约 98 GiB 目录；在修订完成前不得把该路径作为正式 R2 数据流程。**
