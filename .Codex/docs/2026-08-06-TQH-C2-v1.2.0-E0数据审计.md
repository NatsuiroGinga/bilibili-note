## 6. 27 列实际模式

48 个逐单元表和 4 个聚合表全部采用同一 27 列、同一类型模式：

- 浮点：`ts`、`duration`、`orig_bytes`、`resp_bytes`。
- 整数：`orig_pkts`、`resp_pkts`、`orig_p`、`resp_p`、`orig_ip_bytes`、`resp_ip_bytes`、`missed_bytes`、`interval_s`、`jitter_pct`、`y`。
- 字符串：`uid`、`orig_h`、`resp_h`、`proto`、`conn_state`、`history`、`ja4`、`ja4s`、`ja4h`、`profile`、`encryption_profile`、`capture_id`、`label_raw`。

README 只明确写 D 为 27 列，没有“26 特征”声明。实际口径必须区分：

- 27：全部存储列。
- 26：只排除 `y`，但仍含直接标签副本 `label_raw`，不能称为安全检测特征。
- 25：同时排除 `label_raw` 与 `y` 后的非目标列，但仍含身份、地址、端口、采集条件和连接状态捷径。
- 7：本审计建议 E1 默认共同使用的无明显身份捷径字段。

因此，**以实际 27 列模式为准**；“26”最多是排除 `y` 后的存储列计数，不是模型输入合同。

### 7.1 Parquet 缺失

| C | 0 | 23,292 | 23,292 | 1,990 |

Parquet 真空值只出现在 `history`，共 12,490。空字符串只用于指纹字段。数值字段没有 NaN、无穷或负值，UID、目标和组元数据没有缺失。`missed_bytes` 在每个测试床内都只有一个非空取值，默认不作为共同输入。

### 7.2 重复

- 原始 UID 全局重复：0。
- `capture_id+uid` 重复：0。
- 原始完整行重复：0。
- 特征完整行重复：0。
- 去除 `ts`、`uid`、`capture_id`、`label_raw`、`y` 后的重复特征：2,352 个超额行，涉及 1,318 个签名组。
- 上述重复全部位于同一 capture 内；跨 capture、跨测试床和冲突二元标签均为 0。

因此，完整 capture/cell 分组可把重复留在同一分区。测试床聚合表只是逐单元表的完整聚合，二者内容逐行一致；训练读取时必须二选一，不能把逐单元表和聚合表同时拼入数据集，否则会人为复制全部 152,765 行。

## 8. README 与实际制品差异

### 8.1 36 与 48 单元

README 开头已声明 D 是第四个测试床，文件表也列出 D，但概览和总量仍写 3 个配置、36 个单元。实际四包构成 A/B/C/D 各 12 个单元，共 48 个。**36 是未同步 D 的旧概览，实际应为 48。**

### 8.2 A/C 行数

README 声称 A+C 共 218,227 行，其中 A 为 181,556、C 为 36,671。该数值与 manifest 汇总完全一致，但当前逐流标签和特征只有 119,441 行，相差 98,786 行。A+C 的 `malicious_c2` 数仍同为 24,842，差异集中在非目标流。

22 个 A/C 单元共有 53 个 `manifest.result` 计数字段与实际逐流标签不一致；A/B/C 的校正计数文件与当前逐流标签差异为 0，逐单元特征和聚合表也完全一致。因此本阶段以当前逐流标签、校正计数和特征表为实际制品口径，不使用旧 manifest/README 总行数训练或汇报样本量。

### 8.3 B 与 `unknown`

README 的 B 分段表描述约 8% 至 26.5% 的 `unknown`，当前 B 实际只有 `benign` 21,472 行与 `malicious_c2` 324 行，`unknown` 为 0。README 分段流量规模也不对应当前 B 小包。E1 只使用实际制品计数。

### 8.4 C 加密配置命名

C 的 23,292 个特征行写 `encryption_profile=http`，逐流标签与 manifest 写 `http_aes`。`capture_id`、`profile`、间隔和抖动均一致，因此不影响组连接；但该字段既不一致又与测试床固定绑定，必须禁止进入检测输入。

## 9. 字段角色与捷径

### 9.1 实际捷径关联

`shortcut_statistics.csv` 只对字段取值做 SHA-256 去标识后建立与 `y` 的列联计数，没有保存取值，也没有训练模型。下表的“纯度增量”是同一制品内按字段取值多数标签得到的加权纯度减去全局多数类纯度，仅用于识别捷径，不是开发集或最终测试性能。

| 字段 | 正类不同值数 | 负类不同值数 | 共享值数 | 集合完全分离 | 纯度增量 |
| --- | ---: | ---: | ---: | --- | ---: |
| `resp_h` | 19 | 144 | 0 | 是 | 0.1776 |
| `resp_p` | 48 | 10 | 5 | 否 | 0.1697 |
| `history` | 29 | 229 | 14 | 否 | 0.1620 |
| `conn_state` | 7 | 8 | 6 | 否 | 0.0841 |
| `orig_h` | 96 | 91 | 84 | 否 | 0.0783 |
| `capture_id` | 48 | 48 | 48 | 否 | 0.0347 |
| `profile` | 4 | 4 | 4 | 否 | 0.0152 |
| `encryption_profile` | 4 | 4 | 4 | 否 | 0.0152 |
| `orig_p` | 12,162 | 16,851 | 12,034 | 否 | 0.0033 |

`resp_h` 在当前制品上与标签取值集合完全分离，验证了目的地址捷径。`resp_p`、连接历史和连接终态也携带强标签关联。即使全局关联较弱，地址、端口和采集身份仍可能在单测试床内记忆固定环境，不能作为默认检测输入。

### 9.2 默认共同允许字段

E1 默认只使用以下 7 个字段：

- `duration`
- `orig_bytes`
- `resp_bytes`
- `orig_pkts`
- `resp_pkts`
- `orig_ip_bytes`
- `resp_ip_bytes`

### 9.3 条件允许字段

`proto`、`missed_bytes`、`ja3`、`ja3s`、`ja4`、`ja4s`、`ja4h`、`cipher`、`curve`、`version`、`resumed`、`request_body_len`、`response_body_len` 只能进入预注册的协议或指纹专属消融，不能混入默认共同基线。

实际内容具有明显测试床专属性：

- `ja4/ja4s` 仅 A/B/D 有有效内容，C 全为空字符串。
- `ja4h` 仅 C 有有效内容，A/B/D 全为空字符串。
- 原始逐流标签中的 TLS/QUIC 元数据只在 A/B/D 有效。
- HTTP 方法、主机、URI、状态码、用户代理和请求/响应体长度只在 C 有效。

### 9.4 禁止字段

以下字段不得进入检测输入：

- 地址与端口：`orig_h`、`resp_h`、`orig_p`、`resp_p`。
- 身份与绝对时间：`uid`、`capture_id`、`ts`。
- 测试床和采集条件：`profile`、`framework`、`encryption_profile`、`interval_s`、`jitter_pct`。
- 连接状态捷径：`conn_state`、`history`、`established`。
- 目的或应用身份：`server_name`、`http_host`、`http_uri`、`http_method`、`http_version`、`status_code`、`user_agent`。
- 标签派生字段：`label`、`label_raw`、`y`。

逐字段来源、有效测试床和理由见 `field_roles.csv`；逐测试床缺失与不同值计数见 `field_statistics.csv`。

## 10. 实验面板支持性

### 10.1 C 困难域

结构上支持：C 有 12 个完整单元并覆盖完整间隔抖动网格。困难程度尚未由 E0 证明，必须由 E1 开发区基线测量。`C_i30_j0` 的尺寸离群和 C 中 880 条 `malicious_recon` 必须保留在分层统计中，不能静默丢弃。

### 10.2 B/D 受控配对

结构上支持：B 与 D 的 manifest 都标记 Merlin，并共享 12 个间隔抖动组合，可按相同组合形成 12 个配对键。B 有 324 条 C2 连接，D 有 1,964 条，反映 QUIC 长连接与 HTTP/2/TCP 多连接的流语义差异。比较必须按完整组和方向报告，不能把逐流样本量相等当作控制条件。

小包足以核验框架、组键和标签结构，但没有读取 PCAP，因此不能独立证明 README 所称的所有运行环境因素都只差传输层。

### 10.3 A 简单域

结构上支持：A 有完整 12 单元。A 是否“简单”尚未由 E0 测量，只能在 E1 作为非退化面板验证，不能预先写成性能结论。

### 10.4 间隔/抖动面板

结构上支持：四个测试床共享 12 个完整 `interval_s×jitter_pct` 键。每个测试床每个组合只有一个 capture，因此组合留出必须保持整组，不能在单元内部随机拆分。

### 10.5 会话组限制

当前表只有每条 Zeek 连接的 `uid`，没有跨连接的应用会话标识。不能把 `uid` 当作应用会话，也不能用地址五元组跨 capture 拼接会话。当前最安全的划分原子是完整 `capture/cell`。若后续从 PCAP 建立应用会话，`session_id` 必须嵌套在 `capture_id` 内，整会话不得跨分区。

## 11. 候选组级划分算法

`candidate_groups.csv` 列出 48 个完整采集组、时间组合键、B/D 配对键与不含标签内容的清单哈希。所有 `split_assignment` 均为“未分配”，没有提前指定最终测试。

候选算法如下：

1. 以 `release、profile、capture_id、interval_s、jitter_pct` 组成完整 capture/cell 组键。
2. 冻结协议版本和随机种子后，以 `SHA-256(protocol_version|seed|panel|group_key)` 生成确定性顺序，不按标签计数挑组。
3. C 与 A 面板按完整 cell 分配；间隔抖动面板按完整组合键留出。
4. B/D 配对开发时，相同间隔抖动的两端保持同分区；方向迁移时，目标测试床整体不可用于模型选择。
5. 当前先只写开发训练、校准和开发验证分配。最终测试组在字段、过滤、模型、阈值、停止条件和随机种子冻结后才一次性确定。
6. 最终测试不得用于修正缺失值、选择捷径字段、调整阈值或选择模型。
