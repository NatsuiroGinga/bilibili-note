# R2 QUIC 可恢复采集实施计划

> **执行要求：** 按 `writing-plans` 与 `executing-plans` 执行；项目规则明确禁用测试驱动开发循环，本机不运行 `pytest` 或格式化，只执行一次覆盖改动的语法检查，并给出服务器目标测试命令。

## 目标

实现 QUIC v8.1 的可恢复正式采集：旧 v5 `23 finished + 1 failed` 证据不可覆盖，失败或未完成索引只能在全新 attempt 中逐项运行，正式发布只接受绑定同一冻结配置、连接身份、代码和输出哈希的 120 条全新正式身份。

## 范围

- 仅修改 QUIC 采集器、启动器、直接相关测试和本实施报告。
- 不连接服务器，不执行同步或采集。
- 不修改 E2、GPU 训练、ns-3 v3、DistilBERT 或旧运行制品。

- [x] 阶段 1：恢复规则、总控与 QUIC v5/index24 证据。
- [x] 阶段 2：定位采集器、启动器、配置与测试接口。已完成，并识别出 `D1`–`D5` 五处阻塞验收的实现缺陷，证据见[证据笔记](2026-08-07-R2-QUIC可恢复采集-notes.md)。

## 验收条件

1. 旧运行目录存在时拒绝复用或覆盖。
2. 单项诊断身份不能作为正式恢复输入。
3. 每个恢复项绑定原 v5 冻结配置、连接身份、代码和输出哈希。
4. 同一索引在新 attempt 中只允许一个完成身份；失败项保留证据并可换新身份重跑。
5. 只有 120 个全新正式项全部完成且绑定一致时才能原子发布汇总。
6. 本机 Python/Shell 语法检查通过；服务器目标测试命令可直接执行。

## 决策

- 恢复单位为单个索引，而不是向旧 v5 目录补写。
- 诊断运行仅用于解释失败，不进入任何正式矩阵。
- 发布清单记录每项身份和输出哈希，避免按文件名静默拼接。
