## 规则发现与子域路由（强制）

- Codex 启动时从项目根走到当前工作目录；每层只使用 `AGENTS.override.md`、`AGENTS.md` 或已配置回退文件中的第一个。离当前目录更近的规则优先。
- 默认组合上限为 32,768 字节。新增规则前必须核算全局文件与当前路径各层规则的累计字节，不能依赖超限后的截断内容。
- Codex 不会因为随后编辑了子目录文件而动态重新发现规则。从仓库根启动时，只要任务涉及下列子域，必须在分析或编辑前主动**完整读取**对应局部文件；任务横跨多个子域时逐一读取。

- 论文正文、章节结构、公式、数据证据或图件：`thesis/AGENTS.md`。
- `llm_probe` 代码、配置、测试、同步或服务器实验：`thesis/AGENTS.md`、`thesis/experiments/llm_probe/AGENTS.md`；涉及 `scripts/` 时还必须读取 `thesis/experiments/llm_probe/scripts/AGENTS.md`。
- 原始论文、PDF 或外部材料：`raw/AGENTS.md`。
- Obsidian 笔记、论文笔记或索引：`wiki/AGENTS.md`。
- 两份恢复文档或高层交付物：`output/AGENTS.md`。
- 计划、记录、审查报告或历史归档：`.Codex/docs/AGENTS.md`。
- RWKV 路线：当用户明确将当前会话绑定到 RWKV，或会话摘要含 `RESEARCH_ROUTE=RWKV` 时，先完整读取 `.Codex/docs/RWKV/AGENTS.md`；该局部文件规定的恢复路径取代 PINN/R2 默认路径。

- `.rules` 只控制命令执行权限，不能承载或代替内容规则。
- 不得假定 Codex 支持 Claude Code 的斜杠命令；只使用当前环境实际提供的技能、代理和可复现命令。

## 仓库边界

- 本仓库主线是《面向恶意流量检测的新型大模型训练方法研究》的论文研究、实验开发和 Obsidian 知识管理。
- 非论文历史资料仅作旁支保留。用户未明确要求时，不把它们作为默认上下文或论文结论来源。
- 原始材料、结构化知识、当前交付和详细过程分别归入 `raw/`、`wiki/`、`output/`、`.Codex/docs/`，具体写入规则由各目录的局部文件规定。
- 外部证据按“`raw/` 原件 → `wiki/` 全文核验与结构化笔记 → `thesis/` 或 `output/` 可公开论断”晋级。未通过来源真实性、全文和论断证据门槛的内容只能标为推论或待验证假设。
- `ns3/` 只保存本机源码压缩包、官方文档和安装参考；正式构建与运行使用服务器固定环境，本目录不是正式结果目录。

## 上下文恢复协议（强制）

- 恢复前先确定唯一研究路线。优先级为：用户在当前会话中的显式绑定、会话摘要中的字面哨兵、当前任务的明确研究对象。无法唯一判断时先询问用户，不得同时加载两套路线上下文后自行推断。
- **RWKV 路线**：用户明确绑定 RWKV，或会话摘要含 `RESEARCH_ROUTE=RWKV` 时，只按固定顺序完整读取 `.Codex/docs/RWKV/AGENTS.md` 和 `.Codex/docs/RWKV/RWKV路线总控.md`。默认不读取 `output/开题改进交接文档.md`、`output/第一创新点实验总控.md` 或 PINN/R2 过程文档；只有用户要求跨路线比较、返回 PINN/R2，或正式决定以 RWKV 替换论文主线时才按需读取。
- **PINN/R2 默认路线**：没有显式绑定其他路线时，按固定顺序完整读取 `output/开题改进交接文档.md` 和 `output/第一创新点实验总控.md`。二者链接的详细证据默认不逐篇读取，只在当前任务需要具体接口、要求核验或实时状态冲突时按链接读取。
- 在完成所属路线的默认恢复前，不得运行实验或重新分派子代理。任务涉及服务器实验时，随后先查询子代理状态，再只读核对服务器日志、GPU 进程、`screen` 会话和磁盘占用，防止重复启动。
- 运行事实以服务器原始日志和制品为准；验收状态以实现或审查报告为准；需求以实施计划为准；研究边界以所属路线总控为准。不得用旧进度覆盖新证据，也不得用实验日志擅自改变研究边界。
- 当前进度落后时，先依据实际制品、任务报告和日志修复所属路线总控，再分派下一任务；不得仅凭上下文摘要继续研究方向、数据集、方法公式、实验方案或任务状态。
- PINN/R2 的新裁决按原规则更新两份 `output/` 总控。RWKV 的新裁决、确定结果、实验路径和任务状态只更新 `.Codex/docs/RWKV/RWKV路线总控.md`；只有用户明确决定替换论文主线时，才同步修改两份 `output/` 文档。
- RWKV 会话的上下文摘要必须保留字面哨兵 `RESEARCH_ROUTE=RWKV`，PINN/R2 会话不得写入该哨兵。

- 更具体的 shell、同步、环境和服务器规则由 `thesis/experiments/llm_probe/AGENTS.md` 规定。

## 默认搜索排除边界（强制）

- 根目录以 `.ignore` 控制 `rg` 与已解析的 `fd`/`fdfind` 遍历命令的默认搜索噪声；在本机 Codex 明确验证支持前，不得依赖或新建 `.codexignore`。
- 文件遍历不得直接假定命令名为 `fd`：先执行 `command -v fd`，未命中时再执行 `command -v fdfind`，将命中的绝对路径保存为统一变量（如 `FD_CMD`），后续只通过该变量调用。两者均不存在时仅文件枚举可降级为 `rg --files`，其他遍历必须停止，禁止使用 `find`。
- `.ignore` 只允许排除 `.Codex/docs/archive/`、依赖目录、语言工具缓存、编辑器缓存和可再生临时渲染物。
- 不得排除 `AGENTS.md`、两份恢复文档、当前 `.Codex/docs/`、`thesis/` 正文与实验源码、`raw/`、论文 PDF、数据集、模型制品、实验 `runs/`、SwanLab 日志或普通实验日志。
- `thesis/experiments/llm_probe/.gitignore` 已排除 `runs/*`，默认 `rg --files` 不会列出运行制品。核验实验结果必须使用总控中的明确路径，或临时使用 `rg --no-ignore`、`"$FD_CMD" --no-ignore`，不得据此误判文件不存在。
- 核验历史备份时使用明确路径或 `--no-ignore`；不得为缩短上下文删除历史文件，也不得把历史内容复制回默认恢复文档。

## 实验工程开发范式（强制）

- `brainstorming` 只在需要提出新的研究机制、模型结构、物理公式、数据合同或实质性改变既有实验行为之前调用，用于澄清目标、列出候选设计、比较取舍并形成经用户确认的冻结设计；若还需要文献证据，随后进入 `research-ideation`，确认设计后再进入 `writing-plans` → `subagent-driven-development`。
- 常规实验启动、重复运行、参数扫描、结果查询、只读诊断、远程同步和已有根因明确的缺陷修复不得调用 `brainstorming`，不得借此重新打开已经冻结的实验合同或阻塞实验。冻结合同因新的结构性证据失效时，才允许在下一版本合同设计前重新调用；例如当前 QUIC v4 不追溯调用，只有其出现合同层面的失败并准备设计 v5 时才触发。
- 非平凡实验工程、功能实现或缺陷修复固定使用 `writing-plans` → `subagent-driven-development`；每个实现或修复子代理必须在其边界内调用一次 `test-driven-development`，先运行能够复现需求或缺陷的最小目标测试并观察预期失败，再实施最小生产改动并运行同一目标测试至通过。
- 纯只读探索、数据盘点、论文调研、独立复审、远程同步和仅启动既有实验的子代理不修改生产代码，不适用 `test-driven-development`。不得为了形式给这些任务补造测试，也不得由复审代理重复运行实现代理已经记录通过的同一测试。
- 主代理先建立持久化实施计划，写明边界、文件范围、验收命令、制品路径和阻塞条件；无计划不得开始多步骤实现。
- 执行阶段由主代理拆分任务、分派子代理、记录进度、独立复核并最终验收。不得以主代理直接实现替代已分派任务；同一时间只允许一个实现子代理修改同一任务范围。
- 实现完成后必须由新的审查子代理检查计划符合性和代码质量。存在严重或重要问题时，由修复子代理针对新问题执行一次最小红灯、绿灯周期并重新审查；不得删除正确实现、重建整项任务或补造测试历史。
- 子代理报告写入 `.Codex/docs/`，至少记录修改文件、失败与通过的测试命令和结果、格式化与静态检查、运行制品路径及遗留风险。
- 格式化与静态检查是任务交付门禁，不是服务器实验启动门禁。上下文恢复后以实施计划和进度记录为准，不得凭记忆重复分派任务。

## 调试纪律（强制）

- 遇到缺陷、测试失败或异常行为时必须组合使用 `systematic-debugging` 与 `bug-detective`：前者约束调查顺序，后者提供错误类型和语言模式速查，二者不能互相替代。
- 先按 `systematic-debugging` 调查根因，再用 `bug-detective` 识别常见模式；随后只提出一个可证伪假设，一次改变一个变量并做最小验证。
- 出现“先快速修一下”“跳过测试手工看看”或未调查便列多个修复方案时，立即停止并返回根因调查。
- 连续三次修复失败后停止打补丁，先与用户讨论是否需要架构调整，不得尝试第四次修复。
- 修复后执行对应的修复检查，并增加能覆盖原问题的回归测试。
